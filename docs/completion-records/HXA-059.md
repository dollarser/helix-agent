任务书（`docs/development/roadmap.md` §9B，`### HXA-059`）：把后端模型列表**自动带出来**——连接测试通过且后端返回列表时，Provider 行面板展示「后端可用模型」（有界显示 + 过滤），点选把模型预填进编辑表单（手输仍允许，不自动保存）；`Unsupported` → 显式「后端未提供模型列表，请手动输入」；phase 2 `Failed` → 展示既有稳定错误、不显示列表。查询是只读 GET，不新增任何网络/写路径；key 永不进入 UI 文本/日志/诊断；模型列表不入 logcat/Room 诊断字段；模板不写死模型名。

**交付**：
1. **probe 契约**（`provider:api`）：`ProbeOutcome.Ok.models` 携带 phase 2 实际列表（`Listed` → 规范化后带出；`Unsupported` → null；`Failed` → 既有失败语义不动）。列表在 probe 内规范化与有界：去空、去重（保序）、截断 1000（`CapabilityProbe.MAX_MODELS_IN_OUTCOME`，防御恶意/异常 provider 的超大列表；UI 另有 200 显示上限）。规范化函数 `CapabilityProbe.normalizeModelIds` 为 public（app 存储解析侧复用同一权威，避免两处漂移）。
2. **状态存储**（`app`）：`ConnectionTestStatus.Passed` 增加 `modelIds: List<String>?`（默认 null，构造兼容）；`ProviderTestStatusStore` 行格式**向后兼容**追加可选第 8 字段 = 模型列表 JSON 数组（空列表/无列表 → 不写第 8 字段，旧 7 字段行原样合法，读回 modelIds=null）；parse 对第 8 字段**独立降级**：坏列表 → modelIds=null 但 PASSED 状态与 capabilities 保留（fail-closed 只降级列表，绝不假装 passed 为 untested；capabilities JSON 损坏仍整体降级 Untested，既有语义不变）；读侧再跑 `normalizeModelIds`（防篡改文件无界增长）；`recordPassed` 加模型参数（尾参默认 null），`recordFailed`/`clear` 不带列表（FAILED 行恒 7 字段）。
3. **服务接线**（`app`）：`ProviderService.runConnectionTestNow` Ok 分支把 `outcome.models` 记入状态存储；行 UI 派生（`providerRowUi`，从 `ProviderService.rowUi` 提为纯函数，同模块可测）把 `status.Passed.modelIds` 带进 `ProviderRowUi.backendModels`；`update()`/`create()`/`delete()` 的既有 `testStatus.clear(id)` 自动清列表（确认无新逻辑）。
4. **UI**（`app`）：行卡片在状态 Passed 且列表非空时展示「后端可用模型 (N)」区块（`provider-models-section`）：过滤框（`provider-models-filter`）+ 可点芯片（`provider-model-chip-<index>`，index 基于过滤后显示序；模型 id 是不透明字符串，**绝不拼进 tag**，断言走文本）+ 显示上限 200（`MODELS_DISPLAY_CAP`，超出显示「共 N 个，显示前 200」）；点选 → 打开该 provider 的**编辑表单并预填** `fields.model`（复用 onEdit 打开路径 + 可选 model 初值；**不自动保存**，取消后行上模型不变）；Passed 且无列表（Unsupported/旧行）→ 行详情显式「后端未提供模型列表，请手动输入」（`provider-models-unsupported`）；Failed/Untested → 无区块（稳定错误文案走既有 `statusDetail`）。

## 验证中缺陷（仲裁会话发现并修复，随本 commit）

1. **生产缺陷：自托管无 key provider 的编辑表单「保存」被静默禁用（HXA-059 芯片预填→保存链路断裂）**。根因：`onEdit` 用 `editTemplateFor(protocol, endpoint)` 猜测编辑模板；自托管 provider（ollama/sglang 模板，`credentialRequired=false`）的端点非模板默认值时回退到 generic OpenAI 模板（`credentialRequired=true`），而该 provider 无存储 key → `keyOk=false` → 保存按钮 `enabled=false`，对话框永远关不掉。设备实证（诊断 dump 语义属性）：保存按钮带 `Disabled` 标记、cleartext checkbox `ToggleableState: On`、无错误文案——排除其他 `saveEnabled` 条件后锁定 `keyOk`。修复 = `editTemplateFor(config, hasStoredKey)`（无存储 key 时强制 `credentialRequired=false`；有 key 时模板原样，`keyOk` 恒真）。修复后 fixture 用例 ① 的「芯片→保存→行模型变更」链路与真实 SGLang smoke 的同一链路均绿。该缺陷在 HXA-059 之前即潜伏（任何编辑自托管 provider 的操作都会撞上），HXA-059 把它变成核心路径问题，故随本 HXA 修复。
2. **测试断言缺陷 ×4（`ProviderModelDiscoveryUiTest`，子代理编写，仲裁会话修复）**：
   - ① 预填断言读错属性：`OutlinedTextField` 的合并语义 `Text` 只带 **label**（`模型 ID`）不带输入值（诊断实证：表单值已正确写入且保存成功，但字段节点语义只有 label）→ 原断言恒挂。修复 = 改为端到端证明：取消后行模型不变（不自动保存）+ 保存后行上持久化模型变为芯片选中值（预填生效）。

## 决策记录：关键取舍与理由

1. **probe 内规范化 + UI 显示上限双界**：`normalizeModelIds`（1000）在 probe 边界做（防御恶意/异常 provider 的超大/脏列表，且是存储行的写侧与读侧同一权威）；UI 200 显示上限独立（行卡片渲染成本）。`ModelCatalogResult.Listed` 自身已有 1024/去重/非空校验，probe 侧规范化是 defense in depth（未来 adapter 变更或自定义 `ModelProvider` 绕过 typed 结果时仍受界）。
2. **设备 ②「Unsupported」用 Anthropic 协议而非任务书原文的「/v1/models 404」**：OpenAI-compatible 的 phase 1（`validateConfiguration`）**就是** models 调用（`WireModelProvider.validateConfiguration` 先调 `listModels`），404 会在 **phase 1** 以 PROTOCOL 失败，永远到不了 phase 2；协议层面无 models 端点的只有 Anthropic（`modelsPath() == null` → phase 1 走 stream 验证、phase 2 恒 `Unsupported`）。故 ② 以 anthropic 模板 + Anthropic SSE fixture 驱动真实的 Unsupported 路径，`provider-models-unsupported` 文案才有真实触发条件。（任务书 ③ 的「401」在 OpenAI-compatible 下按「第一次 200、第二次 401」实现，phase 1 过、phase 2 Failed——与任务书意图一致。）
3. **第 8 字段独立降级，不整体降级**：任务书明确要求——坏列表 → modelIds=null 且状态保留（列表是显示数据，丢了不假装 untested）；capabilities JSON 坏 → 整体 Untested（既有语义不动）。
4. **`normalizeModelIds` 设为 provider:api public**：app 存储解析侧复用（避免两处规范化逻辑漂移）；模块无 binary-compatibility validator，无 .api dump 需更新。
5. **行派生提为 `providerRowUi` 纯函数**：`ProviderService` 构造依赖 `HelixStorage`（Room，JVM 不可实例化、项目 JVM 测试无 Robolectric 先例），故把 `entity+status → ProviderRowUi` 的纯派生提为同模块 `internal` 函数直接单测（record → statusFor → row 全链路在 JVM 覆盖）；probe→record 的网络路径由 provider:api probe 测试 + 设备套件覆盖。
6. **芯片 tag 用 index 不用 id**：模型 id 是不透明字符串（可含 `/`、`-` 等，如 sglang 长路径 id），拼进 testTag 会破坏语义；断言走文本（任务书口径）。
7. **fixture 服务器顺序处理连接**：probe 五阶段严格串行（suspend 顺序），accept 线程内逐连接顺序处理保证 `OPENAI_PHASE2_AUTH` 的「第 N 次调用」状态机确定性；每连接 `Connection: close` 避免 keep-alive 复用歧义。
8. **ADR 状态**：不适用——本 HXA 不形成新架构决定：只读 GET 列表带出 + 显示/预填，不新增网络写路径、不扩大 Agent scope、不触碰 ADR-0012/0013/0014 边界；`ProbeOutcome` 契约只增 `models` 载荷（`Failed` 语义不动，HXA-044/057/058 行为不变）。
