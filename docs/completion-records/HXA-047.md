## 范围（对应 `docs/development/roadmap.md` HXA-047）

任务书原文：「实现受限 zip/tar 创建与解压；防 Zip Slip、symlink/device、文件数、总大小和膨胀比。」

- **`tools:files` 新增（纯格式 codec + 薄工具，无第三方依赖）**
  - `ArchiveCodec.kt`（新）：受限 zip/tar 的解析与产出，store-independent、可纯 JVM 单测。zip 用 JDK `java.util.zip`，tar 用自实现 classic-ustar 读/写（512 字节头）。此处承载两条内生防御：
    - **条目名**（`validateMemberName`）是 Zip Slip / 路径穿越主守卫——**拒绝**绝对路径、任何 `..`/`.`/空段、反斜杠与控制字符，而不是 normalize 折叠（core 的 `PathSyntax.normalizeRelative` 会静默折叠 `a/../b`，正是 slip 攻击想要的）。
    - **条目类型白名单**：只接受 regular file + directory；symlink、字符/块设备、fifo、hardlink、PAX 头一律 fail-closed。zip 里的 "symlink" 在此惰性（工具层只写 regular file，从不调 `createSymbolicLink`）。
    - 有界检查（条目数 / 单文件 / 总量 / 膨胀比）由 `ArchiveLimits` 从工具层传入——是**策略**不是格式事实，值由工具层持有。
  - `ArchiveTools.kt`（新）：`FilesArchiveTool`（`files.archive`，创建）+ `FilesExtractTool`（`files.extract`，解压）。薄工具层只做 scope + region 准入，containment 与配额全部经 `WorkspaceArtifactStore`（每次写入都复查）；把 codec 的稳定 reason code 映射成 sanitized 模型可见 detail。真实路径绝不进入参数 / 输出 / 失败文本（doc 10）。
  - 放置策略（显式、fail-closed）：`files.archive` 从任意用户区域（`input/`/`work/`/`output/`）读源目录、只把归档包写进 `work/`；`files.extract` 从任意用户区域读 `.zip`/`.tar`、只解压进 `work/` 内一个**既有**目录。destination region 固定 `work/` + store 逐成员强制 containment/配额 → 无法解压进 `.helix/` 或别的 scope。
  - 有界常量（策略）：条目数 10 000、单文件 16 MiB、总量 32 MiB、膨胀比 100、单包文件 64 MiB、递归深度 64。
- **`app`**：`AppContainer` 注册 `files.archive` / `files.extract`（生产工具表，`LOCAL_MUTATION`、`baseRisk L2`、`BuiltInOrigin`）。
- 回归测试：
  - `ArchiveCodecTest`（13 用例）：zip/tar round-trip、Zip Slip（`..` 与绝对路径名）、膨胀比（zip bomb）、条目数 / 单文件 / 总量上限、tar symlink / PAX 条目拒绝、tar 校验和损坏拒绝、tar 截断拒绝、`validateMemberName` 各类拒绝。
  - `ArchiveToolsTest`（19 用例）：descriptor 契约、create→extract round-trip（zip + tar）、region/scope 准入（destination 只在 `work/`、source 只在用户区域、跨 scope 拒绝）、**Zip Slip fixture 于工具层**（滑出条目被拒且无处落盘）、**膨胀比 fixture 于工具层**（bomb 被拒且不写）、tar symlink/损坏于工具层、冲突 + overwrite、空源、不支持的格式、缺 destination、非法参数、cancel 短路、配额 fail-closed、失败消息无真实路径泄漏（doc 10）。

## 决策记录：关键取舍与理由

1. **纯 codec / 薄工具分层 + 零第三方依赖**：格式解析与 Zip Slip/膨胀比/条目类型防御集中在纯 [ArchiveCodec]（无 store 依赖、可纯 JVM 单测）；工具层只准入 scope/region 并把 containment/配额交给 store。`:tools:files` 是 dep-free 的纯 JVM 模块，AGENTS.md 禁止任意加 Maven 依赖（要动 root build + `libs.versions.toml` + 两个 lockfile + `verification-metadata.xml` + ADR），故 zip 用 JDK `java.util.zip`、tar 自实现 classic-ustar——与仓库"格式自实现、不引重依赖"的既有取舍一致。
2. **白名单 fail-closed，而非黑名单**：只放行 regular file + directory，其余（symlink/device/fifo/hardlink/PAX）默认拒绝。新增的 tar 条目类型（未来格式演进）默认 fail-closed，不随时间静默变松。zip "symlink" 在此惰性——工具层从不创建符号链接，只写 regular file。
3. **放置策略把 destination 钉死在 `work/`**：archive 产物与 extract 目标都只能落 `work/`。这是"即使拿到 all-files / 更宽 scope，归档工具也无法往 `.helix/` 内部或别的 scope 写"的可被用户推理的边界，且与 store 逐成员 containment/配额复查形成纵深防御（codec 校验名 + store 校验落点，两道独立关卡）。
4. **Zip Slip 守卫是"拒绝"不是"normalize"**：`PathSyntax.normalizeRelative` 会把 `a/../b` 折叠成 `b`（成功穿越到根内任意点），所以 codec 的 `validateMemberName` 显式拒绝 `..`、绝对路径、空段、反斜杠、控制字符。这是本 HXA 的核心安全不变量，有 codec 层与工具层两级 fixture 覆盖。
5. **有界常量是策略、由工具层持有**：条目数 / 单文件 / 总量 / 膨胀比 / 深度上限写在工具层（`ArchiveLimits` 传参），codec 只负责按给定界执行。将来按真实场景调界，只改工具层一处，格式 codec 不动。
6. **ustar 偏移按 POSIX 标准**：name 0 / size 124 / mtime 136 / chksum 148 / typeflag 156 / magic 257 / version 263 / prefix 345。实现初版偏移整体前移 4 字节且 mtime 与 size 字段重叠，会（a）让自家 tar round-trip 因 mtime 覆盖 size 末尾而解压出 0 字节，（b）解析不了真实 GNU/BSD tar——已在 codec 测试 round-trip 下抓出并改正。受限解读者也只读 name/size/typeflag/magic/checksum/prefix，其余字段保持零。
7. **幂等性**：`files.archive` = `IDEMPOTENT`（给定源目录内容 → 确定性归档字节；目标已存在需显式 `overwrite`）；`files.extract` = `NON_IDEMPOTENT`（覆盖目标目录既有文件，重放效应依赖当前目录状态）。
8. **归档成员名保留 scope-root 相对路径**：`files.archive` 归档 `work/src` 产生 `work/src/...` 条目（而非剥掉源前缀），create→extract 自洽 round-trip 且成员名天然 containment-safe（无 `..`、无绝对路径，经 `validateMemberName` 再校验）。"相对源目录"的更直观语义不在本 HXA 范围，留待后续按需调整。
9. **两工具共享一个实现**：`files.archive` 与 `files.extract` 复用同一个 `ArchiveCodec` 与同一组 `ArchiveLimits`，不产生第二份 Policy——两者都是 `LOCAL_MUTATION` + `baseRisk L2`（逐次审批），符合 roadmap"both L2, sharing one implementation (no second Policy)"。
