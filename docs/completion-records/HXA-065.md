## 目标

roadmap M6 / HXA-065「通知和日历」+ doc 09（`architecture/android-platform-capabilities.md`）§11 + doc `overview.md` §11：

- 「通知 app allowlist/time window」；
- 「Calendar 先草稿再 commit」；
- 「权限关闭返回 `PermissionMissing`」。

本任务把这三条落地为**模型可调用、可审批、可审计的稳定工具契约**：3 个工具解析（已 schema 校验的）参数、调用**恰好一个**纯 JVM 端口方法、把闭合状态枚举映射成稳定 `ToolExecutorResult`——一个权限/策略拒绝是稳定 status（`permission-missing`/`draft-not-found`/`no-handler`），绝不一律回「成功」、更绝不用空列表冒充一次成功的读取（doc `overview.md` §11：「NotificationListenerService 层返回 PermissionMissing，不能返回空列表冒充成功」）。真实 Android 系统调用（读 `NotificationListenerService` 快照、`CalendarContract` 查询/写入、运行时权限判定）都在 Context-backed 生产端口里，安全控制（权限门、allowlist/window 过滤、草稿生命周期）住在那里，不在工具层。本任务**不做**新 Capability 声明、不做通知**写入**（只读快照）、不做日历**读/改/删**（只单条写新事件）（见「未实现/明确排除」）。

## 实现的契约

1. **3 个工具都是端口的薄 fail-closed 映射**（与 HXA-062/063 的 `browser.*`、HXA-064 的 `android.*/clipboard.*` 同一原则）：工具 `execute` 解析（已 schema 校验的）参数、调用**恰好一个**端口方法、把闭合状态枚举映射成稳定 `ToolExecutorResult`——`QUERIED`/`PREPARED`/`COMMITTED`/`PERMISSION_MISSING`/`INVALID`/`DRAFT_NOT_FOUND`/`NO_HANDLER` → Completed（携带稳定 status，拒绝态的 `reason` 是稳定类别串），`ERROR` → Failed（`bounded(reason)`），取消 → Cancelled，**绝不一律回「成功」**。参数缺失/越界 = `Failed`（`sideEffectFree`）。
2. **通知 app allowlist + time window**（roadmap HXA-065、doc 09 §11）：纯 JVM `filterNotifications` 只保留 package ∈ `allowedPackages`（1..16，每项 1..128 字符）**且** post 时间 ∈ `[since, until]`（`until > since`，窗口 ≤ 24h）的通知，newest-first 上限 20 条、每条 title/text 有界；`excludedCount` 报窗口内被 allowlist 滤掉的条数（让模型知道窗口里有它无权看到的更多活动）。其他 app 的通知**绝不**进入结果。
3. **权限关闭返回 `permission-missing`、绝不空列表冒充成功**（doc `overview.md` §11）：`notifications.query` 在 `NotificationPermissionProbe` 报 listener 未启用时、`calendar.commit_event` 在 `WRITE_CALENDAR` 未授予时，都返回**稳定 `permission-missing` status**（Completed 携带 status，`reason="permission-missing"`），而非空 entries 冒充一次成功读取、更非 ERROR。这是可观测、可诊断的显式「未授权」信号。
4. **日历先草稿再 commit**（roadmap HXA-065、doc 09 §11：「直接 Provider 写入属于 L2」）：`prepare_event` **只构建 + 持有**结构化草稿（不写日历、无需权限），返回 `draftId` 供用户/模型审看 title/time/timezone/location/notes；`commit_event` 是**唯一写路径**（L2 EXTERNAL_ACTION、每次调用都经审批卡批准），先过 `WRITE_CALENDAR` 闸门、再取草稿、写 Calendar Provider，成功则**消费**草稿（一份草稿至多 commit 一次，二次 commit → `draft-not-found`）。
5. **输出无 JSON null**：3 个工具的 Completed 输出 schema 合规，逻辑缺失值发 `""`（`NotificationsCalendarToolsMappingTest` 全覆盖）。
6. **纯 JVM 端口/助手 + Context-backed 实现的测试分工**：`filterNotifications` 是纯 JVM（JVM 单测独立钉住 allowlist/window/排序/上限/截断边界）；安全控制（权限门、allowlist/window 过滤、草稿生命周期、Calendar 写入）住 Context-backed 实现，经注入 seam 在设备验真实 gating + 生产过滤 + 真实权限探针 + 真实 manifest 声明。

## 未实现/明确排除

- **无新 Capability 声明**：可见的权限/前台控制是端口实现的运行时闸门（`NotificationPermissionProbe` / `CalendarPermissionProbe`），不是 capability 层能力；3 个工具 `requiredCapabilities = emptySet()`（不引入 capability 探测门；风险由 L2 + 审批卡 + 运行时闸门承接）。

- **通知内容属第三方 app 数据，有界出**：title/text 分别截断到 200/500、结果上限 20 条；不缓存/不持久化通知正文。
- **无永久特权 JS 桥、网页内容不受影响**：本任务与 WebView 无关，不引入 `addJavascriptInterface`。

## 决策记录：

1. **纯 JVM 端口 + Context-backed 实现（端口是安全边界、工具只做薄映射）**：与 HXA-062/063 的 `browser.*`、HXA-064 的 `android.*/clipboard.*` 同一原则。3 个工具只解析参数 + 把闭合状态映射成 `ToolExecutorResult`；真实 `NotificationListenerService` 快照读取 / `CalendarContract` 查询与写入 / 运行时权限判定都在 `NotificationsBridgeImpl`/`CalendarBridgeImpl`。这把工具层做成可 host 单测（20 例 fake bridge），设备测试再驱动真实系统服务——安全关键逻辑住可复现、可回归的层。
2. **权限关闭返回稳定 `permission-missing`、绝不空列表冒充成功**（doc `overview.md` §11）：`notifications.query` 与 `calendar.commit_event` 的未授权分支都映射成 **Completed + 稳定 `permission-missing` status**（而非空 entries 冒充成功、亦非 ERROR），使「未授权」成为模型可观测、用户可诊断的显式信号（JVM 用例 `queryPermissionMissingIsAStableStatusNotAFakeEmptySuccess` 钉住该语义）。
3. **日历「先草稿再 commit」、commit 是唯一写路径且消费草稿**（roadmap HXA-065、doc 09 §11「直接 Provider 写入属于 L2」）：`prepare_event` 无写无权限（L1 READ_ONLY），只铸造 draftId 持有结构化草稿供审看；`commit_event` 是 L2 EXTERNAL_ACTION、每次调用都经审批卡批准，先过 `WRITE_CALENDAR` 闸门再写，成功后 `drafts.remove` **消费**草稿（一份草稿至多 commit 一次，设备用例 `commitConsumesTheDraftSoItCannotBeCommittedTwice` 钉住）。这使「先给用户看、再落盘」的草稿模型在端口层可验证，而非依赖 UI。
4. **allowlist + window 过滤抽成纯 JVM `filterNotifications`**：JVM 单测独立钉住 allowlist/窗口/newest-first/上限 20/title·text 截断/excluded 计数边界；`excludedCount` 让模型知道窗口内还有它无权看到的更多活动（而非假装窗口就这么点）。其他 app 的通知绝不出现在结果里。
5. **通知 listener 用可注入 seam 而非依赖 flaky 的实时绑定**：生产 `NotificationListenerService` 需用户在系统设置手动启用、模拟器上 flaky，故 `NotificationPermissionProbe`/`NotificationSource` 是 seam，设备测试注入 `ToggleNotifProbe`/`FakeNotifSource` 确定性验两个状态；真实 `Settings.Secure` 探针另跑一例 smoke（无抛）。`HelixNotificationStore` 是纯 JVM（只持 `RawNotification`），listener 只负责从平台回调喂它。
6. **`requiredCapabilities = emptySet()`、风险由 L2 + 运行时闸门承接**：通知/日历授权是端口实现的运行时闸门，不是 capability；不引入 capability 探测门。`commit_event` 的写风险由 **L2 EXTERNAL_ACTION + 每次审批 + `WRITE_CALENDAR` 运行时闸门**三层承接。
7. **detekt 高返回/吞异常/泛型 catch 点用针对性 `@Suppress`（最小作用域、附一行说明）**：端口实现里「每守卫一个返回」与「把系统异常吞成稳定 ERROR/`permission-missing` outcome」是 fail-closed 语义本身；`write` 的深嵌套与两个长 `descriptor` 分别按 `findWritableCalendarId`/`notificationEntrySchema` 抽取降嵌套、`@Suppress("LongMethod")` 处理，均按仓库既有 `@Suppress` 惯例（见 `AndroidSystemTools.kt`/`BrowserTools.kt`）。

## 风险或后续任务

- **`WRITE_CALENDAR` 是危险级运行时权限**：manifest 声明后，commit 前需用户授予运行时权限；未授予走稳定 `permission-missing`。发布清单（HXA-122）申报该权限的用途文案待后续收口。
- **通知 listener 需用户手动启用**：`NotificationListenerService` 无法自授，未启用时 `notifications.query` 恒 `permission-missing`；这是平台约束，非缺陷。若未来要更强的「无空列表冒充」诊断，可在 reason 里补一句启用指引。
- **日历仅单条写新事件**：读/改/删/重复/提醒/多日历选择都不在范围；`findWritableCalendarId` 取首个可写日历，不做选择。若出现真实需求，在端口实现加读/改/删方法（工具 schema 会相应变化）。
- **通知内容属第三方数据、隐私敏感**：title/text 有界出、不持久化；若后续要通知摘要类 Skill（HXA-068 `notification-digest`，依赖本 HXA-065 验收），应在既有 `notifications.query` 之上做，不新增读路径。
- HXA-066（HTTP fetch 与前台任务）开工时：GET/HEAD、SSRF/redirect/size/timeout；URL Policy 检查全部 A/AAAA/IPv4-mapped IPv6（roadmap M6 / HXA-066）；与本任务的 `:tools:android` 无共享执行路径（不同安全边界，HTTP/前台是各自的新端口与前台服务）。
