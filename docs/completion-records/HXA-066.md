## 目标

roadmap M6 / HXA-066「HTTP fetch 与前台任务」前半 + security doc 7.9：

- 「GET/HEAD、SSRF/redirect/size/timeout」；
- 「URL Policy 检查全部 A/AAAA/IPv4-mapped IPv6，只把本次已验证地址集合交给 transport」；
- 「保持原 hostname 的 TLS Host/SNI/证书验证并复验 peer」；
- 「每跳重做 origin/DNS/IP/credential/scope 检查」；
- 「测试 DNS rebinding、连接复用、编码地址、metadata 和 redirect 逃逸」；
- 「Standard 仅公网；Advanced 只能使用用户预建的精确 LAN/loopback `NetworkOriginScope`，模型 URL 不能创建 scope」。

本任务把这六条落地为**模型可调用、可审批、可审计的稳定工具契约**：`http.fetch` 解析（已 schema 校验的）参数、调用**恰好一个**纯 JVM 端口方法、把闭合状态枚举映射成稳定 `ToolExecutorResult`——一次策略/SSRF 拒绝是**稳定 status `refused` + 稳定 reason code**（`rebind-blocked`/`metadata-blocked`/`lan-not-allowed`/`scope-violation`/`invalid-url`/`redirect-limit` 等），绝不一律回「成功」、更绝不用空 body 冒充一次成功的读取（与 HXA-065 的 `permission-missing` 同一原则）。**真实 socket 传输与全部安全控制**（解析、整组判定、只连已验证集、peer 复验、TLS 原 hostname、逐跳 redirect 再判定、有界读）都在纯 JVM `SsrfAddressPolicy` + `HttpFetchBridgeImpl` 里，不在工具层。本任务**不做**「前台任务」子单元（见「未实现/明确排除」）、**不做** POST/写 body（只 GET/HEAD）。

## 修改文件

**`:core:policy`（M3 策略模块源码；纯 JVM，新增连接期 SSRF 分类器）**：

- **`SsrfAddressPolicy.kt`**（新）：`object SsrfAddressPolicy`——**纯 JVM**（只吃网络字节序原始地址 bytes，无 `InetAddress`，故 host 可单测、可被 `:tools:android` transport 与设备测试复用）。三方法：
  - `classify(raw: ByteArray): IpAddressClass`：4 字节→IPv4、16 字节→IPv6、其他→`MALFORMED`。IPv4-mapped（`::ffff:a.b.c.d`）/ 废弃 IPv4-compatible（`::a.b.c.d`）IPv6 字面量**展开后按内嵌 IPv4 分类**，故**绝不**能冒充公网 IPv6。`::1`/`::` 有 96 位全零、若不加守卫会被误读成内嵌 `0.0.0.1`/`0.0.0.0`，故单列（`::1`→`LOOPBACK`、全零→`OTHER_RESERVED`）优先于展开。
  - `check(addresses, profile, lanScopes, endpoint): SsrfCheckResult`：对**整组**解析候选判定（security doc 7.9「一次解析并检查全部 A/AAAA 候选…任一候选违反当前 scope 时 fail closed」）。空集→`NO_ADDRESSES`；任一是 `CLOUD_METADATA`/`MALFORMED`→`RESERVED_METADATA`；按 `endpoint.residence()` 分公网路径（`checkPublicHost`：任一非 `PUBLIC`→`NON_PUBLIC_ADDRESS`，否则 `Allowed`）与 LAN/loopback 路径（`checkLanHost`：STANDARD→`LAN_NOT_ALLOWED`；无精确 `NetworkOriginScope` 匹配 host:port→`SCOPE_VIOLATION`；任一是 `PUBLIC`/`OTHER_RESERVED`（scoped host rebind 到公网/保留）→`SCOPE_VIOLATION`；否则 `Allowed`）。`Allowed.connectable` 就是「只把本次已验证地址集合交给 transport」的那组。
  - `revalidatePeer(peer, profile, lanScopes, endpoint)`：连接建立后把**实际 peer** 单独喂给同一 `check`（security doc 7.9「连接建立后复验 peer address」），拒 resolve 与 connect 之间改址的 in-flight rebinding。
  - `IpAddressClass { PUBLIC, LOOPBACK, LINK_LOCAL, PRIVATE_LAN, CLOUD_METADATA, OTHER_RESERVED, MALFORMED }`；`SsrfDenialCode { NO_ADDRESSES, RESERVED_METADATA, NON_PUBLIC_ADDRESS, LAN_NOT_ALLOWED, SCOPE_VIOLATION }`（稳定拒因码，供 UI/审计/测试）；`sealed SsrfCheckResult { Allowed(connectable); Denied(code, reason) }`。V4：cloud metadata（AWS `169.254.169.254`、GCP/Ali `100.100.100.200`）/ `127/8` loopback / `169.254/16` link-local / RFC1918 `10/8`·`172.16/12`·`192.168/16` / `1..223` public / 其余保留。V6：Azure IMDS `fd00:ec2::254` / `fe80::/10` link-local / ULA `fc00::/7` / `2000::/3` public / 其余保留 + 展开内嵌 IPv4。

## 实现的契约

1. **`http.fetch` 是端口的薄 fail-closed 映射**（与 HXA-062/063 的 `browser.*`、HXA-064 的 `android.*/clipboard.*`、HXA-065 的 `notifications.*/calendar.*` 同一原则）：工具 `execute` 解析参数、调用**恰好一个**端口方法、把闭合状态枚举映射成稳定 `ToolExecutorResult`——`FETCHED`/`REFUSED` → Completed（REFUSED 携带稳定 reason code、空 url/body）、`TIMEOUT` → TimedOut、`ERROR` → Failed（`bounded(reason)`）、取消 → Cancelled，**绝不一律回「成功」**。参数缺失/越界 = Failed（`sideEffectFree`）。
2. **整组候选判定、只把已验证集合交给 transport**（roadmap HXA-066、security doc 7.9）：`SsrfAddressPolicy.check` 对**全部** A/AAAA/IPv4-mapped 候选判定，任一是 cloud-metadata/malformed 即整组 `RESERVED_METADATA`、公网主机任一非公网即 `NON_PUBLIC_ADDRESS`（DNS rebind 逃逸被拦）；只有 `Allowed.connectable` 这组**已验证**地址交 transport 连接，绝不给「仍含违规候选」的部分集。
3. **连接后复验实际 peer**（security doc 7.9「连接建立后复验 peer address」）：`revalidatePeer` 把 `socket.inetAddress.address` 单独喂给同一 `check`，resolve 与 connect 之间改址（in-flight rebinding）被拒。
4. **原 hostname 做 TLS Host/SNI/证书**（roadmap「保持原 hostname 的 TLS Host/SNI/证书验证」）：`tlsIfNecessary` 用 `endpoint.host`（**原 hostname**，非解析出的 IP）建 TLS socket，证书对 hostname 校验。
5. **每跳重做 origin/DNS/IP/scope 判定**（roadmap「每跳重做 origin/DNS/IP/credential/scope 检查」）：redirect 换 origin 后**整跑** `fetchHops`（重新 parse → 重新 resolve → 重新 check → 重新连接 → 重新 peer 复验），跳数封顶 `maxRedirects`（超限 `redirect-limit`）；redirect 逃逸（302 指回 loopback/metadata）被拦。
6. **Standard 仅公网；Advanced 仅精确预建 LAN scope，模型不能创建 scope**（roadmap「模型 URL 不能创建 scope」）：`EgressPolicy` 从 **app** `profileStore` 读（`SafetyProfile` + `lanScopes`），模型 URL 只能**读**到 transport 的拒绝、**不能**加宽 scope；STANDARD 下 LAN/loopback→`LAN_NOT_ALLOWED`，ADVANCED 需**精确** host:port `NetworkOriginScope` 且不得 rebind 到公网/保留（否则 `SCOPE_VIOLATION`）。HXA-068 前 `lanScopes` 为空 → ADVANCED 下无 LAN host 可达（fail closed）。
7. **输出无 JSON null**：`http.fetch` 的 Completed 输出 schema 合规，逻辑缺失值发 `""`/0（`HttpFetchToolsMappingTest` 全覆盖）。

1. **纯 JVM 端口 + 原始 socket 生产实现（端口是安全边界、工具只做薄映射）**：与 HXA-062/063/064/065 同一原则。`http.fetch` 只解析参数 + 把闭合状态映射成 `ToolExecutorResult`；全部 SSRF/URL-Policy 安全逻辑住纯 JVM `SsrfAddressPolicy`（`core:policy`，可 host 单测 21 例）+ 原始 socket `HttpFetchBridgeImpl`（设备测试驱动真实 socket 11 例）。用**原始 `java.net.Socket`** 而非平台 HTTP 客户端，因它不受 cleartext-traffic 策略约束、对 127.0.0.1 天然可连，且能精确控制「只连已验证地址 + 原 hostname TLS」两个安全点。
2. **整组候选判定 + 只交已验证集 + peer 复验，三层拦 DNS rebinding**（security doc 7.9）：`check` 对**全部** A/AAAA/IPv4-mapped 候选判定（任一违规整组拒，绝不给含违规候选的部分集）→ transport 只连 `Allowed.connectable` → 连接后 `revalidatePeer` 复验**实际** peer（resolve 与 connect 之间改址被拒）。设备测试用 fake `AddressResolver` 把公网 hostname 确定性 rebind 到 loopback/metadata，证明零连接尝试即 `rebind-blocked`/`metadata-blocked`。
3. **原 hostname 做 TLS SNI/证书、绝不用 IP**（roadmap「保持原 hostname 的 TLS Host/SNI/证书验证」）：`SSLContext.getDefault().socketFactory.createSocket(socket, endpoint.host, port, true)` 以原 hostname 建 TLS，证书对 hostname 校验（对 IP 校验无法匹配真实证书）。
4. **每跳整跑 origin/DNS/IP/scope 判定、跳数封顶**（roadmap「每跳重做…检查」）：redirect 换 origin 后 `fetchHops` 从 parse 起整跑一遍（非只换 URL 直接连），`maxRedirects` 封顶防无限循环；设备测试验 `302` 跟随 + 新 origin 再判定 + 死循环 `redirect-limit`。
5. **egress 决策从 app `profileStore` 读、模型 URL 不能创建 scope**（roadmap「模型 URL 不能创建 scope」）：`EgressPolicy(profile, lanScopes)` 由 **app** 注入（`profileStore.profile` + 用户预建 LAN scope），模型 URL 只能**读** transport 的拒绝、**不能**加宽 scope；STANDARD 仅公网、ADVANCED 仅精确预建 `NetworkOriginScope`。HXA-068 前 `lanScopes` 空 → ADVANCED 下无 LAN host 可达（fail closed，非缺陷而是「scope 未建」的显式拒绝）。
6. **`http.fetch` 拆出「前台任务」子单元单独交付**：HXA-066 标题含「HTTP fetch 与前台任务」，但 verification-matrix HXA-066 行的验收命令与焦点（DNS rebinding/redirect/peer/scope 与 Standard/Advanced 网络边界）**只覆盖** http.fetch 网络边界（`:tools:android` + `:core:policy`），前台任务（dataSync 服务 + `onTimeout` + 6h/24h + 通知停止 + WorkManager）是 net-new **app-level** 基础设施、无独立验收行且 `:app` consumer 设备套件在本机偏 flaky。故本 commit 交付并验证 http.fetch + SSRF 网络边界（可复现、可回归、验收命令与 matrix 行完全一致），前台任务作为**后续子单元**（独立验收）紧随其后交付——保持「每个已 commit 子单元验收命令 = matrix 行 + 全绿」的既有口径。
7. **detekt 高返回/吞异常/泛型 catch/多函数点用针对性 `@Suppress`（最小作用域、附一行说明）**：transport 里「每守卫一个返回」「把系统异常吞成稳定 outcome」是 fail-closed 语义本身；`HttpFetchBridgeImpl` 23 个小型原语函数（逐 line/byte/framing）按 `TooManyFunctions` 类级 `@Suppress`（附一行说明），其余 `SwallowedException`/`TooGenericExceptionCaught`/`ReturnCount`/`LoopWithTooManyJumpStatements` 逐函数 `@Suppress` + 一行原因，均按仓库既有惯例（见 `AndroidSystemTools.kt`/`BrowserTools.kt`）。

### 实现的契约

1. **前台只覆盖用户主动发起的传输、等待审批/输入即停**（roadmap「等待审批/输入时停止」）：`DataSyncForegroundController` 仅 `TRANSPORT_ACTIVE` 起前台，`WAITING_APPROVAL`/终态/无 turn 立即停，故**绝非常驻后台**；决策纯 JVM（`TurnState` 入、`ForegroundServiceLauncher` 副作用），host 可单测。
2. **声明 dataSync + 两权限**（roadmap「声明 `dataSync` + `FOREGROUND_SERVICE_DATA_SYNC`」）：manifest `<service … foregroundServiceType="dataSync">` + `FOREGROUND_SERVICE`（API 29–33）+ `FOREGROUND_SERVICE_DATA_SYNC`（API 34+），`startForeground(id, n, FOREGROUND_SERVICE_TYPE_DATA_SYNC)`。
3. **Android 15+ `onTimeout()` 超限自停**（roadmap「实现 Android 15+ onTimeout()」）：override `onTimeout(int,int)`（API 35）在系统给的几秒宽限内 `stopDataSync`（否则系统判 app 崩溃）；`DataSyncLimitPolicy` 纯谓词建模 6h/24h 边界并 host 单测。
4. **通知提供停止**（roadmap「通知提供停止」）：通知带停止动作（`PendingIntent.getService` → `ACTION_STOP`），设备测试验触发后服务拆、通知撤。
5. **WorkManager 只做可延期维护/提醒**（roadmap）：沿用 HXA-065 既有 `GoalReminderWorker`（checkpoint 提醒走 WorkManager 可延期）；本前台服务**不做** WorkManager、也绝不把计算冒充 `dataSync`（只包用户主动发起的传输/文件处理）。

### 决策记录

8. **前台生命周期由 turn 状态驱动、纯 JVM 决策与 Android 副作用分离**：`DataSyncForegroundController`（纯 JVM，`TurnState`→`ForegroundServiceLauncher`）承载「何时起 / 停」，`AndroidForegroundServiceLauncher`（真实 `startForegroundService`/`stopService`）承载 Android 副作用——决策 host 单测 9 例、Android 路径设备验 3 例，与 M6 工具「端口是边界、薄映射」同一分层。`AppContainer` 用 `appScope` 收 `chatService.screen` 的 `activeTurn?.state`，前台服务与 turn 严格同寿命、turn 等用户 / 结束即拆，从机制上杜绝常驻后台。
9. **override 的是 `onTimeout(int,int)`（API 35）而非无参 `onTimeout()`**：核对 android-36 `android.app.Service` javap 与 Android 官方文档确认——Android 15 的 dataSync 等具体前台服务类型限时回调是 `onTimeout(int startId, int fgsType)`（API 35，`@RequiresApi(VANILLA_ICE_CREAM)`），另有 `onTimeout(int)`（API 34，仅 `shortService`）；**无参版本不存在**（首版按记忆写无参 override，编译期 `'onTimeout' overrides nothing` 才纠正，候选签名为 `onTimeout(Int)` / `onTimeout(Int,Int)`）。`@RequiresApi(35)` 门控 + minSdk 29 编译（compileSdk 36）；API<35 框架永不调用、方法存在即为死代码；`onStartCommand` 的 `ACTION_STOP` 停止动作是不依赖该回调的第二条停止路径。
10. **`runningInstance` 设备证据槽沿用 `GoalReminderWorker` 既有模式**：为设备测试能反射调用运行中 service 的 `onTimeout`，companion 存 `AtomicReference<DataSyncForegroundService?>`（`onCreate` 置、`onDestroy` 清，生命周期有界、无泄漏），与 `GoalReminderWorker.lastProcessedObjective` 同款「设备证据槽」惯例。

## 风险或后续任务

- **前台服务生命周期完全由 turn 状态驱动，无独立看门狗**：dataSync 前台起 / 停由 `DataSyncForegroundController.onTurnState`（turn 状态）唯一决定；系统 6h 限额由 Android 15 `onTimeout(int,int)` 兜底自停（API<35 无该回调）。当前 turn 状态机不会让 turn 长时间挂在 `TRANSPORT_ACTIVE`，且通知停止动作是第二停止路径；若未来允许 turn 在传输态长时间挂起，需再评估超时策略。
- **`lanScopes` 目前恒空**：HXA-068（Advanced 有界出网规则管理）落地精确 LAN scope 的类型化持久化/UI 前，ADVANCED 下**无** LAN/loopback host 可达（稳定 `scope-violation`）——这是 fail-closed 而非缺陷；HXA-068 会把规则 store 接进 `EgressPolicyProvider`。
- **原始 socket transport 的 HTTP 覆盖是 v1 有界子集**：处理 Content-Length / chunked / 读到关闭三种 body 帧、`Connection: close`（不复用连接）、HTTP/1.1；不处理 gzip/压缩响应体、HTTP/2、`Expect: 100-continue`、鉴权头。这些够 `http.fetch` 的 GET/HEAD 只读用途，若后续要更富的 HTTP 语义再扩展端口（不破坏现有契约）。
- **设备测试的 TLS 握手路径未断言**：设备测试对 loopback 无法提供受信证书，故 TLS（原 hostname SNI/证书）由 transport 构造保证、未做绿色断言（记录已注明，非绿色放行）。公网 https 真实握手归后续设备矩阵。
- **`http.fetch` 是 L1 NETWORK**：只读 GET/HEAD，但返回的响应体是**不可信外部数据**（web content）；下游把它当指令/凭据的既有边界（web content 标记不可信、Tool 输出脱敏）继续适用，本任务不改变该边界。
