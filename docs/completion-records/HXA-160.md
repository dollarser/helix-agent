# HXA-160：Activity 级浏览器宿主与 Context 功能验证

Date: 2026-09-09
Status: completed

## 交付

- `BrowserViewOwner` 由 Activity 持有，用真实 Activity Context 惰性创建 WebView；应用控制器只弱绑定 owner。下载继续使用 Application Context，不把所有 Context 一律替换。
- attach/detach、pause/resume 和旧页回调校验 owner/宿主身份。释放时先使绑定失效，清空宿主引用，再销毁 View；旧 Activity 的迟到解绑不能伤及新宿主。Compose 根据 View 身份重建绑定。
- 后台保留 View；真正销毁清理 loading/history 可用性与 DOM token，保留 URL/标题。无 owner 的非空 open 明确失败且不增加标签；无真实页面的历史/重载不假报成功。没有自动恢复 URL、POST、表单或 ToolCall。
- JS alert/confirm/prompt/beforeunload 仅在选中、resumed、可用 Activity 中显示；后台、导航、停止、切标签和销毁终结待处理结果一次。独立对话框组件管理窗口结果，未增加永久 JavaScript bridge。
- 真实系统 AutofillService fixture 使用合成数据验证填写、保存、重建和服务撤销；服务只在测试 APK 中，测试前后的系统配置恢复。

最终 Autofill 单例在双 API 各连续 3 次复验通过（每次含重建前后填写/保存及服务撤销）。最终 API29/36 浏览器默认套件均 `OK (38 tests)`，各 36 项执行通过、2 skip、0 failure/error；MainActivity/首次启动回归各 `OK (2 tests)`、无 skip。浏览器默认套件共 38 项，其中 `rawPlatformWebViewLifecycleControl` 与 `continuousResourceSoak` 两项是既有显式 opt-in 对照/长稳，不在默认运行内；不得把 runner 的 `OK (38 tests)` 记为 38 项均执行。包含新增无 owner 失败、旧回调、后台、JS 结果与 Autofill；MainActivity 用例连续重建三次，验证共享逻辑控制器及仅显式导航创建新 Activity View。

Autofill 夹具最初失败过程保留：API29 选择填充后立即读取 DOM 为空；API36 初始输入定位未聚焦预期字段，定位修正后仅聚焦仍未触发请求，真实输入字符后填写/保存成功。扩大至完整套件后发现编辑入队与保存之间的异步竞争，改为等待 DOM 中编辑结果后再提交保存，继续断言服务实际收到编辑值。后续输入焦点问题由 API29 的 `Injecting to another application requires INJECT_EVENTS permission` 定位到系统保存窗口退出/Activity 重建之间的竞争；最终等待真实 WebView 窗口重新获得焦点、限定目标 App 的 HTML 输入节点，并通过公开 InputConnection.commitText 提交合成字符。连续复验暴露过模拟键盘丢字（例如预期 edited 实际 dited）；InputConnection 仍经过 WebView 原生输入处理和系统 AutofillService，避免依赖模拟器软键盘组合输入状态。填写选择/保存仍点击真实系统窗口，既没有直接给 DOM 赋值，也没有直接调用 Autofill 回调。曾尝试的无障碍 SET_TEXT 在已测 WebView 上不能稳定触发真实 Autofill 通知，已撤回。API29 还复现直接调用 AutofillManager.commit 时系统认为值未变化；最终使用合成用户名/密码，通过与 browser.click 相同的 DOM 点击路径触发表单提交，并断言服务器返回成功页面，再检查系统保存 UI/回调。截图与 URL 证明 API36 虚拟节点 ACTION_CLICK 曾返回成功但未提交，因此不能据该返回值假报操作完成。系统 UI 查找覆盖 interactive windows；没有移除生产 WebViewClient 或绕过 URL Policy。没有跳过测试、伪造服务回调、扩大超时或在产品中强制触发 Autofill。

## JNI/Binder 有界证据

API29：WebView 91.0.4472.114；API36：133.0.6943.137。专用 arm64 模拟器，同一 NDK agent SHA-256 `362f762860855518703a408ae07dba19ef52a58648c36119534d13c27c8c2531`。

```sh
ANDROID_HOME=SDK_PATH python3 scripts/diagnostics/run-jni-reference-trace.py SERIAL --count 100 --scenario settled-close
ANDROID_HOME=SDK_PATH python3 scripts/diagnostics/run-jni-reference-trace.py SERIAL --count 100 --scenario network-recreate
ANDROID_HOME=SDK_PATH python3 scripts/diagnostics/run-jni-reference-trace.py SERIAL --count 100 --scenario network-background
```

`settled-close` 同一观察器改前/改后各 100 轮，两个 API 的目标引用均创建 1000、删除 1000、残留 0、unmatchedDeletes 0。全局 summary live 分别为 API29 6、API36 10（前后相同），不是全局 JNI 引用为零。

| API | Context 改前 local/proxy Binder | 改后 local/proxy Binder | 结论边界 |
| --- | --- | --- | --- |
| 29 | 161 / 50 | 205 / 49 | 结束时采样，local 增、proxy 减；不是增长斜率或泄漏证明 |
| 36 | 259 / 78 | 216 / 76 | 结束时采样降低；不得据此宣称整体内存改善 |

真实网络重建与后台切换在双 API 各 100 轮，四条路径均目标创建 1000、删除 1000、残留 0、unmatchedDeletes 0；服务端各收到 100 个不同 iteration 的请求。重建/后台两路径结束时 local/proxy Binder 分别为 API29 435/44、41/44，API36 339/67、227/103。原始记录包含全局引用与进程状态，不把非目标组当成目标泄漏。

JNI 目标配对未见劣化。系统 Binder 生命周期问题继续开放；单点计数无法替代 GC/系统服务释放归因和长稳。既有诊断 agent/采样仅在测试进程，不打包产品。历史应用规避和根因边界见 [原生问题报告](../development/native-reference-mitigation.md)。

诊断脚本原先在结束时读取可被后台构建替换的 APK 散列；本轮修正为安装不可变副本并记录该副本散列。迭代期记录保留，使用固定安装副本复跑三条路径，避免将末尾散列当作安装身份。诊断与最终功能测试之间仅迭代了测试夹具，生产浏览器实现未变；各次诊断安装副本及独立 hash 均保留，不混称所有测试使用同一个 APK。

本地日志、APK/agent hash、版本与原始采样保存于被忽略的 `build/reports/hxa160/`。

文档、ADR、i18n、secrets、Python 语法及 diff 门禁通过。
