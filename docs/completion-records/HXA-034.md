# HXA-034 完成记录

- 目标：Approval hash 与一次性消费（roadmap M3）：canonical JSON + tool/version/schema/scope/session/target hash；一次性、过期、拒绝和并发 consume。复用存储层封闭 `ApprovalDecision(APPROVED, DENIED)` 和 DAO 的 `decision = 'APPROVED'` 原子守卫，禁止重新开放自由字符串。明确区分“决定记录已处理”和“批准凭证被消费”：只有类型化 `APPROVED` 能生成/消费 Approval Proof，`DENIED` 即使已记录/已查看也不能授权执行，禁止用 `decision != null` 或 `consumedAt != null` 单独判断批准。页面/UI token 也绑定 approval；测试 pending/denied/过期不可消费、任意字符串无法进入仓库 API、并发只有一个批准消费成功。

- 实现的契约（逐条对照任务书）：
  - canonical JSON + tool/version/schema/scope/session/target hash：`ApprovalBinding.canonicalJson`（9 键字母序固定 JSON + 全转义）→ `hash`（SHA-256）；tool/version/schema/scope/session/target 六字段逐项变化测试 + toolCallId/argsHash/uiToken 一并覆盖（9/9 字段敏感）。
  - 一次性 consume：`consumeByBinding` 单条 UPDATE 的 `consumedAt IS NULL` 守卫 + 重复消费测试（仓库 API 抛、SQL 0 行）。
  - 过期：`expiresAt` 列（NOT NULL DEFAULT 0）+ mint 的 `EXPIRED` 拒绝 + SQL `expiresAt > :now` + 边界 `now == expiresAt` 即过期测试 + 迁移行 0 值不可消费测试 + 创建期窗口上限（≤24h、`expiresAt > createdAt`）。
  - 拒绝（DENIED 不授权）：`decide` 类型化封闭集 + mint 的 `DENIED` 拒绝 + SQL 字面量 `decision = 'APPROVED'` 双保险；“已记录/已查看”（decidedAt 非空）不铸造不消费有专门测试。
  - 并发 consume：无应用层锁；SQL 行级原子更新，8 线程恰一个成功（matrix 焦点，设备测试）。
  - 复用封闭 `ApprovalDecision` 与 DAO 原子守卫，禁止自由字符串：仓库 API 全类型化（`decide` 只收枚举）；DAO `decide` 的 SQL 守卫保留并有自由字符串 0 行测试；本任务**未**新增任何字符串决策路径。
  - “决定记录已处理”≠“批准凭证被消费”：`mint` 纯只读（不写任何列）；`consumedAt` 只由原子 consume 写入；`deniedIsProcessedButNeverACredential` 测试断言 DENIED 行 `decision/decidedAt` 有值但 `consumedAt` 恒 null 且不可铸造/消费；mint 的拒绝码把 PENDING/DENIED/CONSUMED/EXPIRED 与“可铸造”显式区分，不存在 `decision != null`/`consumedAt != null` 的捷径判断。
  - 只有类型化 `APPROVED` 生成/消费 Proof：`Minted` 只在 APPROVED+未过期+未消费时返回；consume 的 SQL 同时要求 `decision = 'APPROVED'`（即使拿到伪造 Proof 对象也过不了库）。
  - 页面/UI token 绑定 approval：`uiToken` 是 9 字段之一参与哈希（变化→不同 hash 测试）。
  - 测试 pending/denied/过期不可消费、任意字符串无法进入仓库 API、并发仅一个成功：设备 6 测试 + 守卫 5 测试逐条覆盖（仓库 API 层无字符串入口 + DAO 层自由字符串 0 行双证）。
- 关键实现决策：
  - **schema v2 用 RENAME 而非加列**：列语义从“args 摘要”变为“全量绑定哈希”，保留旧列名会造成双哈希歧义；`expiresAt INTEGER NOT NULL DEFAULT 0` 使所有 v1 迁移行**永久过期**（fail closed——旧批准迁移后永远无法铸造/消费凭证，安全侧失败）。迁移可逆性：结构上可回退（反向 ALTER 同样简单），行为上旧批准全部作废，符合“每 ToolCall 有限期”的产品约束。
  - **mint 只读、consume 单写者**：区分“记录已处理”与“凭证已消费”的落位——任何读路径（mint/resolve）永不改写 `consumedAt`，唯一写者是 4 条件原子 UPDATE。
  - **24h 上限在仓库 API（`MAX_APPROVAL_TTL_MILLIS`）**：产品上限在写入点强制（构造/入库前拒绝），不依赖 SQL 或调用方自觉；dispatcher（HXA-035）创建审批时必然经过此 API。
  - **`core:storage → core:policy` 依赖边**：Repository 公开 API 以 policy 类型（`ApprovalBinding`/`ApprovalProof`/`ApprovalMintOutcome`）为契约；core:policy 保持零 Android 依赖的纯 JVM 叶子，方向与 `tools:framework → core:policy`（HXA-031）一致。
  - **设备迁移测试走生产路径**：`Room.databaseBuilder(...).addMigrations(MIGRATION_1_2).build()` 对带数据的 v1 文件——Room 自己执行迁移并更新 `room_master_table` identity hash，与真机升级完全同路径（手工 `Migration.migrate` + `PRAGMA user_version` 会被 Room identity 校验拒绝，见排障 2）。
- 未实现/排除：Dispatcher 管线（validate→capability→policy→approval→execute→verify→audit，HXA-035）；审批 UI/审批卡（HXA-036，`uiToken` 的生成方在 UI 层）；binding 的调用点组装（dispatcher 从 ToolDescriptor+注册事实+session 生成，本任务只提供类型与哈希）；规则/审批的 app 层持久化 UI 无变化；无新 ADR（复用 ADR-0005 的类型化审批语义与 doc 02 §9.1/§9.2 存储约定，schema v2 为可逆实现细节，本记录留档）。

- 排障：
  1. `MigrationTestHelper.runMigrationsAndValidate(name, 1, false, MIGRATION_1_2)` 语义陷阱：它**从 schema export 重建**数据库（手工插入的行被清掉）且不返回含行数据的库——首次运行迁移测试只见 v1 列（断言直接暴露）。
  2. 退而求其次的手工路径 `MIGRATION_1_2.migrate(db)` + `PRAGMA user_version = 2` 被 Room 拒绝：`Room cannot verify the data integrity ... Expected identity hash: f7c0562b..., found: 8792eb4b...`——`room_master_table` 仍存 v1 identity hash，而该表由 Room 在真实迁移后更新，不可手工绕过。最终采用生产路径（`addMigrations(...).build()`），同时顺带验证了“迁移缺失时 Room 拒绝打开”的默认行为。
  3. `SupportSQLiteDatabase.query` 无 Kotlin vararg 重载（`query(String, Object[])`）：`db.query(sql, id)` 不编译 → `arrayOf(id)`。
  4. `v1ExportMatchesTheCodeBuiltSchema` 在版本升到 2 后语义失效（代码构建的是 v2，与 1.json 永不再匹配）：删除；drift-loop 由 `v2ExportMatchesTheCodeBuiltSchema` 继承，1.json 保留为迁移基线（仅 existence 断言 + 被 v1ToV2 测试消费）。
  5. 生命周期测试 `seedToolCall` 固定 session id，同一测试第二次调用撞 `sessions.id` UNIQUE → session/turn id 按 callId 唯一化。
  6. 并发测试断言 `consumedAt == 160`（第一个 worker 的时间戳）失败（胜出者是 161 的 worker）→ 断言改为“库中值等于实际胜出者的时间戳”（`successes.single()`）。
  7. 金色 canonical 串按行拆 chunk 时每个 chunk 头多带一个 `"`（`"scopeRef":"ws-1","` 的收尾引号已是下一个键的开引号），JUnit diff 精确指出 stray quote 位置 → chunk 2/3 去头引号。
  8. `spotlessApply` 会把长 raw string 的插值表达式折行（`${"b".repeat(\n 64,\n)}`，内容无害）并改变行长 → 所有 detekt 行长问题都在 format 后按实际文件重定位修复。
  9. Kotlin 智能转换：`list?.contains("1.json") == true && list != null` 中第二个条件被编译器判为恒真（前者为 true 已蕴含非空）→ `?: false` 双布尔重构消警告（detekt/编译器零告警纪律）。
