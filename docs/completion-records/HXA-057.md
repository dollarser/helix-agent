## 实现的契约

**解析 + 每次使用实时复核（`SafTreeScopeResolver.resolve`，全部 fail-closed → `ScopeNotAvailable`，消息不含 URI）**：
1. grant 存在（`registry.find(scopeId)`）；
2. `deriveScopeId(grant.treeUri) == scopeId`（aliasing / 文档 ID 欺骗——scopeId 与 treeUri 的哈希必须自洽）；
3. `check.verify(treeUri) != null`（provider 消失 / 撤销 / 进程死亡重启）；
4. `facts.rootLive`（根文档存在）；
5. `facts.authority == treeUriAuthority(treeUri)`（provider 身份——恶意 provider 换 authority 即失败）；
6. `facts.rootDocumentId == treeUriRootDocumentId(treeUri)`（URI 变化——根文档 ID 改变即失败）；
7. 模式门（READ→`readable`，WRITE→`writable`；只读 grant 拒绝写）。

**模型不透明**：模型/Tool/诊断/日志只看到 `scope:<saf-…>:<相对路径>`（`toModelReference()`）与显示名；`content://` URI 只进 `ContentResolver`，不进 `SafTreeScope`/`SafTreeSource`/任何 `ScopeNotAvailable` 消息/来源列表。

**只读浏览后端**：`FileManagerService` 对 `saf-` scope 的 list/read/preview/mime/info 全部经 `verifySaf` 复核后走只读 `SafTreeReader`（`DocumentsContract`）；变更入口对 SAF scope fail-closed。`realFileFor`（分享）把 SAF 文档暂存到 app 私有目录，`content://` 分享 URI 瞬时被 OS 消费，从不渲染（doc 10）。模型侧 `files.*` 工具仍是 nio-only（对 `saf-` scope fail closed）——本 HXA 的浏览后端服务用户驱动的文件管理器（受每次调用复核治理，满足"禁止 UI/DAO 直接操作外部文件"）。

## 验证中缺陷（设备期发现，已修复随本 commit）

1. **生产缺陷：根级文件路径的 walk 错位（Kotlin `substringBeforeLast` 无分隔符语义）**：`walkToDocument`/`walkToDocumentMetadata` 用 `relativePath.substringBeforeLast('/')` 取父目录段——Kotlin 在无 `/` 时返回**原字符串**而非空串，导致 `read/stat/copy("a.txt")`（根级文件、路径无 `/`）先按"父目录 = a.txt"walk 进文件自身 id，再在其中找子 `a.txt` → 恒 `FileNotFoundException`。设备 `SafTreeReaderDeviceTest`（read/stat/copy 根级文件用例）捕获；JVM fake 未覆盖该 walk 分支。**修复**：`splitLastSegment`（显式 `lastIndexOf('/')`：`<0` → 父目录为空串），两处调用点同改。设备修复后 24/24 × 2 全绿。
2. **测试夹具缺陷：`TreeDocumentsProvider` 子列表 URI 段单复数错误**：fixture 匹配 `.../document/<id>/child`（单数），而 `DocumentsContract.buildChildDocumentsUri` 实际发出 `.../document/<id>/children`（复数——设备 logcat 实锤 `segments=[document, root, children]`，与框架 `UriMatcher` 的 `document/#/children` 一致）→ 子列表查询落 else 分支返回空 cursor，全部按名查找 fail-closed。**生产 reader 无错**（用框架 API 构造 URI，真实 SAF provider 即按此应答）；仅 fixture 路径段写错。修复 fixture 匹配段 + KDoc。

## 决策记录：关键取舍与理由

1. **Path 基解析器 vs SAF tree**：统一 `FileScope` 解析（`ScopeRootResolver`/`WorkspaceArtifactStore`）是 nio 的，而 SAF tree **没有 `java.nio.file.Path`**——既有 nio 路径对 `saf-` scopeId 已天然 fail closed（`scopeRoots` else 分支抛 `ScopeNotAvailable`）。因此 SAF 不复用 nio 解析器，而另设 `SafTreeScopeResolver`（复核）+ `SafTreeReader`（`DocumentsContract` 只读后端）两个 SAF 专用接缝，由 `FileManagerService` 按 `scopeId` 前缀（`saf-`）分发。二者共用 `SafGrantStore`（同一 grant registry）与同一"模型只看到 scopeId + 相对路径"契约，模型不透明度不变。
2. **只读里程碑决定**：用户选定"解析 + 只读浏览后端"。SAF scope 在文件管理器中只读（`FileSourceKind.SAF`、`supportsMutation=false`），变更入口 fail-closed——沿用 HXA-045 all-files 的"即使有授权也只读、绝不覆盖"可推理边界。写后端显式推迟（见未实现范围），不混入本 commit、不留桩。
3. **每次使用实时复核而非一次性**：resolver 每次 `resolve` 都重跑 7 步（含 `check.verify` 的 live `resolver.query`），所以撤销、provider 卸载、根目录删除、进程重启后 grant 不再应答，都会在**下一次浏览**即 fail closed，而不是缓存到下次启动。`liveSources()` 同样每次调用复核，dead grant 从来源列表即时消失。
4. **provider 身份 / 根文档 ID 是结构性 + 篡改防御**：生产 `ContentResolverSafTreeCheck` 从**存下的 URI** 解析 authority/rootDocId（所以生产里它总与 grant 自洽）；resolver 第 5/6 步钉住它们，作为对**篡改的 grant / 换 authority 的 provider** 的防御——JVM fake 证明了 mismatch 时 fail closed，设备测试用 `LyingContentProvider` 固定真 `ContentResolver` 路径。
5. **空目录 ≠ 撤销**：复核的活信号是 `resolver.query(treeUri)` 返回 **cursor**（非空），不是行数——一个**活的空文件夹**返回 0 行 cursor 仍判活（`empty-tree` 用例），撤销/provider 消失表现为 query 失败（null cursor 或异常）。这与 HXA-044 `ContentResolverSafGrantProbe` 在设备上已证明的口径一致。
6. **相对路径↔文档 ID 的歧义名 fail closed**：SAF 用不透明文档 ID；`ContentResolverSafTreeReader` 按显示名逐级 walk，**同一段 0 个或多个匹配都抛 `FileNotFoundException`**（歧义名绝不猜）——设备 `dup/same.txt` 用例固定该边界。
7. **分享暂存有界 + fail closed**：`realFileFor` 把 SAF 文档 chunk-copy 到 app 私有 `shareDir`（`SAF_SHARE_CAP` 有界；超限删除部分文件并抛 `SafTreeReadLimitExceeded`），FileProvider 造瞬态 `content://` 分享 URI；文档 ID 与原始 `content://` URI 从不渲染（doc 10）。
8. **单一 grant registry**：`AppContainer` 的 `safGrantStore` 与 `featureFiles.grantStore` 是**同一个** `SafGrantStore`（同一持久化文件 `workspaces/saf-grants.json`）——SAF tree scope 与 SAF 导入/导出共享同一份 persisted grant，`SafGrantStore` 实现 `SafTreeGrantRegistry` 供 resolver 复用，不引入第二份 registry。
9. **`check-docs.sh` 最小放宽**：per-HXA bullet 的里程碑正则加 `[A-Za-z]?` 以接受 M5B（roadmap §9A/§9B 引入字母子里程碑）。仅放宽这一处的匹配，不改其他门禁逻辑；记录于此以维持"脚本改动有根因"的约定。
10. **ADR 状态**：本 HXA 不触发新 ADR，不影响已接受 ADR-0012（capability-first 授权）与 ADR-0013（store 形态）；SAF 只读 + 模型不透明的决定落在本 HXA 范围内（`SafGrantStore` 复用 + 只读浏览后端），无需新 proposed ADR。
