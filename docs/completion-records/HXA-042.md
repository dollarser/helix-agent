## 范围（对应 `docs/04-roadmap-and-backlog.md` HXA-042）

- `read`：`offset/maxBytes` 分页、UTF-8 编码边界（跨窗多字节序列丢弃，`nextOffset` 落在序列起点）、稳定 EOF（offset≥size 返回终窗而非错误）、二进制返回 base64。10 MiB 文件 = 恰好 10 个 1 MiB 窗、无字节跳过/重复（`ReadToolTest.aTenMiBFileIsExactlyTenOneMiBWindowsWithNoByteSkipped`）。
- `write`：region（input/work/output）准入 + 前置 hash 覆盖守卫（`overwrite`+`expectedSha256`）。
- `edit`：精确 span 替换，fail-closed 唯一性（非 replaceAll 时 oldText 必须恰好出现 1 次），UTF-8 文本文件守卫（二进制/UTF-16 拒绝），`expectedSha256` 乐观并发。
- `files.stat` / `files.list`（有界分页+truncated）/ `files.search`（名字子串、大小写不敏感、`maxResults`/`maxScan` 双上限、不跟随 symlink）/ `files.mkdir`（parents、已存在拒绝、region 限制）。
- 所有工具：真实路径绝不进入参数/输出/失败消息（doc 10）；失败消息一律 sanitized 稳定串；cancel 信号短路为 `Cancelled`。
- **contractHash 门槛（本任务硬门槛）**：`ToolDescriptor.contractHash` = SHA-256(全安全 descriptor 规范化串)（ADR-0011，proposed）；`ApprovalBinding` 增加 `contractHash` 字段并进入 `canonicalJson`/`hash`；`ToolDispatcher.buildBinding` 从**当前注册** descriptor 取 `contractHash`。`serverProvidedHints` 刻意排除（不可信展示文本）。
- `ContractHashGateTest`（`tools/framework`）机械证明：每个安全字段单独变化 → `schemaHash` 不变、`contractHash` 变、`ApprovalBinding.hash` 变（旧凭证不匹配）；`ToolDispatcherTest` 证明 dispatcher 实际绑定当前 descriptor 的 `contractHash`。
- `AppContainer` 注册 7 个文件工具 + `time.now`；app 自身 workspace scope（`filesDir/workspaces/app`），`ensureLayout`。

## 决策记录：关键取舍与理由

1. **选择"完整 descriptor 的 contractHash"关闭审批失效缺口**（roadmap 二选一中的 ADR 路径），而非"强制安全字段变化必升 version"。理由见 [ADR-0011](../adr/0011-full-descriptor-contract-hash.md)（Status: proposed）：registry 不保留旧 version 历史，进程内无法可靠判定"相对上次是否改了安全字段"；version 语义已用于契约演进，不宜再编码安全字段。
2. **`contractHash` 覆盖字段**：name、version、description、schemaHash、operationClass、baseRisk、timeout(ms)、maxOutputBytes、requiredCapabilities(按 name 排序)、idempotency、executionTarget、origin.canonicalOf()。`description` **纳入**（fail-closed：描述变化强制新审批）；`serverProvidedHints` **排除**（不可信，纳入会让 MCP 服务器握有审批否决权）。字段顺序/编码一旦接受即冻结（ADR "Reconsider when"）。
3. **`files.search` 为有界"名字子串"搜索**而非内容搜索：roadmap 仅写 `files.search`；名字搜索有明确有界语义（`maxResults`+`maxScan`，不跟随 symlink 目录，不能逃出 base）。内容搜索需要远大于本任务范围的契约（内容编码/大小上限/索引策略），留待后续 HXA 显式立项，不在此处静默扩大范围。
4. **`files.*` 短名与 namespaced 实现共用同一 descriptor/Policy**：每个工具单一 `register()` 同时注册 contract 与 implementation，`(name, version)` 唯一，不存在"两个契约"。
5. **store 侧新增 `stat`/`listDir`/`search`/`mkdir` 全部 containment-enforced**（`resolveContained` + `LinkPolicy.REJECT_SYMLINKS`），工具层不 join 真实路径；`mkdir`/`write`/`edit` 双重 region 门（工具层 + store `regionOf`）。
6. **`edit` 的 UTF-8 守卫基于 `ContentProbe` 前缀分类**：非 UTF8/EMPTY 拒绝（否则 decode+re-encode 会损坏二进制/UTF-16 字节）；空文件过编码检查后由匹配检查 fail-closed。
7. **quota 语义维持 HXA-041**：写前预检（admission），单写者串行下是硬保证；跨会话并发写可能超限——由**下一次**写的预检拒绝，报告而不回滚（已发布的成功写不可撤销）。
8. **`read` 后无工具回报 `sha256`（已知限制，本 commit 不扩大契约）**：`edit`/`write` 的 `expectedSha256` 前置守卫要求调用方给出它最后一次看到的文件哈希，但当前 `read` 输出无 `sha256` 字段，`files.stat` 只返回存在/大小/目录/文件/symlink，无内容哈希。最小修复（`stat`/`read` 加 `sha256`）会把有界探测变成 O(size) 全文件哈希，并改动输出 schema（→ `schemaHash`/`contractHash` 变化、既有审批全部失效），属契约扩大，留待 HXA-043 立项决策。当前可行工作流：`read` 看内容 → `write`（`overwrite`，不传 `expectedSha256`）拿到文件 `sha256` → `edit`。
9. **`files.stat` 的 `isSymlink` 字段恒为 false（已知限制，字段保留）**：`store.stat` 先经 `resolveContained`（`LinkPolicy.REJECT_SYMLINKS`）在 `NOFOLLOW_LINKS` 属性读取**之前**对路径中的 symlink 抛 `SymlinkInPath`，所以现行政策下 `isSymlink=true` 不可达，字段恒 false 但语义正确。移除字段会改动输出 schema（→ `contractHash` 变化）且无收益；保留字段为未来非拒绝 link 策略保留语义位置。

## 评审修复（对抗审核，本 commit 前完成；取代决策记录第 6 条的旧描述）

- **缺陷 1（CRITICAL）`edit` 的 UTF-8 门只覆盖 `probe` 的 8 KiB 前缀**：>8 KiB 文件尾部的非法 UTF-8 字节旧实现会 fail-open，把 U+FFFD 损坏内容发布出去。修复：`EditTool.decodeStrictUtf8Text` 以 JDK `REPORT` 错误模式对**整文件**严格解码（并拒绝 NUL 字节），解码失败即 fail-closed 拒绝。回归：`EditToolTest.anInvalidUtf8ByteBeyondTheProbeWindowIsRefusedAndTheBytesStayUnchanged`（9000 ASCII + 0x80 + "end"，断言 edit 被拒且 0x80 字节未被替换为 EF BF BD）、`EditToolTest.aNulByteBeyondTheProbeWindowIsRefusedAndTheBytesStayUnchanged`。
- **缺陷 2（HIGH）目录目标被 `probe` 误判为"不存在"，原始异常泄漏真实路径**：write/edit 目标是已存在目录时，`probe` 返回 `sizeBytes=-1` 放行，随后 `AtomicFileWriter` 的 `Files.move` 抛原始 `FileSystemException`（message 含真实绝对路径，违反 doc 10），crash-class throwable 抵达 batch 调用方。修复：`WriteTool` 改用 `store.stat` 预检并 upfront 拒绝目录目标（稳定消息、无真实路径）；`WriteTool`/`EditTool` 的 catch 链末尾各加 `IOException` 兜底（sanitized 消息，raw 文本永不抵达 model/batch caller）。回归：`WriteToolTest.aDirectoryTargetIsRefusedWithAStableMessageAndNoRealPathLeak`（断言消息含 "directory"、不含 scope root 真实路径、`overwrite=true` 同样拒绝、目录保持不动）。
- **缺陷 3（MEDIUM）`contractCanonicalForm` 未按 name 排序 `requiredCapabilities`**：ADR-0011 明文要求"按 name 排序"，而 Kotlin 集合迭代序随构造顺序变化，等值集合可产生不同摘要。修复：`ToolDescriptor.contractCanonicalForm` 改为 `sortedBy { it.name }`。回归：`ContractHashGateTest.theContractHashIsInsensitiveToTheCapabilitySetOrder`（同一 3 元素 Capability 集的两种插入序 → 相同 `contractHash`）。
- 缺陷 4（LOW）是契约级取舍而非代码缺陷，结论记于决策记录第 8、9 条（已知限制，本 commit 不扩大契约）。
