# HXA-023 完成记录

- 目标：OpenAI Chat Completions adapter（roadmap HXA-023）：独立实现 Chat Completions SSE；不得失败后自动切 Responses，协议由配置确定。
- 前置任务/commit：`f37cec5`（“HXA-022：OpenAI Responses adapter”）。
- 修改文件：
  - `provider:openai-chat`（新增源码，纯 JVM 库模块，模块图 `provider:openai-chat → provider:api + core:model` 不变，与 HXA-022 协议岛同构、零共享代码）：
    - `ChatSseReader.kt`：`internal class ChatSseReader`——独立实现的增量 SSE 读取器（doc 02 §6.2 要求：一行拆包、多行 data、UTF-8 边界、`[DONE]`）：
      - Chat Completions 只用 `data:` 事件（无 vendor `event:` 字段），终止符是字面 data 载荷 `[DONE]`——解析器只负责交付载荷，`[DONE]` 语义在解码器。
      - 任意字节边界拆包（行中/多字节 UTF-8 序列中，尾部最多缓冲 3 字节）、逐字节 UTF-8 解码（组装后 code point 做 overlong/越界检查，HXA-022 修正后的同一纪律）、LF/CRLF/裸 CR、`:` 注释行（vendor 以 `: OPENAI:HTTP_REFUSAL_POLICY_NOTICE` 发 ping）、`data: value` 仅剥一个前导空格、多 `data` 行以 LF 连接。
      - `finish()` 宽容派发“有 data 但缺尾随空行”的挂起事件；截断半行按 WHATWG 丢弃（解码器终止守卫转为可重试 `Error(PROTOCOL)`）；坏 UTF-8/1 MiB 超长行/8 MiB 超量 payload → 解析失败。
    - `ChatCompletionsStreamDecoder.kt`：`public class ChatCompletionsStreamDecoder`——`chat.completion.chunk` → `ModelEvent` 映射：
      - `delta.content` 非空 → `TextDelta`；role-only 首块与空 content 丢弃。
      - `delta.tool_calls[]` 按 vendor fragment `index` 键控（界 0..1024）：携带 `id`+`function.name` 的片段 → `ToolCallStarted`（id charset 经 `ToolCallId` 校验、单响应 ≤32 个调用）；后续片段 → `ToolArgumentsDelta`（空片段丢弃）；重复 start、未知 index 的 arguments 片段 → 整流失败。
      - `finish_reason`：`stop`/`length` → `Completed`（带未闭合 tool call 时失败）；`tool_calls` → 按 index 升序 `ToolCallFinished`×n + `Completed("tool_calls")`（无开放调用时失败）；`content_filter` → `Refusal("content_filter")`（合法完成；拒绝时未闭合调用不再闭合——refusal 权威，KDoc 记录）；未知 reason → 失败。
      - usage 尾块（空 `choices` + `usage` 对象，`stream_options.include_usage` 时 vendor 在 finish 块之后发送）→ `Usage(prompt_tokens, completion_tokens)`（null 透传）——**终止事件后仍接受**（vendor 文档化顺序：Completed 先于 Usage）。
      - `[DONE]` 是流终止符不是终止事件：`[DONE]` 但无任何 finish 块 = 无终止 → `Error(PROTOCOL, retryable=true)`。
      - 终止后非 usage 块、块内 `error` 对象（非 2xx 属 HXA-025 transport，块内 error 对象无文档化语义）、非法 JSON、并行 candidate index（n>1 不支持）→ `Error(PROTOCOL, retryable=false)` 且停止产出。
      - 无终止（流结束/断流，含半行 JSON 截断）→ `Error(PROTOCOL, retryable=true)`。
    - `ChatCompletionsRequestEncoder.kt`：`public class ChatCompletionsRequestEncoder(imageResolver)`——`ModelRequest` → Chat Completions 请求体（与 Responses 的形态差异逐一对应）：
      - `messages`：SYSTEM/USER/ASSISTANT → 字符串 content（USER 带图像时 content 数组：`text` 部分在前 + 每图一个 `image_url` 部分）；TOOL → `{"role":"tool","tool_call_id":...,"content":...}`；assistant 的 tool calls 不回编码（HXA-021 契约：工具关联只在 TOOL 消息上，与 HXA-022 encoder 同行为）。
      - `tools`：`{"type":"function","function":{name,description,parameters}}`（schema 经严格解析器校验为 JSON 对象后逐字嵌入）。
      - `max_tokens`（Responses 是 `max_output_tokens`）、`stream_options:{include_usage:true}`（让流携带 usage 尾块——解码器 Usage 事件的来源）、`reasoning_effort`（`name.lowercase()`，OFF 省略）、`temperature`/`seed`/`stop` 按需出现。
      - 图像经注入的 `ImageResolver`（`ImageReference` → `ImagePayload.Base64/Url`，本模块独立定义的等价边界——协议岛不共享 HXA-022 类型）：Base64 → data URL；Url → 校验非空白/无控制字符；resolver 抛 IAE 原样上抛（fail-closed）。
      - stateless（doc 10 §2.5）：每次请求携带完整会话；body 无 secret（transport 加 Authorization，HXA-025）。
    - `OpenAiChatAdapter.kt`：门面——无状态 `requestBodyEncoder` + 每流 `newDecoder()`；KDoc 明确协议岛纪律：本协议失败绝不静默切 Responses，协议由 provider 配置（`OPENAI_CHAT_COMPLETIONS`）固定。

- 关键实现决策（均为可逆实现选择，不触发 ADR）：
  - **零共享的协议岛**：roadmap 明文“独立实现”——`ChatSseReader` 是本模块自有的 SSE 实现（Chat Completions 只有 `data:` 事件，比 Responses 的 `event:` 模型更简单）；`ImagePayload`/`ImageResolver` 是本包内等价边界。不为此引入跨 adapter 依赖或把 HXA-022 代码移入共享模块（那会扩大本 HXA 的修改面到已验收模块）。
  - **`[DONE]` 语义**：流终止符而非终止事件——vendor 可能发 `[DONE]` 而无 finish 块（非良构），该情形按“无终止”处理（`retryable=true`，连接级）；正常流 `[DONE]` 在 finish 块 + usage 块之后到达，被静默消费。
  - **usage 尾块在终止后**：Chat Completions 文档化顺序是 finish 块 → usage 块 → `[DONE]`，故 `Completed` 先于 `Usage`（Responses 侧 vendor 把 usage 放在终态事件内，Usage 先于 Completed）——两 adapter 事件序不同是 vendor 形态差异，`ModelEvent` 契约不规定 Usage 与终端的相对顺序（只规定终止事件唯一）。终止后守卫因此只放行 usage 块。
  - **retryable 二分与 HXA-022 同一语义**：无终止/断流 → `PROTOCOL(retryable=true)`；块内 error 对象、非法 JSON、终止后块、未知 finish reason、工具契约违约 → `PROTOCOL(retryable=false)`。Chat Completions 无文档化流内 vendor 错误码映射（非 2xx 是 transport 的 HXA-025 映射面），故不引入 vendor code map。
  - **content_filter 拒绝不闭合开放调用**：refusal 权威终止整个响应，未完成的 tool call 不再发 `ToolCallFinished`（KDoc 记录；与 HXA-022 的 refusal 语义一致）。
  - **detekt 定点豁免（4 处，均带注释理由）**：解码器类级 `@Suppress("TooManyFunctions", "ReturnCount")`（函数数 = vendor chunk 词汇 + 访问/emit 助手）；`mapPayload`/`handleFinishReason`/`handleToolCallFragment` 三处 `@Suppress("ThrowsCount")`（每个 throw 是独立 vendor 契约违约，fail-closed 首个即停）。沿用 HXA-020/022 定点豁免先例。

  - 首次编译失败是依赖锁定门禁：`--write-locks` 前 `kotlinx-serialization-* 1.9.0` 不在 openai-chat lock state → 按先例 `./gradlew :provider:openai-chat:dependencies --write-locks --write-verification-metadata sha256` 再生（lockfile +5；verification-metadata 零漂移，组件已注册）。

  - `toolArgsChunk` fixture 括号配平错（HXA-022 同类陷阱的变体）：`arguments` 值后闭了 4 个 `}` 再闭 `tool_calls` 数组，使数组在父对象（delta）闭合后才闭合 → 整块 JSON 非法 → 解码器正确报 `Error(PROTOCOL, false)`（测试失败暴露）→ 正确形态是 `}}]}`（function、fragment、数组、delta）后 `,"finish_reason":null}]}`；Python `json.loads` + 深度计数复核通过。
  - `incompleteTailWaitsForMoreBytes` 首版用 `"data: e\u00C3".toByteArray()`：`\u00C3` 是字符 U+00C3（UTF-8 两字节 C3 83），不是裸 0xC3 字节 → 没有产生不完整尾部 → 改 `"data: e".toByteArray() + byteArrayOf(0xC3.toByte())`。
