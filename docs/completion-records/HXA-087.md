## 范围与交付

### 1. 同签名 APK 更新（"需更新"检测 + 显式重定基线）

平台事实：Runtime 只随同签名 companion APK 更新（构建期固定资产，§6.4-9），设备上不在线下载
executable。"更新"的用户可见面分三块，全部用户点击、零静默接受：

- **检测**：已验证锚点（`VerifiedRuntimeStore`，主 App 包内）pin 了上次验证时的规范 lock 指纹。
  companion APK 更新后内嵌 lock 指纹变化 → 零 Job 验证的握手比对稳定失败于
  `UnavailableCause.LOCK_MISMATCH`（= 085 执行路径的 `NEEDS_UPDATE` 审计码）。主 App
  Settings「验证 Runtime」点击后经 `ProotToolModule.verifyNowNote()` 展示
  "需更新：Runtime 基线与已验证锚点不匹配（Runtime APK 已更新？）"。
- **更新动作**：companion 修复页（`ProotRepairActivity`）新增更新态识别——
  `RuntimeInstallQueries.activeLockSha256()` 读活动安装目录的 `manifest.json`（内嵌 lock
  指纹，082 激活门已验证其完整性）与本 APK 内嵌 lock 比对，`updateStateFor()`（纯 JVM，
  fail-closed：无活动/不可读 = INSTALL，绝不"最新"）决定主按钮文案：
  未安装→「安装/修复」/ 指纹不同→「更新 Runtime（APK 内嵌版本较新）」/ 一致→「安装/修复」。
  安装路径 = 082 原子安装（`.partial`→promote→原子激活；**更新失败旧 runtime 保持可用**，
  §10 必测项，082 已证 + 本轮回归）。
- **重定基线**：`ProotRuntimeSupervisor.clearAnchorForRebaseline()`（+ 模块
  `rebaseline()`）删除锚点。UI 仅在显示"需更新"后展示「重定基线（我已知晓基线变更）」——
  **两次显式用户动作**（看到不匹配 + 点击重定基线），之后下一次「验证 Runtime」对新 lock
  重建锚点。锚点的"移动基线绝不静默接受"属性保持（083）。

### 2. rollback（用户入口）

`RootFsInstaller.activateRollback`（082，纯指针交换、文件不动、状态锁全程持有）此前无用户面。
本轮：修复页在存在回滚版本时显示「回滚到上一版本」按钮（同一签名权限、同一用户门控面），

不一致 → 下一次验证按"需更新"显式处置（同上，不静默）。

### 3. 完整删除（不误删 Workspace）

- companion 侧：`ProotRuntimeRemoval.remove(runtimeRoot)` **只**删除 `filesDir/runtime`
  状态树（版本目录 + state 指针；Job journal/evidence 都在其下）。路径名 `runtime`
  删除前再校验（fail-closed，错根拒绝不删）。主 App 的 Workspace 在**另一个包**，结构上
  不可达；companion 自身 filesDir 的兄弟文件在删除中存活（设备断言）。
- 主 App 侧：Settings「删除 Runtime」→ 确认对话框 → `ProotToolModule.removeRuntime()`：
  先清本包锚点（自己的文件，验证声明随删除失效），再以 `EXTRA_REMOVE_RUNTIME` extra 打开
  companion 修复页——consent 跨 uid 传递，companion 侧仍有**面内二次确认按钮**
  （`ProotRuntimeRemoval` 才真正执行）。gate 随即降级 NOT_VERIFIED。
- 语义：删除后「bash」Tool 需重新安装/验证（gate = 安装 ∧ 启用 ∧ 锚点）。

## 决策记录：

1. **"需更新"只在用户点击验证时揭示**：gate（`availabilityGate`）保持零绑定四态
   （READY/未安装/被禁用或强制停止/未验证）；lock 漂移检测需要一次握手，故归入
   用户点击的零 Job 验证路径（`verifyNowNote`），被动 Registry 刷新绝不重绑——085 的
   门控不变量原样保持。
2. **重定基线 = 两次显式动作**（看到"需更新" + 点「重定基线」），不做"更新后自动重建
   锚点"：锚点（083）的安全属性是"移动基线必须被用户意识到"，单次自动接受会把它变成
   橡皮图章。签名一致由平台保证（同签名权限/同签名集），所以用户显式确认即充分。
3. **删除 = 双端各自清自己的状态 + 面内二次确认**：主 App 清锚点（自己的文件）、
   companion 删 `filesDir/runtime`（自己的文件）；extra 只是 consent 的跨 uid 载体，
   companion 按钮点击才是删除动作。任何一端都不访问对方 uid 的文件。
4. **法律页放 companion 而非主 App**：lock/许可证文本的单一真相在 companion 资产
   （081 构建管线产出）；主 App 复制 = 双份真相 + consumer/developer 资产分叉。
   页面经签名权限显式 intent 打开（与修复页同形），内容纯本地资产、离线。
5. **更新检测读活动安装 manifest 而非激活指针**：激活指针只有 installId；
   `manifest.json` 内嵌完整 lock + 规范指纹（082 解析时重算验证）。损坏 manifest 抛错
   → UI 映射为稳定拒绝，绝不读成"一致"（fail-closed）。
6. **`activeLockSha256` 独立成 `RuntimeInstallQueries`（读侧）与 `RootFsInstaller`
   （写侧）分离**：更新态判定不坐在安装/回滚突变旁边（职责 + detekt 函数数双因）。
