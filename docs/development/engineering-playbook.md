# 个人工程手册：开发倾向、决策方法与实践经验

Engineering Playbook · 整理日期：2026-10-03

本文根据项目所有者在历史对话中反复表达的选择，以及 Helix 已记录的工程案例整理，供本人和协作开发者跨项目复用。它解释“为什么倾向这样开发”，不是个人能力评级，也不是把所有助手建议追认为所有者的要求。

> **定位声明：本文是一份与 Helix 具体架构解耦的个人工程方法论与决策手册。它主要回答“为什么这样开发、面对冲突信息如何判断、什么时候继续或停止”，Helix 只作为经验来源和案例库。本文不是 Helix 架构说明、项目 SOP、Agent 硬规则、当前排期、验收清单或授权文件；任何项目落地时都必须重新确认自己的产品阶段、平台约束、数据承诺和操作授权。**

**核心取向：让用户意图得到充分实现；用尽量少、但真实有效的机制守住授权、执行事实和系统完整性；通过可复核的证据交付。**

## 0. 如何使用，以及本文不负责什么

本文区分三种内容：**明确偏好**来自所有者直接表达；**项目经验**来自仓库案例中可追溯的机制与结果；**归纳建议**是将前两者推广后的实践方法，不自动成为新的硬性规则。章节会说明主要性质，案例不代表所有平台都已验证。

在 Helix 中，当前请求及适用的 [AGENTS.md](../../AGENTS.md)、[当前状态](status.md)、当前任务和有效 ADR 决定具体工作。本文不扩大操作授权，不修改渠道边界，不批准设备测试、真实账号使用或 Git 操作，也不维护第二份排期、验收清单或运行时实现。

## 1. 决策速查

以下是明确偏好与经验的简要归纳，不应脱离右列边界变成机械口号。

| 倾向 | 落地判断 | 必须保留的边界 |
| --- | --- | --- |
| 能提示就不阻塞 | 用户已表达清楚意图，风险告知足够时继续 | 无授权、非法参数、缺少实际能力或资源不可用不能伪装成可执行 |
| 能复用授权就不重复询问 | 在同一授权主体、用途与范围内复用用户决定 | 不把主体、接收方或范围变化当作原授权自然延续 |
| 策略、授权、机制与事实各有责任主体 | 开放式路线交给合适的决策者，基础机制提供真实执行与反馈 | 不让策略层自行授予权限或改写执行事实 |
| 持久化意图，重建运行态 | 断连、进程死亡不代表用户撤销配置 | 不恢复旧 token，不盲目重放外部动作 |
| 默认不设无依据的全局排他 | 只协调具体不可重入资源和真实物理容量 | 事务、原子发布、执行身份与内部状态完整性仍需保护 |
| 复用能力，不重复建系统 | 能用已有工具、执行域或协议就优先接入 | 必须确认隔离、取消、输出和授权语义仍正确 |
| 保留语义，不保留错误结构 | 开发阶段允许删掉旧内部兼容层 | 不因此破坏用户数据、外部有效协议和已承诺的升级路径 |
| 评审先验证再排期 | 把评审结论当作可证伪假设，先核对实际入口、触发条件和保护 | 评审语气、问题数量和严重级别标签不代替证据 |
| 限制有进入理由，也有退出条件 | 说明它保护什么，以及条件变化后何时应缩小或撤除 | 权限、系统完整性和真实不可重入约束不能因追求畅通而绕过 |
| 先证据，再结论 | 给出触发条件、最小反例、执行结果和适用范围 | 构建、单测、模拟器、真机和发布结论不互相冒充 |
| 验证优先消除关键不确定性 | 先验证最可能推翻方案的条件，再扩大实现和测试 | 已约定的强制门禁不能在失败后临时跳过 |
| 重构有退出条件 | 当前目标成立、旧路径退出、必要验证通过后交付 | 不因新想法或目录不够对称无限延长阶段 |
| 文档解释决定，而不是复制真相 | 每类信息维护一个当前入口 | 历史证据保留出处与时间，不再指导今天的任务顺序 |

## 2. 职责划分：策略、授权、机制与事实分开

**性质：Agent 分工来自明确偏好；通用职责划分为项目经验与归纳建议。**

先区分四个问题：谁决定完成目标的路线，谁有权批准动作，什么机制保证动作正确执行，以及依据什么事实判断进度。这些职责可以由不同组件或主体承担；不能因为某层能提出方案，就让它同时授予权限或定义执行结果。职责分离不要求增加服务或进程，而是让决定、约束与事实的来源清楚。

在 Agent 产品中，这表现为所有者倾向的浅 Harness：模型选择业务路线，用户决定授权，框架提供执行基础与真实反馈。它不意味着所有软件都应该引入模型，也不意味着确定性业务规则应被移出程序。下面用 Agent 场景说明这一通用判断。

### 2.1 用“换成更强模型后是否仍需要”筛选框架机制

即使模型足够强，执行身份、权限复核、输出来源、原子写入、取消和真实容量仍不可缺少；这些属于基础机制。相反，“遇到某按钮必须先执行固定三步”“某类任务只能沿唯一工作流完成”，往往是业务策略，应先考虑工具说明、上下文、Skill 或模型决策。

这个问题只是筛选器，不是反对确定性流程。若用户明确要求固定步骤，或协议本身要求可审计、可复现、严格排序和状态收敛，固定流程可能正是在实现用户意图。真正需要警惕的是：框架是否在没有确定性必要的地方替模型决定开放式业务路线。连接、任务所有权和资源生命周期需要确定状态；确定性协议实现与替模型规划业务步骤不是同一件事。

### 2.2 反馈要足够真实，而非替模型宣判目标完成

“平台接受点击”“命令退出码为零”“文件已写入并完成哈希登记”“用户目标已实现”是不同层次。工具准确报告前面的事实，模型结合后续观察判断任务进度，用户验收最终结果。确定性的输出检查仍有价值，但不能凭薄弱代理指标断言业务成功。

例如，找不到节点应说明是目标不存在、观察不完整、窗口变化还是平台不可用；动作已发出但回执丢失应报告不确定。比起新增一个隐藏恢复流程，先让模型看到这些差异，通常更符合这一开发取向。Helix 的具体职责与反馈契约由 [Harness 方案](../architecture/harness-refactor-plan.md)维护。

## 3. 最少限制：区分风险、授权和事实前置条件

**性质：明确偏好。**

所有者明确要求：不该锁的不要锁，不要轻易限制执行；仅可能影响运行结果而不影响系统稳定性的冲突，可以由用户和模型最终验收。HTTP 与 Mobile Use 的讨论又进一步强调，有风险可以提示，不要在已经授权的范围内不断增加阻碍。

实现前应把限制归类，而不是看到“风险”二字就禁用按钮。

| 限制来源 | 合理处理 |
| --- | --- |
| 用户已知的传输或结果风险 | 明确提示实际影响，保留用户选择，不额外制造同义授权 |
| 当前权限不足或用户明确禁止 | 按现有授权机制处理；不能用另一工具绕过 |
| 参数不成立、模型未选择、目标不存在 | 说明缺什么并提供修复入口，不吞输入、不假装成功 |
| 平台暂时不可用 | 返回暂不可执行与恢复条件，尽量保留配置和草稿 |
| 真实资源不可重入或容量耗尽 | 仅限制相关资源，报告占用事实，不锁住无关能力 |
| 已发出动作的结果不确定 | 停止自动重放该动作，保留观察、核查和其他获准工作入口 |

### 3.1 去掉表层限制不等于完成行为修改

HTTP 案例说明：只移除 UI 确认框不够，发现模型、连接测试、普通发送、Plan、队列和底层网络配置都可能保留旧门槛。优化应沿真实调用链检查，最后验证实际制品；同时不关闭 HTTPS 校验，不把 HTTPS 失败静默降级为 HTTP。见 [HXA-242 记录](../evidence/development/hxa242-http-ui-host-2026-10-02.md)。

### 3.2 不把“畅通”误读为删除所有保护

缺少授权与用户愿意接受风险不是一回事。用户输入不完整、资源已经耗尽、内容或目标身份发生变化时，继续执行可能根本无法忠实实现原意。应提供具体诊断，而不是为了按钮能点而隐式改参数、丢附件、伪造完成或绕过系统权限。

不可逆、高影响操作是否需要额外确认，应由明确的产品契约、用户设置和适用约束决定；本文不新建关键词黑名单，也不取消已经接受的特定规则。

### 3.3 限制也要有退出条件

一条限制应先判断属于哪一类：**长期必须成立的完整性约束、用户可选择的产品策略、当前实现能力的限制，还是临时规避措施。** 后三类不应因为已经写进代码、测试或文档，就自然升级成永久事实。

新增锁、确认、白名单、固定超时或兼容层时，除了说明“它在保护什么”，还应说明“什么条件变化后值得重新评审”。例如单实例引擎变成真正可并行的执行域、临时故障被根治、产品默认改变或用户已有更高层授权时，都应重新判断旧限制是否仍有价值。撤除过时限制时应同步生产行为和测试契约；修改旧测试预期不等于削弱测试，前提是新的接受契约和必要保护已经说清楚。

这种退出条件不要求新增一套登记流程。能在 ADR、任务或相关代码注释中简洁说明原因和重新评审条件即可；方法论的目标是防止临时约束固化，而不是制造新的审批表。

### 3.4 默认值与上限要有依据，不能藏在实现细节里

**性质：项目经验与归纳建议。**

调用预算、超时、列表容量和默认选择会改变任务能否完成，因而也是产品行为。应区分平台硬限制、资源保护、产品默认与经验估算，说明它们作用于一次调用、一个任务还是整个系统，以及触及边界时用户会遇到什么。允许调整的范围和无法突破的条件也应分清；不是每个内部参数都需要成为设置项。

调整之前先判断问题来自容量不足、分配不当、错误计数还是误用默认值。提高上限不能修复错误计数，隐藏必要能力也不能证明系统更简洁。Helix 历史上对 Goal 预算、有限工具面和默认选模的反复调整，说明这些值不能仅凭“通常够用”定下来；可复用的是依据和作用范围，不是当时的具体数字。限制何时重新评审仍按第 3.3 节处理，不另建参数审批流程。

## 4. 授权设计：高层意图、正确主体、尽量少次确认

**性质：明确偏好；持久授权为特定用途设计，不是所有权限的统一默认。**

在 Mobile Use 中，所有者连续明确了三个要求：按 Conversation 绑定；尽可能减少授权次数；授权后不因为锁屏、重启等原因自行关闭。这个演化说明，授权应围绕用户能理解的主体与用途设计，而不是围绕一次 API 调用或一次图片处理弹窗设计。

### 4.1 一次明确授权，范围内复用

用户应能看懂授权给哪个主体、允许做什么、数据将由哪些接收方处理，以及如何关闭。在已说明用途的范围内，后续动作不应重新证明同一意图。内部仍可为每次调用生成绑定主体、内容、目标的校验凭据；**重新校验不是重新询问用户**。

Helix 的 Mobile Use 记录采用 Conversation 持久配置，覆盖后续原生截图及本会话中用户选择的模型。普通附件、文件读图或浏览器图片不自动获得同一授权。模型切换免重复确认是该用途已告知、用户主动选择下的决定，不能推广成任何程序都能把私密数据静默改发新接收方。见 [HXA-244 记录](../evidence/development/hxa244-conversation-mobile-use-host-2026-10-03.md)。

跨项目时，授权主体可以是会话、项目、账号、设备、组织空间或其他用户能理解并控制的对象；不能把 Helix 的 Conversation 级选择固化成普遍规则。可复用的原则是：主体、用途、接收方、范围和撤销边界必须与用户当时理解的一致。

### 4.2 不创建两套互相竞争的权限

系统权限回答“平台允许应用做什么”，会话配置回答“用户允许这个会话做什么”，工具模式回答“这类操作自动允许、询问还是禁止”。应复用这几层已有职责，而不是另造 Mobile Use 专属逐动作审批器。

用户主动选择“需要批准”时，工具审批不是应删除的冗余；用户选择“完全访问”且范围已授权时，再逐截图要求同义确认才是应收敛的重复。手动操作入口和模型工具入口也不能互相冒领权限。具体规则见 [会话授权 ADR](../adr/permissions/001-session-authorization.md)。

### 4.3 关闭授权与暂时不能执行分开

用户关闭授权是持久决定；锁屏、连接断开或服务不可用是执行条件变化。后者应暂停有关运行态而保留用户决定。显式修改范围使旧执行凭据失效，但并不意味着必须弹出多张重复确认卡。

持久授权也不表示卸载、清除应用数据、会话删除或存储损坏后仍能凭空恢复；保存失败必须报告事实。某些有期限的账号、委托和平台令牌有独立有效期，不能从 Mobile Use 的偏好推导“所有权限永久有效”。

## 5. 状态与恢复：持久事实是依据，运行态可以重建

**性质：明确偏好与项目经验。**

应分别建模用户决定、执行记录和临时资源。按领域明确唯一权威来源，不等于所有状态必须塞入一张表或同一个全局对象。

| 内容 | 应如何看待 |
| --- | --- |
| 会话配置、用户授权、已接受输入 | 持久业务事实，临时断连不应使其消失 |
| 原始调用、执行开始与终结记录、产物归属 | 恢复与审计依据，不能被 UI 猜测覆盖 |
| Coroutine、Job 句柄、连接、节点和 frame token | 临时运行态，按实际生命周期创建与废止 |
| UI 加载状态、剩余时间、当前投影 | 展示层派生信息，不取代底层事实 |

### 5.1 恢复事实，不自动恢复旧执行

进程死亡后，应先读到原任务做了什么、哪些结果存在、哪些副作用未确认；重新建立连接和新观察不等于重放先前动作。是否继续、换路线或开启新 Turn，应由当前任务契约与模型决定，不为了表现“无缝”而深度重建不可验证的执行栈。

同样，授权仍在不等于任务必须自动恢复。用户取消一项任务可以停止该任务而不必清除整个会话的能力配置；明确撤销能力则应阻止后续相关执行。具体停止入口的含义应在 UI 和契约中一致。

### 5.2 本地失败不能证明外部回滚

数据库事务回滚、协程取消、网络超时或回执丢失，都不能单独证明点击、消息发送或文件修改从未发生。应区分执行前拒绝、确定完成、确定失败以及结果未知，不把未知标成可安全自动重试。

Mobile Use 从临时许可到持久配置的案例尤其说明：授权身份与临时运行身份分开后，可以保留用户意图，同时废止旧节点和旧 frame。相关经验见 [HXA-243](../evidence/development/hxa243-mobile-use-host-2026-10-03.md)和 [HXA-244](../evidence/development/hxa244-conversation-mobile-use-host-2026-10-03.md)，后者承接持久授权语义。

### 5.3 按重建能力与有效引用决定数据生命周期

**性质：项目经验与归纳建议。**

“缓存”“临时文件”“辅助记录”只是名称，不能决定数据是否可以删除。清理前应判断：能否从其他权威数据可靠重建，是否仍被有效对象引用，以及删除后会失去什么能力。不可重建且仍被引用的数据就是当前功能的依赖，即使它不属于用户直接编辑的正文。

Helix 曾把协议签名记录按最近 128 条保留，导致新操作淘汰旧会话续聊所需的记录。可复用的教训不是“永远保留所有记录”，而是回收必须尊重依赖；取消误删只是正确性修复，容量观测、引用感知回收和不可恢复时的处理仍是后续设计问题。数据可再生成也不等于应无代价删除，重建所需时间、网络、账号条件和配额同样需要考虑。见 [v0.0.4 回放修复记录](../evidence/development/v0.0.4-release-2026-10-01.md)。

## 6. 工具、能力与并发：按真实边界组织，而非数量组织

**性质：明确偏好与项目经验。**

### 6.1 一项新能力不一定需要一个新子系统

FFmpeg 的最终选择是复用高级版已有 Bash／Linux Job，而不是另造一套媒体 Service、执行身份和产物收取。关键不是少写几个类，而是复用已经成立的权限、取消、日志、原始 Job 和输出路径；命令能力仍受实际编入组件约束。见 [HXA-240 接入记录](../evidence/development/hxa240-ffmpeg-proot-2026-10-02.md)。

同理，Skill 内容、MCP 协议、Plugin 交付组织、Provider 推理接口和 Runtime 执行域不是同一概念。可以统一发现和治理，但不应为了“统一”把不同职责合成一个巨型抽象。

### 6.2 模型能使用能力，比接口存在更重要

能力接入应追到：是否发现得到、说明是否准确、参数能否表达需要的动作、授权后是否执行、结果是否进入下一轮上下文、产物是否属于原会话。存在一个接口、生成了一张截图或 CLI 编译成功，都不是链路已经可用的充分证据。

工具数量不是优化目标。大量接口可通过按需发现和清楚的能力分组组织，不强迫全部常驻上下文；也不能靠隐藏真正需要的能力来人为减少数量。是否增加专用工具，应由真实任务和现有接口表达缺口决定，见 [实施指南](implementation-guide.md)与 [开发策略](feature-refactor-strategy.md)。

### 6.3 默认不设无依据的全局排他，只锁真实资源

加锁前写清楚保护哪个资源、为何不可重入、持有和释放的真实条件，以及是否影响无关任务。文件结果可能相互覆盖和引擎内部状态会损坏，是两类不同问题；前者可通过提示、范围与任务组织处理，不自动成为全局执行锁的理由。

“默认并发”也不等于无界并发。线程、进程、IPC、设备手势、单实例引擎和日志通道仍受真实物理容量约束；队列和背压可以存在，但应只影响竞争同一资源的工作。取消等待不等于执行器已经退出，容量释放应跟随真实执行生命周期，不能用超时释放制造并发超额；同样，一个未知动作也不应无条件冻结整个会话或整台设备。

同批工具可并发时，应把依赖关系说明给模型。写完再读的动作需要等待前置结果，而不是为解决这一个依赖恢复所有工具串行。HXA-241 的依赖提示和运行证据是具体案例，不是“模型从此不会犯错”的证明。

## 7. UI 与交互：让用户表达意图，不让用户猜内部状态

**性质：明确偏好，部分形式为归纳建议。**

用户高频操作应靠近发生位置：以 Conversation 为主入口，模型和权限状态在会话中可见；编辑、重发、复制和分支有清晰语义；复杂内部配置用用户熟悉的选择方式表达。应用名称选择优于手填包名，模型勾选优于把服务端返回的所有模型都塞进候选列表。

### 7.1 可操作性与解释来自同一状态判断

不可发送时，应说明是未选模型、附件未恢复、配置保存中还是提交进行中，并保留草稿。不能把按钮禁用，再只在无法触发的点击回调里放一条解释。

风险警告、暂不可执行、权限拒绝和框架失败应使用不同反馈。后台保存草稿失败不该无故锁住文字编辑；附件不完整也不能静默丢弃后伪装为原消息发送成功。见 [HXA-242](../evidence/development/hxa242-http-ui-host-2026-10-02.md)。

### 7.2 能力存在之外，还要能发现、能准备、能继续

交付需要连接发现入口、必要准备、实际执行、结果使用和失败后的继续路径。终端能执行命令，但用户找不到入口或不知道环境尚未安装，仍不能完成使用；连接已配置，但会话无法选到模型，也不能算功能闭合。先确认用户在哪一步受阻，再决定补入口、解释还是能力本身。终端案例见 [入口与准备指引](../evidence/development/terminal-menu-entry-2026-10-01.md)。

新增 Provider 有滚条而管理列表没有，说明只修了入口，没有覆盖完整使用路径。长表单、模型管理、选择弹窗、展开内容和短窗口都应检查溢出可发现性；共用滚动反馈，避免每页手写不同逻辑。

键盘让聊天区域变小不天然是 Bug，应检查控制是否被遮挡、焦点是否正确、附件是否挤占过多空间和操作是否仍可达。布局建议需要对应设备、方向、字号和窗口条件，不能从一个固定高度常量直接推出“真机体验很差”。

### 7.3 用效果一致性建立心智模型

API、自托管、端侧和账号订阅可有不同认证与传输适配，但模型发现、启用候选、选择、错误反馈应尽量一致。使用 endpoint 和 key 的方案不应仅因营销名称含“订阅”就被放进账号登录分类。构建渠道、运行档位和会话权限也应分开表达，避免让用户以为切换权限就能获得 APK 未包含的能力。

### 7.4 从连续反馈提炼目标，不机械叠加局部要求

**性质：项目经验与归纳建议。**

多轮反馈往往逐步揭示同一个用户目标，也可能是在改变产品取舍。先判断属于哪一种，再重审整体交互；不能把每轮要求永久叠加成互相竞争的入口，也不能只执行最后一句而遗忘仍有效的目标。无法判断是否真的改变取舍时，应澄清影响，而不是擅自替用户选择。

例如工具卡片先要求减少默认信息，随后要求优先显示 intent，共同目标是先看懂动作、按需查技术细节，同时保留真实状态。稳定下来的是信息层次与使用目标，不是某一版布局。接受新取舍后同步说明和测试，避免下一轮又恢复已放弃的形式。见 [工具展示调整记录](../evidence/development/tool-details-collapse-2026-10-01.md)。

## 8. 重构：开发阶段优先正确结构，但有停止条件

**性质：发布前兼容取舍为明确偏好；停止条件的表达为项目经验与归纳建议。**

### 8.1 Clean-slate 是内部设计选择，不是数据处置许可

所有者多次要求新设计不考虑旧版本兼容、以当前最优为准。合理落点是：不为了旧枚举保留别名，不维持两套权限真相，不让已经错误的依赖结构决定下一版设计。

但“开发阶段”和“从未对外提供过安装包”不同。整理时 [README](../../README.md)已说明开发预览包及升级边界，因此不能把早期的“不考虑兼容”扩大成对真实用户数据无条件删除。外部协议、第三方组件许可、用户文件和已作出的升级承诺应分别评估；进入稳定发行后，需要重新决定迁移、回滚和弃用策略。

### 8.2 区分三种变更，避免无法归因

结构重构尽量保持行为等价；能力扩展增加新的输入、执行或观察形式；产品变更改变用户期望的行为。三者可以在一个获准目标下协同，但验证应分别证明，不能同时更换模型、Prompt、状态结构和预算后，把全部收益都归功于“架构优化”。

### 8.3 先写结束线，再开始扩展抽象

可复用的停止判断是：当前问题已解决，关键事实只有一个 owner，生产入口已经接线，旧路径有删除或明确退出点，相关回归和适用门禁通过，未覆盖边界已记录。达到当前范围的条件就交付，不把所有未来能力变成前置条件。

接口分离不自动要求新进程、远程服务或第二套数据库。没有真实消费者的“更通用”接口，应先作为候选，而不是延长本轮任务。Helix 的具体退出条件只在 [开发策略](feature-refactor-strategy.md)维护，本文不再复制阶段排期。

### 8.4 追踪共同假设的传播，而不只追踪调用关系

很多跨层缺陷不是“漏改了一个调用者”，而是多个模块仍共享旧假设。数量关系从单个变多个、同步变异步、临时状态变持久状态、默认回退变显式选择、完成语义从“函数返回”变成“底层真实退出”时，应主动检查哪些地方消费这个假设。

至少关注：**生产入口、持久表示、恢复/重开、取消与控制、展示投影、测试 fixture 和证据工具。** 类型能编译、每个模块单测通过，并不足以证明组合路径理解了同一个新契约。优先补一条跨边界反例，例如“未选模型时 UI、服务准入、附件旅程和测试都不能再偷偷回退默认模型”，而不是只搬动类或修编译错误。

CodeGraph 和调用搜索用于找结构关系；共同假设仍需要从领域语义、状态生命周期和测试前置中识别。工具能发现引用，不代表它能自动发现所有隐含前提。

## 9. 调研、评审与选型：先理解机制，再验证和裁决

**性质：参考竞品为明确偏好；证据组织、评审再验证和实验顺序为经验归纳。**

### 9.1 调研先理解机制，不按品牌照搬

所有者经常要求参考桌面与移动端主流 Agent，而不是凭空构思。值得保留的方法不是某个品牌的当前排名，而是先找共同机制，再核对它为什么适用于相应平台和用户路径。

一次调研应能回答：对方实际暴露什么入口；实现依赖什么权限、进程或服务；失败与恢复怎么表达；与本项目的相同点和约束差异是什么；哪一部分应复用，哪一部分不适用。说明资料对应版本、日期和验证范围，源码事实与使用体验、推测分开。

参考不是复制源码，也不是“竞品有，所以我们必须有”。许可证、平台、包体、维护成本和接入复杂度是选型条件。FFmpeg 讨论先要求裁剪编译并看实际大小，再决定是否接入，是“测量代替猜测”的例子；历史阈值属于那次选择，不变成所有依赖的通用上限。

### 9.2 评审结论先验证，再进入任务

评审、代码审查和模型建议首先是**待验证的假设**。接受一项修改前，分别判断三件事：结论是否事实成立；如果成立，实际影响和严重性是什么；即使重要，是否值得在当前范围立即处理。三者不能用一个“高危”“架构问题”或问题数量代替。

核对时回到实际生产入口、触发条件、违反的契约、现有保护和可复现反例。文件很大、类很多、状态机复杂或报告语气强烈都可以是调查线索，但不是自动重构依据。证据不足时保留“不确定”或“候选”，不要为了回应评审而制造新系统；新证据证明当前结束线确实不成立时，再扩大范围并写清新的退出条件。

### 9.3 优先验证最可能推翻方案的未知条件

验证顺序应服务于决策。先找最可能让当前方案失效、且能用较低成本得到清楚答案的条件，例如依赖包体、真实执行域能力、协议行为、资源上限或关键平台限制；先排除这些不可行性，再扩大实现和测试。

这不是为了少跑强制门禁。已经约定的验收标准不能在失败后临时跳过；优化的是**验证顺序和重复工作**，不是成功标准。执行很多命令、生成很多报告本身不构成更强证据，关键是每一步是否减少了会改变下一决策的不确定性。

已接受设计落实到当前 ADR 和任务；研究材料、评审报告和实验结果本身都不批准扩范围。较新的资料也不天然推翻更合适的旧结论，冲突需要基于约束重新判断。

## 10. 验证：测试只证明它实际测试过的事情

**性质：项目经验；不能把下面所有细则都写成所有者曾逐条说过的原话。**

HXA-241 复核不仅修产品，还发现测试契约漂移、扫描器误分类、虚假通过和证据漏记。重要经验是：红灯不总是同一种产品 Bug，绿灯也不总是有效证明；验证工具本身需要验证。见 [模拟器复核记录](../evidence/development/hxa241-emulator-sweep-reconciliation-2026-10-02.md)。

### 10.1 找到失效边界，再判断失败机制

用户报告的功能名称描述遭遇，不直接指出根因。先定位同一次操作最后一个已确认成功的边界与第一个失败的边界；如果中间缺少观察，只能缩小到一个区间，不能把未记录当成未发生。重试可能已产生新身份和不同前置条件，不能把几次操作的片段拼成一次完整成功。

Helix 的 files.list 曾执行成功，但下一次模型请求在历史编码阶段失败。按“文件工具失败”修改权限会修错层，问题实际是参数规范化与协议回填的契约不一致。见 [文件工具与视觉诊断](../evidence/development/files-vision-readme-2026-10-01.md)。因此，诊断应能关联输入、执行、持久化与后续消费；优先记录身份、阶段、结果类别和必要时序，而不是依赖完整私密内容或堆积日志才能排障。

产品缺陷应修生产行为；已接受契约变化应修测试前置和断言，同时保留原本保护的语义；驱动或统计缺陷应修验证工具，不能靠改分类隐藏失败。优先保留一个能在旧实现上失败、在修复后通过的反例。

例如，日志中的普通关键词不能豁免真实失败；单独出现 OK 文本不能证明正确测试类已执行；缺失 JSON 不能静默从分母消失。通过判断要有执行身份、开始与结束、终态、退出码和必要输出证据。

### 10.2 双向正确性：既挡住错误，也放通正确路径

保护机制的验证不能只证明“危险操作没有发生”。一个什么都拒绝的系统也可能通过大量负向断言，却无法完成正常任务。新增权限、锁、过滤、恢复或输入校验时，应同时证明：不该发生的行为被阻止；**应该允许的正常路径和无关能力仍然可用**。

例如工具未发现时应拒绝旧调用，但精确发现后必须真的可用；未选择模型时不能发送，但选择后草稿应能正常继续；一个任务的资源占用不能误伤无关任务。用户和模型负责业务结果验收，不等于框架的可用性、授权正确性和输入完整性也交给用户兜底。

### 10.3 分层陈述，不扩大结论

| 已有证据 | 可以说明 | 不能直接说明 |
| --- | --- | --- |
| 编译、lint 和静态检查 | 对应构建与规则检查通过 | 功能闭环或设备交互通过 |
| 主机单测、合成日志与 fake | 对应逻辑和受控反例成立 | 真实服务、平台回调和 OEM 均成立 |
| APK 内容核验 | 实际包内组件、权限、资源和载荷符合检查 | 安装后一定可运行或可以上架 |
| 指定模拟器的专项运行 | 指定 API、ABI、渠道和场景有运行结果 | 全仓、真机或其他系统版本通过 |
| 真机或真实模型的任务运行 | 被测配置下任务轨迹与结果成立 | 所有模型、应用和长链任务的成功率 |

`skipped`、`not requested`、`pending`、失败和未知分别报告；重复执行与不同场景分别计数。增量构建可以有效，但应说明缓存和未重跑任务，不能写成全量强制重测。

### 10.4 最终交付与证据身份一致

测试之后继续改源码或重新打制品，旧汇总可能过时；同一个 Git HEAD 也不代表脏工作区未变。应核对最终源码、依赖、制品与记录是否对应。HXA-244 收尾发现旧汇总指向较早构建并修正，是证据收尾的具体案例，而不是重新执行设备测试。

历史失败与中间记录保留，最终汇总指出正确版本，不覆盖旧日志制造全绿。完整测试数和哈希放任务证据，不复制到本手册形成另一份会过时的成绩表。与此同时，不应机械地把“任何文件变化”都解释成所有旧证据失效；应判断变化是否影响被证明的行为、依赖、构建或执行环境，不确定时再补验。

### 10.5 验证状态跨越边界，而不只增加运行时间

**性质：项目经验与归纳建议。**

单次正常路径通过，不代表累积使用后的行为成立。根据本次改变的状态生命周期，选择有辨别力的场景：首次与再次、新对象与旧对象、阈值之前与之后、重开之前与之后，以及配置改变后的继续使用。回放记录第 129 条、切换模型后的旧会话、压缩后的续答，考验的都是状态边界，而不是单纯运行更久。

长稳测试应说明想跨越哪种边界：资源累积、身份失效、清理触发或恢复条件。确定性阈值可用小而明确的反例验证；随时间和环境变化的问题仍需要真实持续运行。不要把这些维度扩展成每次必跑的笛卡尔积，按改变的假设、失败代价与已有证据选择覆盖。

### 10.6 项目特定的验证授权，不上升为跨项目定律

Helix 当前明确不使用 GitHub Actions 执行设备验证；本地模拟器、真机和真实账号使用按当前任务授权。历史上测试过、设备已连接或先前代理有权限，都不自动成为本轮授权。执行规则以 [AGENTS.md](../../AGENTS.md)和 [公共验收](verification-matrix.md)为准。

跨项目可复用的不是“设备 CI 永远不能用”，而是：**昂贵、外部或可能影响真实环境的验证，需要由项目明确它的授权主体、执行位置、证据等级和成本边界。** 文档任务也不应仅为展示工作量默认重建全部制品；反过来，当前任务要求的真实设备或服务验收也不能用主机构建替代。

## 11. 多 Agent、Git 与上下文成本

**性质：模型分工和复用已有工具为明确偏好；协作方式为经验归纳。**

### 11.1 按不确定性、错误代价和可验证性分配推理成本，不固定品牌

所有者曾明确希望由能力较强、成本较高的模型思考和复核，使用本地或较低成本模型执行定义清楚的开发切片。更适合抽象为：高不确定性、跨领域契约、错误代价高且难靠确定性检查发现的问题，优先投入更强推理；边界清楚、输入输出明确、可由编译/测试快速判错的切片，可以交给成本更低的执行者。

不要只按文件数、代码行数或表面“难不难”分工。一行权限或结算修改可能比几十个文件的机械迁移风险更高。这也不是认为本地模型只能聊天或只能执行命令；所有者另明确，本地 Provider 也应能驱动完整 Agent loop，模型能否胜任具体任务要看实测，而不是因为运行位置先裁掉能力。

不要固化某产品永远最强、固定修复次数或固定调用上限。衡量的是从需求到可验收结果的**总成本**：上下文读取、澄清、实现、漏改、门禁失败、复核、二次修改和集成，而不仅是单次模型调用价格。没有同条件数据不编造节省比例。

### 11.2 开发协作流程不等于产品业务流程

开发任务可以约定规划、实现、验证、复核等交付步骤；这与不在产品 Harness 中写死每种用户任务路线并不矛盾。前者组织工程交付，后者限制运行中的业务智能。也不应仅为分配几个切片就建设复杂的多 Agent 平台。

### 11.3 保护共享工作，不把单写者扩大到一切

确定共享接口、文件归属和集成顺序后，无冲突切片可以并行；公共接口变更先协调。数据库结算、原子发布、设备写入和 Git 集成各有自己的竞争边界，不需要把所有代理的所有工具串行化。

用户曾授权某轮全权处理其他代理改动，也曾要求“先准备接入、不要接入”。这类指令都是当时的操作范围，不应被记录成跨任务永久权限。默认保留不属于本任务的修改；需要接管时核对当前明确授权。

提交以完整、可复核的逻辑单元为目标，不迷信每次只能几个文件，也不盲目加入整个工作区。写文件、提交、推送、合并和发布是不同动作，分别按当前授权执行；源码、文档与必要验证器一起交付，原始大产物和一次性脚本不自动进入 Git。

### 11.4 阶段性检查点降低未集成风险，不等于提前完成

长时间把多个已验证切片、并行修改和历史材料堆在一个未提交工作树中，会逐渐失去“哪批源码对应哪组证据、哪些文件属于谁、出现回归应退到哪里”的清晰边界。阶段性收尾的价值是降低这种未集成风险，而不是宣布整个产品或长期任务完成。

一个逻辑单元已经可构建、可解释、适用验证通过且剩余边界明确时，应及时核对改动归属、源码/制品身份和未覆盖事项；在当前授权允许时形成可复验检查点。外部账号、设备或发行验收尚未满足，可以继续保持为对应任务的开放边界，不必让独立本地工作无限堆积。Helix 的一次阶段收尾曾面对数百个受跟踪/未跟踪变化，这个案例说明需要检查点，但**不产生“超过多少文件就必须提交”的机械阈值**，见 [阶段记录](../evidence/development/phase-closeout-2026-10-01.md)。

### 11.5 上下文优化优先改读取方式

所有者对重复建设 CodeGraph 替代工具的质疑，体现了“先盘点现有能力，再增加辅助”的偏好。已知小改动直读相关范围；关系不清时用已有 CodeGraph；精确词、文档和未索引内容用限定搜索，再看调用者、状态 owner 与测试。

索引是线索，不是当前文件的证明。交接应保存目标、范围、基线、关键位置、有效契约、已验结果和剩余问题；不要复制全仓或为每个模型再造一份计划。具体操作复用 [上下文导航](context-navigation.md)，不让本手册变成新的必读上下文负担。

## 12. 文档治理：解释、裁决、执行与证据分开

**性质：明确偏好与项目经验。**

所有者多次要求收敛文档、消除过时和重复信息，并明确 HXA 偏代码开发，不为纯文档整理单独编号。长期经验应该有出处，但不能靠增加更多平行文件解决信息混乱。

| 文档角色 | 负责回答 | 不应承担 |
| --- | --- | --- |
| Research | 有哪些证据、方案与取舍 | 自动授权实现、维护实时任务 |
| ADR | 当前接受什么决定、为何变化 | 让读者叠加旧补丁才能拼出有效规则 |
| Architecture | 组件职责、边界和技术契约 | 将计划能力冒充已交付能力 |
| HXA | 本项实现范围、依赖和验收 | 为一次纯整理重复建任务体系 |
| Status | 当前做到哪、下一步是什么 | 复制全部历史流水账 |
| Roadmap | 工作项清单与索引 | 第二份当前排期 |
| Completion / Evidence | 当时改了什么、实际跑了什么 | 将旧现场、旧权限和旧待办永久化 |
| 本手册 | 所有者偏好、判断方法和可复用教训 | 替代项目规则或创建新权限与门禁 |

长期主题使用稳定文件名；时点评审和证据带日期。改名要修引用，合并要保留独有依据，历史材料注明适用时间。页数多不等于应全部合并，时间旧也不等于没有价值。

当源码与 ADR 不一致，应记录实际行为与接受契约之间的差异；不能通过改文字掩盖未实现，也不能因为旧代码如此就恢复已撤销设计。本文只链接 Helix 的具体规则，不再复刻它们的枚举、步骤和状态表。

## 13. 代表性案例：从问题到可复用教训

下表概括历史决定与仓库记录，不是当前待办，也不表示本次重新执行过这些验收。

| 案例 | 当时的选择与结果机制 | 可以复用的教训 |
| --- | --- | --- |
| HTTP Provider | 用户要求警告而非额外授权；接线需贯通表单、探测、发送、队列与网络配置 | 先识别哪一层在拦截；移除 UI 阻碍后还要检查底层与制品 |
| Composer 与管理页 | 恢复异常不锁住文字；未确认附件不静默丢弃；管理列表补齐滚动提示 | 降低阻塞与保持内容真实性可以同时成立；按用户完整路径检查 |
| Mobile Use 授权演化 | 从全局/短期运行许可收敛为 Conversation 持久配置，原生截图复用授权 | 授权主体、有效期和运行态要分开；一次用户决定可以支持多次真实校验 |
| 应用选择器 | 用名称、分类、搜索与多选代替包名输入，保留完整范围 | 简化输入方式不能改变授权集合；列表不可见不代表用户取消选择 |
| FFmpeg 接入 | 先验证裁剪与包体，再复用已有 Bash／Linux Job，避免第二套执行路径 | 优先验证可能推翻方案的成本与边界，通用能力可比有限预设更完整 |
| 模拟器扫描复核 | 区分产品问题、测试契约与驱动缺陷，修复虚假通过和证据漏项 | 评审与红灯都要先判断失败机制；测试基础设施也是质量系统的一部分 |
| 显式选模契约传播 | 从隐式 Provider 默认回退改为会话必须显式选模，UI、服务准入、附件旅程和测试同步调整 | 变更要追踪共同假设，不只修调用者或界面 |
| 执行全局锁撤销 | 保留执行身份、容量和内部一致性，但终端/未知结果不再全局阻塞无关任务 | 临时保守限制不是永久正确；规则需要重新评审和退出条件 |
| 阶段性收尾 | 大量跨阶段工作先核对归属、源码/制品身份与未验边界，再形成检查点 | 检查点降低未集成风险，不等于整个长期任务完成 |
| HXA-244 证据收尾 | 最终源码/测试 APK 与旧汇总不一致，需要重新绑定记录 | 收尾是交付的一部分；旧绿色与当前可验事实不是同一件事 |
| [文件工具执行后回填失败](../evidence/development/files-vision-readme-2026-10-01.md) | 工具已成功，后续历史编码拒绝规范化参数 | 按同一操作的失效边界定位，不按表面功能名称改错层 |
| [回放依赖被当作缓存](../evidence/development/v0.0.4-release-2026-10-01.md) | 旧会话所需签名被条数上限淘汰，跨阈值回归证实问题 | 数据回收服从可重建性与有效引用；短流程绿色不覆盖累积状态 |
| CodeGraph 复用 | 已有代码导航能力时收敛自建辅助和重复资料包 | 增加工具前先证明缺口；维护成本也应计入优化收益 |

案例出处分别为 [阶段收尾](../evidence/development/phase-closeout-2026-10-01.md)、[HXA-238](../evidence/development/hxa238-execution-provider-2026-10-02.md)、[HXA-239](../evidence/development/hxa239-composer-2026-10-02.md)、[HXA-240](../evidence/development/hxa240-ffmpeg-proot-2026-10-02.md)、[HXA-241](../evidence/development/hxa241-emulator-sweep-reconciliation-2026-10-02.md)、[HXA-242](../evidence/development/hxa242-http-ui-host-2026-10-02.md)、[HXA-244](../evidence/development/hxa244-conversation-mobile-use-host-2026-10-03.md)及 [CodeGraph 导航](context-navigation.md)。具体通过范围只以各自记录为准。

## 14. 常见反模式与修正方向

**性质：根据前述偏好和案例归纳，不是认定项目当前仍存在全部问题。**

| 反模式 | 为什么偏离目标 | 更合适的修正 |
| --- | --- | --- |
| 每遇到一种业务失败就加固定恢复流程 | 把模型策略写成框架限制，路线不断膨胀 | 先补观察、错误与可恢复条件 |
| 同一意图在多层逐次批准 | 用户难以理解重复确认的差异 | 区分授权对象，范围内复用 |
| 用超时证明无副作用 | 回执丢失不等于动作没发生 | 记录未知，先观察再决定新调用 |
| 全局 BUSY 锁住所有任务 | 局部资源问题扩散为产品不可用 | 找真实 owner，仅限制相关容量 |
| 临时限制写进测试后永久保留 | 测试把历史实现约束误当成永恒契约 | 记录限制原因和重新评审条件，契约变化时同步修生产与测试 |
| 把评审清单直接转成当前待办 | 事实、严重性和优先级被混为一谈 | 先验证入口/触发/影响，再决定是否进入当前范围 |
| 只证明危险路径被挡住 | “什么都不能做”也可能通过负向测试 | 同时验证获准路径和无关能力仍能正常工作 |
| 界面只置灰、不解释 | 用户无法修复，也不知是否还在工作 | 统一可操作性与原因投影 |
| 数据不完整时默默降级输入 | 表面成功，实际背离用户原意 | 保留草稿和身份，说明补充或移除入口 |
| 包装预设替代已有完整能力 | 功能面变窄，又多一套执行链 | 评估直接复用现有通用能力 |
| 用旧 alias、双写兼容保留错误设计 | 多个事实源持续增加理解成本 | 按产品阶段裁决，替换后删除旧路径 |
| 只追踪调用关系，不追踪共同假设 | 跨层仍可能保留旧数量、生命周期或完成语义 | 明确哪条假设改变，并检查持久化、恢复、控制、UI 与测试 |
| 用工具数、类数或文档数证明进步 | 数量与用户任务收益没有必然对应 | 看真实任务、控制响应与修改影响面 |
| 为了“更规范”重新做已有工具 | 引入维护面但缺少新收益 | 先改善现有工具的接入与使用方式 |
| 把测试编译、跳过或旧日志算通过 | 交付结论超过证据 | 分层、分身份和分状态报告 |
| 把某次全面接管当永久权限 | 历史授权替代了当前用户决定 | 每轮重新确定操作范围 |

## 15. 把原则用于下一次开发

以下是归纳性的思考顺序，不要求写一份额外表格，也不替代既有实施流程。

**开始前：**先描述具体用户阻碍和证据，区分真实缺陷、产品取舍与新能力。评审意见先核对实际入口、触发条件和影响，再决定是否进入当前范围。确认任务授权和非目标，找现有 owner、可复用入口以及会受影响的契约；如果数量、生命周期、身份或完成语义发生变化，明确哪些模块共享这条假设。新增限制时同时说明保护什么和何时值得重新评审；新增抽象时说明实际消费者；重构时说明何时停止。

**实施中：**修复故障时沿同一次操作定位失效边界；验证方案时先找关键不确定性，将其变成可验证反例，优先验证最可能推翻方案的条件，再沿完整调用链修改。尽量分开等价迁移与策略变化，保留原始调用身份与用户内容，逐步删除旧路径。检查共同假设是否同步传播到持久化、恢复、控制、UI 和测试；保护机制既要证明错误被阻止，也要证明正常获准路径仍能工作；按变化选择阈值、重开或历史继续等状态边界反例。发现新的相关正确性问题应处理；无关的好建议记录为候选，不无条件延长结束线。

**结束时：**证明请求的用户路径已经接通，授权没有扩错、结果没有说假、无关能力没有被锁住；报告当前源码和制品对应的实际验证及未覆盖边界。一个逻辑单元已经可构建、可解释、适用门禁通过时，应整理归属和剩余工作，并在当前授权允许时形成可复验检查点；阶段保存不冒充整个长期任务完成。文档只更新自己的职责，按当前授权保存、提交或发布，不以“还可以继续优化”为由拒绝交付。

**判断优化是否值得继续：**比较同条件下的任务完成、无效调用、人工介入、资源开销、上下文获取、复核和二次修改成本。纯结构收敛可以有独立价值，但不要编造成功率和效率提升；没有可重复证据时明确只是设计判断。强模型、便宜模型、更多测试或更多工具都只是手段，目标是降低从需求到可验收结果的总成本。

### 16.3 更新规则

只有出现新的明确偏好、可追溯教训或适用边界变化时更新本文。修改一条原则时保留其理由与例外；具体产品策略更新所属 ADR，执行结果更新任务证据，不在这里追加每次构建流水账。

发布成熟度、平台要求、数据承诺与团队规模变化时应重新判断适用性。需要提炼代理硬规则时，只把已经确认且确有必要的少量内容写进项目 AGENTS；不要要求每个小任务全文加载本手册。

**最终记忆：少建重复系统，少制造同义阻塞；评审先验证，限制有退出条件；持久保存用户决定，准确表达执行事实；既证明不会做错，也证明正常路径能做成；用当前证据和可复验检查点完成有边界的交付。**
