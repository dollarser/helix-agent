# Helix 开发原则与后续推进策略

初稿整理：2026-09-29；模型/Harness 职责与减法原则衔接：2026-09-30。

> **核心结论：先完成一轮有明确终点的公共基础收敛，用真实能力验证边界，再转入功能交付与任务成功率优先的阶段。**
>
> 主要来源是关于“先补功能还是先重构、如何避免反复大重构”以及“模型/Harness 如何分工”的对话。本文只维护开发方法与停止条件；职责规范和重新核验的竞品依据集中在详细重构方案 §13.6、§12.5，不复制第二份技术契约或评测结论。
>
> 本文不是第二份实时排期，也不因文档落盘就接受全部候选功能。当前执行看 [status](status.md)，任务范围看对应 HXA，技术契约看 ADR 与[详细重构方案](../architecture/harness-refactor-plan.md)。

## 1. 本次选择：有限基础收敛，而不是两个极端

Helix 当前不宜先把所有候选功能补齐，再统一清理架构；也不宜先完成所有理想架构、远程能力和通用接口，再恢复功能开发。

推荐的方式是：**宏观上先稳定反复被触碰的公共边界，微观上以保持可用的纵向切片推进；设计覆盖已知变化类型，实现只服务真实消费者。**

| 路线 | 当前主要风险 | 本次结论 |
| --- | --- | --- |
| 先补齐所有功能，之后统一重构 | 新功能继续依赖已知耦合，扩大后续迁移、测试和状态处理成本 | 不采用 |
| 先完成全部未来架构，再补功能 | 接口缺少消费者；远程、多 Agent、触发器等不断变成前置，完成线后移 | 不采用 |
| 有限公共收敛＋代表性能力验证＋后续局部扩展 | 需要约束范围与退出条件，但可以同时获得结构证据和真实交付 | 推荐 |

目标不是“以后核心永远不改”，而是让多数同类能力的新增主要落在自己的领域和适配器中，不再必然改变整套 Turn、权限、上下文与恢复语义。

## 2. 对反复重构原因的归纳

以下是对话中的分析，不是本次重新执行的源码审计。

### 2.1 不同变化被当成“再加一个工具”

| 能力变化 | 真正增加的要求 |
| --- | --- |
| 文本读取 | 有界同步调用和结果 |
| 图片读取、浏览器截图 | 类型化视觉内容、来源、预算和 Provider 编码 |
| 后台命令 | 调用与执行生命周期分离，独立身份、等待和控制 |
| 插件安装、更新与停用 | 一批内容和工具的归属、原子发布及实时失效 |
| 项目记忆 | 项目身份、跨会话范围、内容更新和请求绑定 |
| 子 Agent | 独立决策工作单元、委托上限、预算与取消 |
| 定时或事件启动 | 没有当前用户消息时的新任务启动资格 |

前五类已有真实需求或实现基础，应共同检验当前边界。后两类需要独立设计，不能为了未来可能支持就提前实现全部体系。

### 2.2 “拆类”没有必然形成扩展边界

将大类拆成多个 Service，不能单独证明修改成本降低。应检查：增加内容来源是否仍需多处手工拼接；新增执行适配器是否仍要改 Loop；更新工具是否改变了调度与执行之间的契约；增加异步能力是否又建了一份状态真相。

### 2.3 结构重构、功能扩展和产品变更混在一起

三类工作分别记录，避免把所有返工归为“原架构失败”：

- **结构重构**：外部行为保持，调整职责、依赖和接线。
- **能力扩展**：新增一种输入、执行方式、观察结果或交互形式。
- **产品变更**：用户希望现有功能采取不同的行为，例如聊天输入缓存不再成为发送前置。

第一类应通过本轮收敛减少重复成本；后两类仍会发生，合理边界的作用是限制其影响范围，而不是禁止产品变化。

### 2.4 评审不断扩大“本轮必做”

每个新建议独立看都可能合理，但不能把所有合理建议都升级为当前前置。某阶段新增了存储、事件或生命周期迁移时，应明确范围变化，而不是沿用原来的“小整理”标签。

**评审要帮助已有目标闭合，不能让“还有优化空间”成为永远不能交付的理由。**

## 3. 开发原则

### 3.1 先处理重复触碰的边界，不追求一次设计全部未来

提前考虑工具会更新、执行会异步、结果不只有文本、内容有不同范围、核心有多个入口。不要同时建设所有工具、远程协议、视频平台或多 Agent 工作流。

### 3.2 稳定语义，不冻结错误依赖

保留经过验证的授权、身份、持久结算、幂等和未知副作用处理；允许移动类、修改构造参数、提取端口和替换旧实现。是否保留代码取决于它是否适合目标边界，而不是是否已经写过。

内部 clean-slate 不等于删除用户文件、放弃有效外部协议或破坏当前数据承诺。具体边界沿用现行 ADR，不在本文重写。

### 3.3 接口分离优先，部署保持简单

完整本机 Harness 内区分 Agent Core、统一工具治理和 Execution Host。默认使用本机类型化接口，重资源或不同隔离要求的 Runtime 按已接受方式运行。

接口分离不自动要求独立 Brain 进程、HTTP 服务、网络配对或多套数据库。未来兼容首先来自职责与协议，不来自提前部署所有未来形态。

### 3.4 用真实能力验证抽象

每个公共边界至少应解释它服务的现有调用链、状态和失败路径。已有能力足以验证时，不另外造多个空生产 provider。测试适配器用于验证契约与故障，不冒充真实设备或服务交付。

### 3.5 统一治理，不机械统一领域

模型工具复用统一准入、权限、执行结果和审计规则；Plan/Goal/用户交互与文件/代码/设备操作保留各自领域所有者。Skill 是内容，MCP 是协议，Plugin 是交付组织，Job 是执行工作，不合成一个万能对象。

手动文件管理、配置和任务查看不因统一接口就必须创建会话或调用模型；手动授权也不自动扩大模型权限。[现有规划规则](implementation-guide.md)继续适用。

### 3.6 结构迁移与行为优化分开验证

先保持行为完成生产接线迁移，再增加功能或修改策略，最后验证用户结果。R2-A 与 R2-B 分开，不把模型、Prompt、预算、摘要策略和代码结构同时改变后笼统宣布重构有效。

### 3.7 临时桥接有退出点，旧路径真正删除

迁移允许短期单向适配，保持系统可构建、可运行；不得保留长期双写、平行 Loop、重复 Job 真相或两个可变安装身份。每个切片列出旧路径删除要求。

clean-slate 不要求一个不可构建的大提交。切片是实施和验证边界，不是缩小已授权完整任务的理由。

### 3.8 任务价值和变更成本优先

衡量结果是否正确、用户是否能控制和恢复、同类功能是否更容易接入。类数、接口数、工具数和架构图层数不作为收益。

局部参数、编码和装配文件需要修改很正常；只有局部能力迫使多个无关领域改变权威或生命周期时，才说明公共边界可能有问题。

### 3.9 不用重构掩盖事实，也不以完美为完成标准

构建通过不等于功能正确，正常 Turn 结束不等于用户目标完成，文档门禁通过不等于架构验证。未知、未复现、跳过和未请求保留原状态。

已有结构得到验证后，进一步的美化、另一种命名或竞品新功能应竞争投入，不自动阻止当前阶段结束。

### 3.10 模型主导任务，Harness 保证执行与反馈

模型决定任务路线、工具选择、失败后的策略调整与自然语言完成判断；用户定义授权范围；Harness 负责忠实执行、真实结果、取消和资源边界。执行状态机不等于业务工作流，薄 Harness 也不等于没有权限、状态或预算。

先改善工具能力与反馈，再考虑硬编码流程。确定性重连、查询与收取不转嫁给用户；业务澄清、真实授权和系统认证仍是必要交互。可调运行策略与 Prompt/Skill 指导各归其位，不为每个失败新增一套 recovery driver，也不强制所有动作经过统一 verifier。

每个切片说明保留哪些机制、删除哪些重复流程、哪些规则移入原配置/指导层、哪些变更仍待接受。具体矩阵与十条准则只在 [Harness §13.6](../architecture/harness-refactor-plan.md#136-模型与-harness-的职责优化及减法准则)维护，模型反馈要求见 [§15.6](../architecture/harness-refactor-plan.md#156-面向模型的结果反馈事实充分接口精简)，不以本节扩张当前任务。

## 4. 本轮基础收敛的有限范围

以下是对话形成的建议范围。具体接口、迁移卡片及测试只在[详细重构方案](../architecture/harness-refactor-plan.md)维护，本文不再复制签名或状态机。

| 公共边界 | 本轮建议完成什么 | 不把什么夹带进来 |
| --- | --- | --- |
| 工具身份与治理 | R1：现有工具来源使用准确原子绑定，贯穿曝光、调度、审批和 executor | 全部 Core 迁移、通用 Job、完整插件平台 |
| Core 与执行宿主 | R2-A 的必要端口和生产接线：去 UI/消息格式/存储实体的不合理依赖，保留事务 | 独立云 Brain、远程 Runner、公共网络 Server |
| 调用结果与异步观察 | 固定最小结果/身份/控制契约，并以现有 Linux Job 的 J1 闭环验证 | 所有 Runtime 统一后台化、完整 J2 UI、远程 Job、子 Agent |
| 内容贡献与扩展归属 | 已有图片、Skill、Memory、Reference 与动态来源按同一边界处理 | 全部 PDF/视频/向量检索、整个 Marketplace 扩展 |

Plugin 的安装、组件、连接和选择边界应在设计时明确；完整 R3 在大规模扩展相关安装能力前落地，不成为所有独立功能的前置。

本文中的“最小”表示范围有限，**不表示只写接口和测试后不迁移生产入口**。

## 5. 用六类代表性能力验收架构

主要迁移和验证已有能力，不同时立六个全新功能项目。写作时的基础与实现范围可查 [status](status.md)；既往主机、设备和真实模型证据不可互相替代。

| 样本 | 检验的边界 | 应能回答的验收问题 |
| --- | --- | --- |
| 普通文件读取/修改 | 短调用、参数、权限、结果和产物 | 能否复用同一治理，不在 Loop 加业务分支？ |
| `view_image`/浏览器截图 | 非文本结果、可信来源、预算和协议 | 图片能否作为真实视觉内容进入请求，而非普通字符串？ |
| Linux 后台 Job | 独立执行身份、等待、取消、收取 | 能否停止等待而不误报执行停止，且控制仍可响应？ |
| 动态 MCP 工具/插件更新 | 原子发布、来源失效、旧调用处理 | 新旧契约是否准确绑定，停用后是否仍有错误可达入口？ |
| Skill/Global Memory | 内容贡献、作用域、渐进加载 | 能否增加内容而不再手工修改多条上下文流水线？ |
| Plan/Goal 内部操作及手动文件操作 | 领域所有权与不同用户入口 | 是否既复用必要规则，又不强迫所有操作进入 Runner/LLM？ |

如果这些已知变化仍然迫使核心不断增加特殊分支，就先修正对应边界。若均能合理接入，就进入 §6 的停止判断，不以更多假设消费者继续扩张。

## 6. 本轮重构的五项停止条件

停止条件应在实施前固定。以下为本轮建议结束线，不表示当前已经满足；新增范围只有在有证据说明当前目标无法成立时才讨论。

| 条件 | 所需证明 |
| --- | --- |
| **一份工具绑定事实** | 现有来源已迁移，旧双表写路径删除，更新/撤销/调度交错测试通过 |
| **Core 的错误跨层依赖已移除** | Core 可通过测试存储、Provider 和执行适配器完成无界面回合；真实存储事务另外验证 |
| **主要变化类型已被容纳** | §5 的同步、异步、图片、动态来源、内容贡献和领域入口通过相关契约 |
| **多数同类扩展可以局部完成** | 新能力主要修改自身领域、适配器和装配；不要求再次重做 Turn/审批/恢复 |
| **旧路径删除且手机体验没有退化** | 无永久双轨、重复状态机或无界资源；相关用户任务、取消和恢复有对应证据 |

达到这条结束线后，转入功能交付；未达到时修复具体不满足项，而不是自动开启下一轮全仓架构研究。安全/正确性要求仍按现行 ADR 验收，不能为了停止而降低门槛。

下列理由不能单独延长本轮：更通用的类名、目录更对称、竞品又增加模块、未来可能再有一种 Host、所有接口还没做到统一、仍有不影响当前目标的候选建议。

## 7. 后续推进计划：三段推进，而非无条件串行清单

### 7.1 写作时的状态与建议必须分开

2026-09-29 初稿引用的“R1 下一步”是当时状态。2026-09-30 衔接时，[HXA-232](tasks/HXA-232.md)自主恢复已明确优先于 [HXA-231](../completion-records/HXA-231.md)的 R1；后续实际顺序只看 [status](status.md)。[候选索引](candidate-decisions.md)继续区分 R2/R3/J1/J2 等目标设计与实施授权。

本页不滚动维护进度。文档修订不自动改变任务顺序、接受全部提案或启动实现；已授权范围内的普通可逆实现也不应反复请求立项。下面三段是取舍方法，不能拿来覆盖最新任务。

### 7.2 第一段：有限公共基础收敛

**建议顺序：当前用户阻断问题继续修 → 完成 R1 → 收敛最小 Core/执行/上下文边界，并用已有能力和 J1 验证 → 达到停止条件。**

发送失败、数据丢失、无法停止等直接阻断问题优先处理；不要以进入重构期为由冻结修复，也不要为清单全绿无限追逐尚无新证据的偶发问题。

R1 完成后，R2-A 与 J1 在相关决定接受后按可交付切片推进。接口可以联合设计，实施不要求全并行；共享边界有单一负责人，避免多个执行者各建一套新契约。

本段不包含 R2-B 的全部策略实验、完整插件管理改版、所有 Host、Subagent、远程体系或每一项候选功能。不会把整份长期重构方案变成发行前置。

### 7.3 第二段：优先提高真实任务成功率

基础满足结束线后，根据实际失败轨迹优先完善多轮补全、观察、等待和结果确认，而不是继续增加抽象。

重点包括：缺失参数可从已授权环境取得时先查询；必须由用户决定时精确追问；工具未曝光时发现，真实缺失时说明；动作后读取新状态，不能把接口返回成功当成用户目标完成。

这些是模型的工作准则与工具应提供的能力，不是要求 Engine 硬编码统一步骤。模型可以选不同合法路径；后置核查按任务需要执行，确定性工具检查不伪造成独立业务判断。

分别处理 Job 完成等待、页面/元素条件等待和业务结果确认。三者相关但不等同，不因为需要统一能力就再建一个万能工作流引擎。

### 7.4 第三段：按能力族扩展，局部重构随交付进行

稳定公共边界后，大部分功能采用“影响范围判断 → 必要局部整理 → 完成功能 → 验证任务”的方式。新增真正的生命周期或权限主体时，在相关领域单独裁决，不借机重新讨论所有核心结构。

并行条件是边界与改动归属清楚，而不是“所有新功能都允许同时做”。不触碰正在迁移的共享边界的独立功能可以推进；会在旧核心上增加依赖的功能先等待对应切片。

### 7.5 技术依赖不等于推荐排期

现有依赖正文在重构方案 §9；这里仅强调本次对话中最容易被误读的关系：

| 工作 | 应保留的必要关系 | 不应添加的前置 |
| --- | --- | --- |
| R1 | 当前基线与最小准确绑定契约 | 完整 Core、ContextCompiler 或 J1 |
| R2-A | 存储/事务等端口先行，再迁移 Core 接线与上下文 | 新 Prompt、远程部署、全套插件产品化 |
| J1 基础 join | R1 及最小 completion/控制/期限接线 | 完整 R2；观察自动注入可单独接入 |
| R3＋最小 R5 | R1、现有安装/选择事实、运行中 Job 引用 | 新 J1/J2；也不能把最小可用 UI 全拖到后面 |
| R2-B | R2-A 等价基线与可复核实验 | 所有后续功能完成 |
| J2 | J1 与同执行身份、存活策略证据 | 手动按钮与 AUTO 必须同时交付、远程 Node |

## 8. 候选功能的进入顺序与抉择

以下是条件性建议，不是新承诺或固定日期。完整需求及接受边界继续使用[候选索引](candidate-decisions.md)，不在本页重建 FUT/HXA 清单。

| 方向 | 建议如何进入 | 防止重复重构的接入方式 |
| --- | --- | --- |
| Mobile Use 截图/观察 | 当真实失败需要像素或更及时观察时优先评估 | 复用既有视觉回填；不等完整 Observation 平台，不把浏览器截图当整屏截图 |
| PDF/Office 读取 | 先选择一个格式和明确任务，分别处理解析与视觉 | 作为内容/解析适配器接入；不以全格式兼容为首版目标 |
| Project Memory | 项目身份、会话关联、请求范围先明确 | 使用既有 Memory 与上下文机制，不让检索索引代替项目身份 |
| Plugin 安装/市场扩展 | 扩大来源前完成相关 R3 生命周期迁移 | 包管理与最小配置修复闭环一起交付，不继续堆平行安装入口 |
| J2 AUTO/手动后台化 | 在 J1 与 Runtime 同执行契约成立后推进 | AUTO 与手动 UI 可分步；不重启命令或重置预算 |
| Subagent | 有任务拆分收益和独立范围时立项 | 新决策工作单元单独定义，不作为普通 ProcessJob |
| Code Mode | 有组合工具收益证据时立项 | 复用治理并明确嵌套调用/取消/预算，不开放无边界特权桥 |
| 定时/事件自动触发 | 有明确用户启动与运行资格约定时立项 | 触发新的正常任务，不成为主 Loop 的固定工作流大脑 |
| 远程 Host/双向 A2A/多设备控制 | 有真实消费者后再决定 | 保留受控接口，不提前建设全部网络、配对和远程状态系统 |
| 向量 Memory | 先定位写入、恢复、召回和证据使用瓶颈 | 需要时作为辅助检索，不因单一低分推翻 Markdown 正文 |

“功能更多”不是优先理由。对同一投入，优先选择能减少明确用户阻碍、可验证结果、且不依赖未定公共契约的工作。没有对应证据时保持候选，不编造收益或成本排名。

## 9. 每次新功能先做影响范围判断

不要求每次新增能力都全仓重新评审。先回答五个问题：

1. 它属于哪个现有领域，服务哪条用户任务路径？
2. 是否引入新的生命周期、权限主体或事实所有权？
3. 需要改变哪些公共契约，而不仅是哪些文件？
4. 现有接口为什么不能容纳它，是否有具体调用链或失败样本？
5. 新规则属于必须的执行机制、授权/平台边界、可调策略，还是应交给模型的业务决策？换成更强模型后，这条硬编码分支为何仍有必要？

| 判断结果 | 实施方式 |
| --- | --- |
| 只是新的解析器、Provider 编码或工具适配 | 直接交付功能，附必要局部整理 |
| 同类变化已反复修改多个实现位置 | 先对该模块做有界预备性重构，再接功能 |
| 新增子 Agent、远程执行或新的信任边界 | 先确定相关领域契约和接受范围，不扩展成全仓重设计 |
| 只是设计风格、命名或无消费者的通用化偏好 | 不阻塞当前功能，记录为建议或不做 |

文件改动多不是充分证据；例如三种 Provider 各自编码图片是合理适配。相反，一项局部功能要求 UI、Loop、权限与恢复都改变其权威含义，即使只改几个文件，也值得先处理边界。

## 10. 评审分级与范围控制

### 10.1 评审意见分成三类

| 类别 | 典型内容 | 是否进入当前收口 |
| --- | --- | --- |
| 必须当前解决 | 越权、错误执行、状态丢失、明确违反已接受契约 | 是；给出触发条件和最小修复 |
| 当前范围内应解决 | 直接相关的重复实现、反向依赖、测试缺口 | 是；不能借此无限扩大到邻近领域 |
| 后续候选建议 | 新平台、新模式、额外通用化、尚无收益证据的优化 | 否；回到候选索引和对应来源 |

每次评审说明问题位置、影响和验收办法，不只写“架构还不够合理”。已通过且未受新改动影响的结论可以引用，不能因为更换复审模型就重新开启所有讨论。

### 10.2 改变完成线需要可说明的原因

只有新证据表明当前契约无法满足已接受任务，或出现真正安全/正确性阻断时，才讨论扩大当前范围。必须说明原范围为何不足、新增内容与任务的关系、如何更新退出条件。

新增竞品功能、假想的第三种 Host、目录美观或另一种抽象风格，不自动构成扩大理由。评审中发现的普通改进可以长期存在，不意味着当前阶段不能完成。

## 11. AI 协作、切片与交接

设计/复核负责人稳定公共契约和范围；执行者完成对应切片及测试，不自行增加平行 Engine、Job 库或另一套权限机制。角色是协作职责，不固定绑定某一产品或模型。

对已授权范围内的可逆实现，自行判断并完成，不为每个类名和方法重复请示。遇到真正的跨领域契约变化，给出最小反例、影响范围和可选修复，再进入对应决定流程。

建议每个交付单元保持如下顺序：

```text
核对当前任务、源码与改动归属
    → 固定本切片改变的契约与回归样本
    → 保持行为完成必要结构迁移
    → 在新边界交付功能或行为变化
    → 验证用户结果及失败/取消/恢复
    → 删除旧路径并交接实际证据
```

切片之间保持可构建；临时桥接明确删除点。共享接口由一个负责人收口，不让并行执行者分别设计同义契约。跨任务工作树、提交、设备与真实服务权限遵循 [AGENTS.md](../../AGENTS.md) 和[实施指南](implementation-guide.md)，本总结不授予额外操作权限。

交接只记录当前契约、已完成入口、剩余旧路径、验证结果和下一项输入；不为每个模型维护一份滚动计划。已授权任务不因完成一个测试就停止，也不把未验证范围写成通过。

## 12. 用什么证据决定优化有效

### 12.1 分开结构正确性、任务收益与修改成本

| 维度 | 观察内容 | 避免的误判 |
| --- | --- | --- |
| 结构正确性 | 准确绑定、唯一事实源、无协议孤儿、取消/恢复和事务一致 | 不能用“类已经拆开”替代 |
| 真实任务收益 | 独立核验的结果、耗时、无效调用、人工介入、控制响应 | Turn 正常结束不等于业务成功 |
| 手机资源 | 受影响路径的内存、执行/IPC/构造开销和响应 | 分层不天然更快；不能接受无界线程或重复快照 |
| 变更成本 | 同类能力需修改的无关领域、公共契约反复改动、桥接积累、功能被二次重写 | 接口数量、图的整齐程度不是架构收益 |
| 自主性与反馈 | 可避免的策略阻断、非必要人工介入、模型收到的结果/错误/来源、恢复成本 | 少弹窗不等于正确；更大预算不等于更好架构，比较方法见 Harness §20.2 |

结构性一致性可独立构成价值，不要求每次重构都证明模型得分提高。Prompt/检索/等待策略则需要同条件任务实验；样本和基线不足时明确保留不确定性，不给出固定收益百分比。

### 12.2 评测对本轮排序的指导边界

前述 BFCL/AndroidWorld 分析支持重视多轮信息补全、真实观察和动作后的结果确认；也暴露了成绩聚合、有效样本与环境缺口需要区分。本文不重新判分，不把此前报告中的总分、排名或归因升级为新证据。

沿用以下判读原则：模型直连成绩不是 Helix 全链路成绩；模板尝试覆盖不是有效评测完成；缺失环境不证明模型能力差；正常终态不证明达成目标；向量类别低分不直接证明缺少向量数据库。

实现前后固定模型、任务、输入、预算、制品和判分口径，分开主机、设备、真实服务结果。调试样本与最终验证样本、原失败与修复后结果分别保留，不挑最佳重试拼分。

复用已有 Eval 与[系统基线](harness-system-baseline.md)，必要时做模型、Harness、真实平台三层对照；不因为分层就另建一套长期成绩系统。具体环境与授权遵循[公共验收规则](verification-matrix.md)。

## 14. 开始与结束一个切片时的检查表

此表是上述原则的执行提醒，不增加新的技术契约或交付范围。

**开始前：**

- [ ] 已区分结构重构、功能新增和产品行为变化，并核对当前授权。
- [ ] 说明要解决的实际任务或结构风险，以及具体受影响边界。
- [ ] 写清本切片不做什么、要删除哪些旧路径、如何判定完成。
- [ ] 已区分执行机制、可调策略和模型业务决策；没有把技术恢复或固定流程强加给所有任务。
- [ ] 已选代表性调用与失败样本；没有为假想消费者建立生产框架。
- [ ] 已核对真实依赖，不把推荐顺序误变成所有功能的前置链。

**结束前：**

- [ ] 唯一生产入口已切换，未留下永久双写、平行状态机或无界资源。
- [ ] 功能结果、取消、权限与恢复按范围验证，未请求和失败如实记录。
- [ ] 适用的结果/失败事实确实进入下一模型请求；正常授权内不增加重复确认，真实授权和必要澄清未被删除。
- [ ] 结构收益、任务收益及未测项分别说明，没有以工具数量或主观评分验收。
- [ ] 新发现的未来建议进入候选，不无故改变当前完成线。
- [ ] 达到本轮五项停止条件后，转入功能交付，不因“还能优化”继续扩大基础重构。

**最终原则：该提前设计的是已知变化的边界；该按需交付的是具体功能。当前先收敛基础，随后让真实任务决定投入，允许局部演进，避免普通功能反复触发整套 Harness 重设计。**
