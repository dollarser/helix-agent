# Helix 开发原则与后续推进策略

初稿：2026-09-29；职责衔接与内容收敛：2026-09-30。来源为功能/重构取舍及模型/Harness 分工讨论。本文维护方法与停止条件，不维护实时排期或第二套技术契约。

**主线：有限公共基础收敛 → 用真实能力验证边界 → 转向功能交付与任务成功率。** 当前工作以 [status](status.md) 和用户指定任务为准；已完成阶段不因本文的通用方法重新启动。

## 1. 本次选择：有限基础收敛，而不是两个极端

| 路线 | 取舍 |
| --- | --- |
| 先补齐全部功能再重构 | 不采用：复制已知耦合，扩大迁移和测试成本 |
| 先完成所有未来架构再补功能 | 不采用：接口没有消费者，完成线不断后移 |
| 有限公共收敛＋代表性能力验证＋局部演进 | 推荐：设计覆盖已知变化类型，实现服务实际消费者 |

宏观稳定反复被触碰的边界，微观保持纵向切片可用。目标是多数同类能力局部接入，不是核心永远不改。

## 2. 对反复重构原因的归纳

| 看似都是“加工具” | 实际新增的要求 |
| --- | --- |
| 文本读取 | 有界同步调用与结果 |
| 图片读取/浏览器截图 | 类型化视觉内容、来源、预算和 Provider 编码 |
| 后台命令 | 调用与执行生命周期分离，身份、等待和控制 |
| 插件安装/更新 | 组件归属、原子发布与来源失效 |
| 项目记忆 | 项目身份、跨会话范围与请求绑定 |
| 子 Agent | 独立决策单元、委托、父预算和取消 |
| 定时/事件 | 没有当前用户消息时的新任务启动资格 |

“拆类”不等于建立扩展边界：若新增来源仍需多处拼装、更新工具仍使调度与执行错配、异步能力仍要另建状态真相，就没有解决原问题。

分别记录**结构重构**（行为等价的内部调整）、**能力扩展**（新增输入/执行/观察形式）与**产品变更**（用户希望不同的行为）。后两者仍会发生；架构降低影响面，不应冻结产品。

评审只将当前阻断和相关缺陷纳入收口。新建议再合理，也不能自动成为当前前置；扩大阶段范围必须说明原范围为何不足。

## 3. 开发原则

### 3.1 先处理重复触碰的边界，不追求一次设计全部未来

提前考虑更新、异步、非文本结果、作用域和多入口，不同时建设所有工具、远程协议、视频与多 Agent 平台。

### 3.2 稳定语义，不冻结错误依赖

保留授权、身份、持久结算、幂等和未知副作用语义；类、构造参数、模块和旧实现可以替换。内部 clean-slate 不授权删除用户文件、破坏外部有效协议或既有数据承诺。

### 3.3 接口分离优先，部署保持简单

区分 Agent Core、统一工具治理和 Execution Host，默认本机类型化调用。进程/UID/Runtime 按真实隔离与生命周期决定，不因接口分离自动引入 Brain 服务、HTTP、配对或多套数据库。

### 3.4 用真实能力验证抽象

公共接口须有实际调用链、状态和失败路径；已有消费者足够时不造空生产 Provider。测试适配器证明契约，不冒充真机或外部服务。

### 3.5 统一治理，不机械统一领域

Plan/Goal/问答与文件/代码/设备保留领域归属；Skill 是内容，MCP 是协议，Plugin 是交付组织，Job 是执行工作。手动文件、配置与任务控制无需模型 Turn，手动权限不自动授予 Agent。

### 3.6 结构迁移与行为优化分开验证

先完成等价生产接线，再修改功能或策略。R2-A 与 R2-B 分开，不能同时改变模型、Prompt、预算、摘要和结构后笼统归因。

### 3.7 临时桥接有退出点，旧路径真正删除

允许短期单向适配，禁止长期双写、平行 Loop、重复 Job 真相与安装身份。每个切片列删除清单；保持可构建，不以完成一个切片替代完成已授权任务。

### 3.8 任务价值和变更成本优先

度量结果、控制/恢复和同类扩展成本，而非类、接口、工具数量。三种 Provider 分别编码是合理适配；局部能力迫使无关领域改变权威/生命周期才是结构警报。

### 3.9 不用重构掩盖事实，也不以完美为完成标准

构建、正常 Turn 结束、文档检查分别不等于功能、用户目标和架构验收。未知、未复现、未请求、跳过如实保留；美化和额外通用化不自动延长当前阶段。

### 3.10 模型主导任务，Harness 保证执行与反馈

模型决定路线、工具、策略调整和自然语言完成判断；用户决定授权；Harness 保证忠实执行、真实结果、取消与资源边界。先改善工具与反馈，再考虑硬编码流程；不为每种失败增加恢复 Driver 或通用 verifier。

确定性查询、重连与收取不转嫁人工；真正的授权、业务澄清与系统认证保留。规则分类、十条准则与反例只在 [Harness §13.6](../architecture/harness-refactor-plan.md#136-模型与-harness-的职责优化及减法准则)维护，反馈契约见 [§15.6](../architecture/harness-refactor-plan.md#156-面向模型的结果反馈事实充分接口精简)。

## 4. 本轮基础收敛的有限范围

| 边界 | 有限目标 | 不夹带的工作 |
| --- | --- | --- |
| 工具身份/治理 | 复用已交付 R1 的原子绑定与准入 | 重做 R1、全部 Core/Job/Plugin |
| Core/宿主 | 必要端口及真实生产接线，去除 UI/消息格式/Room 实体泄漏，保留事务 | 独立云 Brain、远程 Server |
| 异步观察 | 以既有 Linux Job 验证结果、身份、等待和控制 | 所有 Runtime 后台化、完整 J2 UI、子 Agent |
| 内容/扩展 | 图片、Skill、Memory、Reference 和动态来源的共同边界 | 所有 PDF/视频/检索与 Marketplace 功能 |

这些是目标范围，不是已接受的统一大任务；技术契约/依赖在 [Harness 方案](../architecture/harness-refactor-plan.md)。R3 在扩大相关安装能力前完成，不成为所有独立功能的前置。“最小”不等于只写接口、不迁移生产入口。

## 5. 用六类代表性能力验收架构

| 已有样本 | 验收问题 |
| --- | --- |
| 文件读取/修改 | 能否复用治理，不在 Loop 增加业务分支？ |
| view_image/浏览器截图 | 是否送入真实视觉内容，来源与预算可核查？ |
| Linux 后台 Job | 等待与执行是否分离，停止控制是否可达？ |
| 动态 MCP/插件更新 | 新旧契约、撤销和执行身份是否一致？ |
| Skill/Global Memory | 内容贡献是否无需手工修改多条上下文路径？ |
| Plan/Goal 与手动入口 | 是否既保留治理又不强迫所有操作经过 Runner/LLM？ |

主要验证已有能力，不同时立六个新项目。若这些变化仍迫使核心增加特殊流程，修对应边界；若满足范围则停止，不寻找假想消费者延长重构。

## 6. 本轮重构的五项停止条件

| 条件 | 所需证据 |
| --- | --- |
| 一份工具绑定事实 | 来源已迁、旧双写删除，更新/撤销/交错测试有效；R1 已有证据不重做 |
| 错误跨层依赖消除 | Core 经测试 ports 跑完整回合，真实存储事务另验 |
| 主要变化类型容纳 | §5 的适用样本满足契约 |
| 多数同类扩展局部化 | 主要修改所属领域/适配器，不重写 Turn/审批/恢复 |
| 旧路径删除且体验不退化 | 无永久双轨和无界资源；结果、取消与恢复有证据 |

这些是按获准范围使用的退出条件，不把尚未接受的所有阶段变成发行前置。达到范围内条件就转向功能；未达到只修具体缺口。类名更通用、目录更对称、竞品新模块、假想 Host 都不能单独延长阶段。

## 7. 后续推进计划：三段推进，而非无条件串行清单

### 7.1 写作时的状态与建议必须分开

R1 已由 [HXA-231](../completion-records/HXA-231.md)交付；初稿的“先完成 R1”不再是待办。当前工作只看 [status](status.md)，R2/R3/J1/J2 的接受边界看[候选索引](candidate-decisions.md)。下面是取舍方法，不覆盖实时顺序。

### 7.2 第一段：有限公共基础收敛

用户阻断问题优先，已完成基础直接复用；有证据和授权后再推进必要 Core/执行/上下文边界，以真实能力和 J1 等需求验证。共享接口有单一负责人，不让 R1 倒等全部 Core。排除全部 R2-B 实验、完整市场、远程体系和所有候选功能。

### 7.3 第二段：优先提高真实任务成功率

按失败轨迹改善信息补全、观察、等待和结果核查：已知信息不重复问，可查询信息在权限内查询，用户选项才澄清，未曝光工具可发现，真实能力缺失如实说明。模型按任务选路线，不由 Engine 强制统一步骤。Job 等待、页面条件等待与业务完成判断分开。

### 7.4 第三段：按能力族扩展，局部重构随交付进行

影响范围判断 → 必要局部整理 → 完成功能 → 验证任务。新生命周期/权限主体在相关领域裁决；不触碰迁移边界的工作可并行，依赖同一共享接口的修改先协调归属。

### 7.5 技术依赖不等于推荐排期

只在主方案 §9 维护依赖表。特别保留：J1 基础 join 不等完整 R2；观察自动注入可后接；R3 不等新 J1/J2；AUTO 与手动按钮可分交付；R2-B 与等价迁移分开。不能将这些关系再次复制成固定排期。

## 8. 候选功能的进入顺序与抉择

下表保留讨论中的接入建议，需求 ID 和接受状态只在候选索引维护。

| 方向 | 进入条件与接入边界 |
| --- | --- |
| Mobile Use 截图/观察 | 真实失败需要像素或新鲜观察；复用视觉回填，不等完整 Observation 平台 |
| PDF/Office | 先选格式和任务，区分解析与视觉；不以全格式兼容为首版目标 |
| Project Memory | 项目身份/会话关联/请求范围先明确；检索不能代替项目身份 |
| Plugin/市场 | 扩来源前完成相关 R3；包管理与最小配置修复闭环一起交付 |
| J2 | J1 与同执行身份成立；AUTO/UI 分步，不重启命令或重置预算 |
| Subagent | 有拆任务收益，独立上下文/委托/父预算；不是 ProcessJob |
| Code Mode | 证明组合收益，明确嵌套调用/取消/预算，复用治理 |
| 定时/事件 | 用户启动与运行资格明确，触发正常任务，不成为主 Loop 大脑 |
| 远程 Host/双向 A2A/多设备 | 有真实消费者再接，不预建所有网络与配对设施 |
| 向量 Memory | 先定位写入/恢复/召回/使用瓶颈；需要时作辅助索引，不推翻 Markdown 正文 |

优先减少明确用户阻碍、可验证且不依赖未定契约的工作；“功能更多”本身不是理由，无证据不编收益排名。

## 9. 每次新功能先做影响范围判断

开始前回答：属于哪个领域和用户路径；是否新增生命周期/权限主体/事实 owner；改哪些公共契约；现有接口为何不够、有什么反例；新规则是必要机制、用户/平台规则、可调策略还是模型决策。

新解析器/编码/适配直接交付；反复多处同义修改先做有界模块整理；子 Agent/远程等新增信任边界先明确契约；纯风格和无消费者抽象不阻塞功能。换成更强模型后仍必需的身份/权限/结果/资源/停止规则才优先进入核心。

## 10. 评审分级与范围控制

| 级别 | 处理 |
| --- | --- |
| 必须当前解决 | 越权、错执行、状态丢失、违反已接受契约；给触发条件和最小修复 |
| 当前范围内应解决 | 相关重复、错误依赖、测试缺口；不扩至无关领域 |
| 后续候选 | 新平台/模式、额外通用化、无收益证据的建议；不改变当前结束线 |

只有新证据证明当前目标不成立或有安全/正确性阻断，才扩大范围，并说明新退出条件。换复审模型不是重开全部讨论的理由；评审输出位置、影响、证据和验收办法。

## 11. AI 协作、切片与交接

设计/复核者稳定契约，实施者完成切片；职责不固定绑定模型产品。已授权可逆实现自行完成，跨领域变化提交最小反例再裁决。复核从实际 diff、调用者与测试开始，不仅依赖实施摘要，也不重新全仓研究。

保持“核对范围 → 回归样本 → 等价迁移 → 行为增量 → 验证 → 删除旧路径”的节奏。交接模板只在[实施指南](implementation-guide.md)维护，读取方式见 [CodeGraph 导航](context-navigation.md)；现场、设备、账号、Git 操作按[根规则](../../AGENTS.md)核对，不因交接继承授权。

## 12. 用什么证据决定优化有效

| 维度 | 观察内容 |
| --- | --- |
| 结构正确性 | 原子绑定、唯一事实源、配对、取消/恢复与事务 |
| 任务收益 | 独立结果、耗时、无效调用、人工介入和控制响应 |
| 手机资源 | 内存、IPC/构造开销、日志、线程和取消延迟 |
| 修改成本 | 无关领域改动、公共契约反复变化、临时桥接和二次重写 |
| 自主性/反馈 | 可避免的策略阻断、模型实际收到的来源/错误/不确定性、恢复成本 |

结构一致性可单独有价值；Prompt/检索/等待策略需同条件实验。正常 Turn 结束不等于目标成功，类数/工具数不是收益。BFCL 模型直连不等于 Helix 全链路，AndroidWorld 模板尝试不等于有效评测，向量低分不证明缺向量库。

固定模型/任务/输入/预算/制品/判分，分开调试与最终样本、原失败与复验、主机与设备/服务；不挑最佳重试拼分。复用 [Agent Eval](agent-eval.md)、[系统基线](harness-system-baseline.md)和[公共验收](verification-matrix.md)，不新建成绩系统或编造收益百分比。

## 14. 开始与结束一个切片时的检查表

**开始：**核对授权与变更性质；定位实际问题、领域和规则类别；写清非目标、删除清单与退出条件；选代表性反例并核对真正依赖。

**结束：**唯一入口切换、旧路径删除；结果/权限/取消/恢复按范围验证；事实实际进入下一模型请求；无多余确认也未删除必要授权/澄清；收益与未测项分开；新建议归候选，达到停止条件就交付。

**最终原则：提前设计已知变化的边界，按需交付具体功能；允许局部演进，避免普通功能反复触发整套 Harness 重设计。**
