# Helix 开发原则与后续推进策略

本文维护功能与重构的取舍方法、证据和停止条件，不维护实时排期或第二套技术契约，也不规定每个任务必须执行同一流程。当前对话确定工作范围，[status](status.md)提供实施事实；候选身份与进入条件见[候选索引](candidate-decisions.md)。

后续结构设计统一见 [Harness 第 24 节：总体架构蓝图与渐进重构路线](../architecture/harness-refactor-plan.md#24-总体架构蓝图与渐进重构路线)。完整 Turn 中立宿主已经交付；11-07 的装配、输入契约、上下文映射和 conversation-input 边界也已有有界交付，不重新排旧 R/J 迁移。后续 conversation 表现/应用层、共享 UI 与 Room 模块迁移及有界真实设备验收已收口，候选与验证限制见蓝图 24.1；不重复迁移，也不以局部通过宣布总体完成。

## 1. 本次选择：有限基础收敛，而不是两个极端

| 路线 | 取舍 |
| --- | --- |
| 先补齐全部功能再重构 | 不采用：复制已知耦合，扩大迁移与测试成本 |
| 先完成所有未来架构再补功能 | 不采用：接口没有消费者，完成线不断后移 |
| 有限公共收敛＋代表性能力验证＋局部演进 | 设计覆盖已知变化类型，实现服务实际消费者 |

按当前合理性、未来扩展成本与有证据的实践选择目标；已有类、表、默认行为没有保留优先权，但“不兼容旧内部实现”也不是必须重写、清库或删除用户数据。先判断职责、事实 owner、生命周期和依赖，再决定替换范围。真实平台/协议适配与当前受管状态不是兼容壳。

## 2. 功能新增与架构重构分别立项、分别验收

| 工作类型 | 要回答的问题 | 证据与结束线 |
| --- | --- | --- |
| 结构重构 | 哪个错误依赖、重复权威或生命周期耦合导致实际成本？ | 真实消费者迁移、禁止依赖消除、原能力及授权/取消/恢复保持；不以目录或类数量验收 |
| 能力扩展 | 新增什么输入、执行、观察或协议能力？ | 正常与失败路径、结果消费和实际平台依赖；结构基础通过不代表功能已做 |
| 产品/策略变化 | 用户希望怎样改变行为，模型策略为何更有效？ | 原主题决定与固定条件效果实验；不以架构清理暗改默认策略或权限 |
| 验证收尾 | 已有实现缺哪类证据？ | 按具体候选补主机、真实 Room、设备、服务或模型消费，不重新实施已交付主体 |

一次用户任务可以包含多类工作，但范围和结论必须分开。已确认的相关 Bug 当前修复，不能因后续已有重构任务延期；新建议也不能自动成为当前前置。

## 3. 开发原则

### 3.1 先处理重复触碰的边界，不追求一次设计全部未来

考虑来源更新、长期资源、非文本结果、作用域和多入口的变化类型；以当前消费者验证，不同时建设所有工具、远程协议、视频与多 Agent 平台。

### 3.2 稳定语义，不冻结错误依赖

保留授权、身份、持久结算、幂等和未知副作用语义；类、构造参数、模块及旧内部实现可以替换。内部 clean-slate 不授权删除用户文件、破坏有效外部协议或既有数据承诺。

### 3.3 接口分离优先，部署保持简单

延续 Android 本机模块化单体，保留唯一 Engine/Registry/Compiler；组合根显式装配，构造与启动分开。编译依赖由适配器指向契约，不因职责分离自动引入新框架、服务、HTTP、配对或多套数据库。模块目标与命名裁决只在蓝图 24.3～24.4 维护。

### 3.4 用真实能力验证抽象

公共接口须有实际调用链、状态和失败路径。已有消费者足够时不造空生产 Provider；测试适配器证明契约，不冒充真机或外部服务。

### 3.5 统一治理，不机械统一领域

Plan/Goal/问答与文件/代码/设备保留领域归属；Skill 是内容，MCP 是协议，Plugin 是交付组织，Job 是执行工作。手动文件、配置和任务控制无需模型 Turn，手动权限不自动授予 Agent。

### 3.6 结构迁移与行为优化分开验证

结构迁移保护有效能力与正确性，不要求先保留错误契约或临时双实现。模型、Prompt、检索、预算与摘要策略的改变另做固定条件实验，不能与结构同时改变后笼统归因。

### 3.7 单一目标替换，旧路径随切片删除

完整纵切迁移全部当前消费者并删除被替代内部路径，不保留生产兼容桥、别名、双写、平行 Loop 或重复 Job 事实；保持可构建。真实 Android/Room/Runtime/外部协议适配继续保留。开发数据政策不免除当前版本原子持久、恢复及用户文件边界，也不把完成一片当完整获准任务结束。

### 3.8 任务价值和变更成本优先

度量结果、控制/恢复和同类扩展成本，而非类、接口、工具数量。Provider 编码、平台后端差异可能是合理适配；局部能力迫使无关领域改变权威或生命周期才是结构警报。调用与长期资源生命周期独立，详见[扩展约束](../architecture/harness-refactor-plan.md#239-后续扩展约束)，不提前建未来引擎或通用事件总线。

### 3.9 不用重构掩盖事实，也不以完美为完成标准

构建、正常 Turn 结束、文档检查分别不等于功能、用户目标和架构验收。未知、未复现、未请求、跳过如实保留；美化和额外通用化不自动延长当前阶段。

### 3.10 模型主导任务，Harness 保证执行与反馈

模型决定路线、工具、策略调整和自然语言完成判断；用户决定授权；Harness 保证忠实执行、真实结果、取消与资源边界。确定性查询、重连与收取不转嫁人工，真正的授权、业务澄清和系统认证保留。先改善工具与反馈，不为每种失败增加恢复 Driver 或通用 verifier。

详细职责与减法准则见 [第 13.6 节](../architecture/harness-refactor-plan.md#136-模型与-harness-的职责优化及减法准则)，反馈契约见 [第 15.6 节](../architecture/harness-refactor-plan.md#156-面向模型的结果反馈事实充分接口精简)，不在本页复制。

## 5. 用代表性能力验收架构

| 已有样本 | 验收问题 |
| --- | --- |
| 文件读取/修改 | 能否复用治理，而不在 Loop 增加业务分支？ |
| 图片/浏览器截图 | 模型是否得到真实视觉内容，来源与预算可核查？ |
| 后台 Job | 等待与执行是否分离，停止是否到达原实例，容量是否等实际退出？ |
| 动态 MCP/插件更新 | 新旧契约、撤销和执行身份是否一致？ |
| Skill/Memory/知识内容 | 来源、用途、版本、资格和共同预算是否沿唯一内容编译路径？ |
| Plan/Goal 与手动入口 | 是否保留治理而不强迫所有操作经过 Runner/LLM？ |

选与本片相关的已有能力，不同时立六个项目。若同类扩展仍迫使核心增加特殊流程，修具体边界；满足范围后停止，不找假想消费者延长重构。

## 6. 重构的停止条件

- 当前范围的错误跨层依赖消除，实际消费者全部迁移，真实适配生产接线有效。
- 工具绑定、执行身份、持久事务和资源 owner 仍唯一，授权、取消、恢复与未知效果边界有适用回归。
- 相关代表性能力可局部扩展，无永久过渡层、平行事实或无界资源。
- 获准目标完整结算，未实现功能和未验范围准确列出；不以一个切片通过代替全部任务。

达到范围内条件就结束结构阶段。更通用的名称、更对称的目录、竞品新模块或假想宿主不能单独延长完成线；没有收益证据的进一步拆分停止。

## 7. 功能推进与结构工作的衔接

用户阻断问题和可复现缺陷优先；一般解析器、编码或适配增量可直接在所属领域交付。反复多处同义修改再做有界整理；新增生命周期、信任主体或执行域先在原主题明确契约。

不共享文件和接口的新功能可以并行，不冻结整个产品直到蓝图最终阶段。共同输入契约或组合根改动须协调所有权，不为并行写代码引入临时双入口。技术依赖不等于推荐排期，服务选型也只阻塞实际依赖它的切片。

## 8. 候选功能的进入条件

候选 ID、已有基础、待实现与待验证条件统一维护于[候选索引](candidate-decisions.md)，本页不再列 PDF、Project Memory、J2、TTS、定时等历史接入排序。新部署、子 Agent、模型 PTY、Code Mode 等仍须按各自条件确定范围，不随共享结构收敛自动获准。

优先减少明确用户阻碍、可验证且不依赖未定契约的工作；“功能更多”不是理由，无证据不编收益排名。

## 9. 影响范围的参考问题

复杂变更关注所属用户路径、新生命周期/权限主体/事实 owner、受影响公共契约，以及现有接口不能满足的具体反例。小而明确的变更不要求另写分析文件。

切片中发现双向内部耦合、第二账本、事务被拆坏或结构迁移混入策略变化时，按蓝图 [24.7](../architecture/harness-refactor-plan.md#247-如何根据实施事实修订计划)记录新证据、最小调整与退出条件；有效长期契约变更回原 ADR，不以计划覆盖合同。

## 10. 评审分级与范围控制

| 级别 | 处理 |
| --- | --- |
| 必须当前解决 | 越权、错执行、状态丢失、违反已接受契约；给触发条件和最小修复 |
| 当前范围内应解决 | 相关重复、错误依赖、测试缺口；不扩至无关领域 |
| 后续候选 | 新平台/模式、额外通用化、无收益证据的建议；不改变当前结束线 |

只有新证据证明当前目标不成立或有安全/正确性阻断，才扩大范围并说明新退出条件。复核从实际 diff、调用者和测试开始，输出位置、影响、证据与验收办法；换复审模型不是重开全部讨论的理由。

## 11. AI 协作、切片与交接

设计/复核者稳定契约，实施者完成切片，职责不固定绑定模型产品。已授权可逆实现自行完成，跨领域变化提交最小反例再裁决。并行修改有明确文件/接口 owner，不覆盖无关工作。

交接参考[实施指南](implementation-guide.md)，工具参考[导航](context-navigation.md)。同一任务有效授权随上下文接续保留；交接不扩大[设备、账号、数据与发布边界](../../AGENTS.md)。

## 12. 用什么证据决定优化有效

| 维度 | 观察内容 |
| --- | --- |
| 结构正确性 | 原子绑定、唯一事实源、配对、取消/恢复、事务与实际编译边界 |
| 任务收益 | 独立结果、耗时、无效调用、人工介入和控制响应 |
| 手机资源 | 内存、IPC/构造开销、日志、线程和取消延迟 |
| 修改成本 | 无关领域改动、公共契约反复变化、临时桥接和二次重写 |
| 自主性/反馈 | 可避免的策略阻断、模型实际收到的来源/错误/不确定性与恢复成本 |

结构一致性可单独有价值，但不证明更快、更省 Token 或更高任务成功率。固定模型、任务、输入、预算、制品与判分；分开调试与最终样本、原失败与复验、主机与设备/服务，不挑最佳重试拼分。BFCL 直连不等于 Helix 全链路，模板尝试不等于有效评测。

复用 [Agent Eval](agent-eval.md)、[系统基线](harness-system-baseline.md)、[公共验收](verification-matrix.md)及蓝图 [24.6](../architecture/harness-refactor-plan.md#246-验证与收益标准)。代码日常迭代用 Debug 门禁，文档-only 做文档/ADR/秘密与差异检查；设备未请求不运行，编译 AndroidTest 不算设备通过。

## 14. 交付边界

以当前获准结果及相关正确性证据判断完成；新建议不自动增加完成条件，未测试或依赖外部条件的部分如实报告。

**提前设计已知变化的边界，按需交付具体功能；允许局部演进，避免普通功能反复触发整套 Harness 重设计。**
