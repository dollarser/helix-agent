# HXA-236：J1 原执行身份的异步观察与有界等待

分类：收尾验收。2026-10-01 所有者要求依次完成剩余工作；承接 HXA-235 主机交付。按 [Harness §8 与 J1 卡](../../architecture/harness-refactor-plan.md#8-j1--j2异步观察等待与安全后台化) 复用已有 Job、Dispatcher、权限、预算和结果收取，不增加第二状态库或执行管线。

## 范围与验收要求

1. 中立原执行 Binding/Observation，模型只携带原调用句柄；宿主完整核验 session/Turn/执行/generation/来源。整个集合先校验后查询，重复项去重，fork 不继承控制权。
2. 唯一 Dispatcher 接 completion 观察，Schema/权限/审批/执行准入/输出校验/审计不旁路；Scheduler 在观察期间释放业务 worker。普通工具继续既有同步执行、有限重试和未知副作用规则。
3. 原 Job 的 retained owner 与观察资源分离；查询不得取得 reconciliation permit。查询最多两路、无排队，单个执行最多一个物理 query；逻辑超时不释放未退出 Binder 的容量，不无限补线程。停止原任务仍保留独立控制通道。
4. 有界 status/await，ANY/ALL、已终态、等待到期、来源不可用、权限撤销、需核查、资源饱和分别返回。最多 16 个观察者、每会话 4 个、每次 8 句柄、15 秒内部等待；外层 deadline 预留 250ms，单 query 2 秒观察上限。后续调整仅能由宿主配置降低，模型不能扩大原 Job 的时间/费用额度。
5. 接实际 Linux Job 查询、正常 Agent 工具曝光及按原顺序回填；收取继续原变更/授权链。界面停止等待与停止执行不同，用户控制不伪造模型调用；不能只实现纯接口即宣布 J1 完成。

## 验证入口

先 framework 纯 JVM 场景和真实 Dispatcher/Scheduler 联合 fixture，后双渠道 App 与 Runtime 编译/测试。覆盖错归属、重复、取消、完成竞争、读取权限撤销、阻塞 IPC 后容量保持、晚到回包、部分失败、输出校验、一次审计、发布失败和普通工具回归。主机共享 slot，源码/格式/静态门禁和双渠道 APK/AndroidTest 编译；设备与真实模型本轮 not requested，不由 fixture 替代。

当日核对 [Codex App Server](https://developers.openai.com/codex/app-server) 的持久执行身份、流式输出与进程控制，[Claude 后台 Bash](https://code.claude.com/docs/en/interactive-mode#background-bash-commands) 的任务句柄与查看/取消分离。采用职责原则，不照搬桌面无限执行或后台超时策略，不复制代码。Helix 的原预算、Android 进程事实和用户授权始终保留。
