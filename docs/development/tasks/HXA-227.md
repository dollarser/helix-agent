# HXA-227：统一轨迹级 Agent Eval 与失败归因

分类：已规划；建议在 HXA-226 稳定后作为下一条能力工程主线，也可独立完成纯 eval schema/汇总工具。不是产品功能，不修改 Agent 策略来“刷分”。

## 背景

Helix 已有多套真实 fixed evaluation：Goal、File、Browser、Plan、MCP、Skill、A2A、Accessibility、Javascript、Root、Provider 等，并已输出 per-case JSON 与 provider/model/device/dataset/tool-version 等 evidence。当前缺口不是“没有 eval”，而是：

- suite 间 evidence 字段不统一；
- PASS/FAIL 多是各任务局部断言，没有统一 trajectory metrics；
- 很难横向回答 Harness 改动究竟改善了 first-pass、recovery、tool selection 还是只增加了尝试次数；
- Queue/Steer/review/successor Turn/compaction 等 HXA-220/223 核心能力缺少统一长轨迹评分口径。

## 范围与验收要求

本任务只统一现有 eval evidence、trajectory metrics、失败归因和汇总工具，并补少量 Core Harness 固定轨迹 case；不改变生产 AgentLoop 策略，不收集生产用户遥测。验收要求是相同任务可复跑、证据可追溯、fixture/fake/real-provider 可区分、A/B 可比较。

## 原则

1. 复用现有 fixed eval 与真实 Room/audit facts，不建第二套 Agent runtime。
2. 原始 per-case evidence 保留；统一层只做规范化、派生指标和失败归因。
3. “模型说完成”不算成功，必须有 deterministic verifier / durable fact / external assertion。
4. fixture、fake provider、真实 provider 结果明确分层，不混成同一总体成功率。
5. 评测代码默认 developer/test surface；不把用户生产会话上传成遥测。
6. 不要求外部付费账号才能完成 schema/aggregator；真实 Provider A/B 作为有条件证据。

## A — Eval evidence schema v1

为现有 suite 定义统一 envelope，至少包括：

```text
identity
  suite / caseId / datasetSha / promptSha
  gitCommit / app flavor / API / device
  provider / exact model / protocol / provider version

outcome
  verifiedResult = PASS | FAIL | BLOCKED | INVALID
  verifier facts / artifact hashes
  failureCategory

trajectory
  turns / successorTurns
  modelCalls / toolCalls
  invalidToolCalls
  repeatedFailures
  approvalsRequired / approvalsAnswered
  humanInterventions
  unknownEffects / reviewsResolved
  compactions / recoveryEvents
  firstPassSucceeded

cost
  wallMillis
  inputTokens / outputTokens / totalTokens where known
  provider/network/local resource fields only when measured
```

未知值写 `null/unknown`，不从 model name 猜 capability、成本或资源。

## B — Failure taxonomy

统一但保持可追溯：

```text
MODEL_REASONING
TOOL_SELECTION
TOOL_ARGUMENTS
TOOL_EXECUTION
PERMISSION_OR_APPROVAL
ENVIRONMENT
CONTEXT_LOSS
RECOVERY
UNKNOWN_EFFECT
BUDGET
PROVIDER_PROTOCOL
VERIFIER
HARNESS_INVARIANT
```

一个 case 可以有 primary + contributing causes；不能用第一个异常字符串自动决定唯一根因。

## C — Core trajectory suite

在现有 domain suites 之外，新增一组小而固定的 Harness trajectory cases，直接验证当前核心架构：

1. Queue：运行中输入排队，terminal 后用户输入优先于 Goal continuation；
2. Steer：final-answer 竞争窗口不丢输入；
3. Cancel：durable CANCELLING 后 late success/failure 不能覆盖取消结论；
4. Review：UNKNOWN effect → NEEDS_REVIEW → immutable review → successor Turn，无 effect replay；
5. Process death：旧 Turn INTERRUPTED，新 Turn 使用 bounded RecoverySummary；
6. Goal continuation：safe Turn boundary + no queued user input 才自动继续；
7. Compaction：关键约束/未解决风险在 compaction 后保持；
8. Tool failure recovery：错误信息驱动换路，不重复同一无效调用。

能 host/fixture deterministic 验证的先做；需要真实模型的 case 再通过现有 evaluation provider port 运行。

## D — Aggregator / report

新增仓库内脚本读取所有标准 envelope，输出：

- JSON summary（机器比较）；
- Markdown report（人工 review）；
- per-suite + per-model + per-protocol breakdown；
- task success / first-pass / recovery-adjusted success；
- invalid-tool / repeated-failure / human-intervention / UNKNOWN-review incidence；
- latency/token 仅在真实有数据时统计；
- baseline vs candidate delta，要求 dataset/config hash 一致才允许直接比较。

不输出一个模糊“Agent 总分”，避免把安全审批次数、任务难度和模型能力混成单一排名。

## E — 用法

HXA-227 完成后，后续 Harness / Prompt / tool schema / Provider routing 优化必须优先使用同任务 A/B：

```text
same dataset
same verifier
same tool surface
same provider/model when isolating Harness
        ↓
baseline trajectory
        ↓
one isolated change
        ↓
candidate trajectory
        ↓
metric delta + failure attribution
```

## 验证入口

- 现有 fixed eval 至少 3 个代表 suite 能产出统一 envelope，且不破坏旧原始 evidence；
- core trajectory suite 有 deterministic verifier；
- aggregator 对缺字段/未知字段 fail-soft，对 schema/version/hash mismatch fail closed；
- 报告可以明确区分 fixture/fake/real-provider；
- 没有生产 telemetry、没有上传用户内容；
- host/static/AndroidTest compile/source/diff gates 通过；设备执行仍由所有者显式请求。
