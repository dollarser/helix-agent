# HXA-222：On-device Local Model Provider

分类：已规划，暂缓实施。长期语义以 [ADR-PROVIDER-001](../../adr/provider/001-models-and-connection.md) 与 [ADR-AGENT-001](../../adr/agent/001-turn-coordination.md) 为准。本任务已获本地模型“一等 Provider、可驱动完整 Agent loop”的设计授权。HXA-220/221/223 已完成 Core clean-slate 收口，但当前产品优先级仍不启动本地模型生产代码、native runtime 或模型资产开发；本文件只冻结未来实现所需的 Provider contract。

## 范围与验收要求

目标是让设备内模型与远端 API、自建推理服务、订阅账号 Provider 使用同一 `ModelProvider`、`ModelRequest` / `ModelEvent`、capability probe、AgentLoop、Dispatcher/Policy/Approval/Audit 体系，同时把当前“Provider = endpoint + key”的隐含假设拆成正交维度。

### 产品入口与底层维度不是一回事

用户侧可以按三类理解和组织 Provider：

```text
API / Self-hosted
  OpenAI / Anthropic / OpenRouter / custom compatible
  Ollama / SGLang / vLLM / enterprise endpoint

Subscription / Managed account
  Codex / Claude 等由适配器持有账号与刷新状态的 Provider

On-device
  Helix 直接持有模型资产并通过 native/local runtime 推理
```

但底层**禁止**使用一个三值 `ProviderKind = API | SUBSCRIPTION | LOCAL` 同时表达所有语义。至少拆成四个正交维度：

1. **Provisioning / ownership**：配置和凭据由谁管理；
2. **Transport**：请求是通过 network endpoint，还是 Helix 直接调用设备内 runtime；
3. **Residence**：模型数据实际去向；
4. **Auth source**：无认证、SecretStore 凭据，还是 managed account/token。

建议 contract：

```kotlin
enum class ProviderProvisioningKind {
    USER_CONFIGURED,
    MANAGED_ACCOUNT,
    ON_DEVICE_ASSET,
}

sealed interface ProviderTransport {
    data class Network(
        val protocol: ProviderProtocol,
        val endpoint: NormalizedEndpoint,
    ) : ProviderTransport

    data object OnDeviceLocal : ProviderTransport
}

sealed interface ProviderAuth {
    data object None : ProviderAuth
    data class Secret(val alias: SecretAlias) : ProviderAuth
    data object ManagedAccount : ProviderAuth
}
```

当前目标组合矩阵：

| 产品 UI 分组 | Provisioning | Transport | Auth | Residence |
| --- | --- | --- | --- | --- |
| API / Self-hosted | `USER_CONFIGURED` | `Network` | `None` / `Secret` | 从 endpoint 派生 |
| Subscription / Managed account | `MANAGED_ACCOUNT` | `Network` | `ManagedAccount` | 从 managed endpoint 派生 |
| On-device | `ON_DEVICE_ASSET` | `OnDeviceLocal` | `None` | `ON_DEVICE_LOCAL` |

例如 Ollama/SGLang/vLLM 即使运行在用户自己的电脑或手机上，只要 Helix 通过 endpoint 请求，仍落在第一行；它们不是第三行。

`ProviderResidence` 继续是数据去向事实，并新增与 `ON_DEVICE_LOOPBACK` 明确不同的 `ON_DEVICE_LOCAL`：

```text
Network(127.0.0.1 / ::1) → ON_DEVICE_LOOPBACK
Network(private LAN)       → USER_AUTHORIZED_LAN
Network(public origin)     → PUBLIC_CLOUD / CUSTOM_REMOTE_UNKNOWN
OnDeviceLocal              → ON_DEVICE_LOCAL
```

**Ollama / SGLang / vLLM 永远按实际 endpoint 分类。** 只要 Helix 通过 HTTP/HTTPS 调它们，它们就是 `Network` transport；即使 endpoint 是 `127.0.0.1`，也只是 `ON_DEVICE_LOOPBACK`，不是 HXA-222 的 `ON_DEVICE_LOCAL`。同一 Ollama 模板指向 LAN 或公网时 residence 必须随 endpoint 改变。品牌名、部署者自称“本地”或是否需要 API key 都不能改变这一事实。

必须满足：

- 设备内 Provider 有显式、可验证的 `ON_DEVICE_LOCAL` residence；`ON_DEVICE_LOOPBACK` 仍属于 network transport；
- 设备内 Provider 不伪造 loopback HTTP endpoint，不要求 network endpoint、wire protocol 或网络 cleartext/egress repair；
- endpoint / wire protocol 只属于 `Network` transport；`OnDeviceLocal` 类型不能构造出“假 endpoint + 假 protocol”；
- provisioning 不决定 transport：`MANAGED_ACCOUNT` 通常仍是 `Network`；`USER_CONFIGURED` 可以是公网/LAN/loopback network；只有 `ON_DEVICE_ASSET` 当前允许 `OnDeviceLocal`；
- auth 不决定 residence：Ollama/SGLang/vLLM 可为 `ProviderAuth.None` 或 `Secret`，仍按 endpoint 判定数据去向；
- 本地 Provider 的工具能力只由真实 capability/eval 决定，不因运行位置被硬编码禁用；
- local backend 的错误、取消、stream terminal 与远端 Provider 使用同一归一化合同；
- 模型资产在 app 私有存储，完整性、配额、用户触发下载与删除必须可验证；
- native/runtime 崩溃或 OOM 不能伪造成成功，不能绕过 TurnEngine lifecycle；
- 不新增第二套 Agent loop、权限或 Tool dispatcher。

当前预留原则：现有功能不得继续把 `ModelProvider`、TurnEngine、capability/eval 或权限体系绑死到“必须有 HTTP endpoint / SecretAlias”的假设；同时也不得因为未来支持 `OnDeviceLocal` 就把现有 Ollama/SGLang/vLLM 从 network safety/egress 分类中移走。HXA-222 未启动前只允许必要的通用接口兼容，不以此任务名义提前开发 native inference。

## 启动条件

Core clean-slate 重构已在 `a015222d` 后达到稳定 checkpoint，因此 HXA-222 的**架构前置已满足**；当前暂缓仅是产品排期决定。真正启动时仍必须重新审查 ProviderConfig/Descriptor、Room `provider_configs`、ProviderFactory、managed subscription、egress/cleartext、model metadata cache 与 UI caller graph，确认没有在 HXA-226 等后续工作中重新引入 endpoint-only 假设。

## L1 — Provider transport contract（强模型）

把当前 `ProviderConfig(protocol, endpoint, secretAlias, ...)` 的 endpoint/key 必填契约拆开，并同时收敛 subscription 的 `managedExternally: Boolean` 临时语义：

- 新增类型化 `ProviderProvisioningKind`、`ProviderTransport`、`ProviderAuth`；不要再用 `managedExternally` 布尔值承担来源、编辑权和认证语义；
- `ProviderDescriptor` / `ProviderConfig` 直接持有 provisioning + transport + auth，并从 transport 派生 residence；
- network transport 持有 `ProviderProtocol + NormalizedEndpoint`；`OnDeviceLocal` 不持有 protocol/endpoint；
- `ProviderResidence` 新增 `ON_DEVICE_LOCAL`，不得复用现有 `ON_DEVICE_LOOPBACK`；
- `provider_configs` clean-slate baseline 在真正实施时可直接调整当前 v1 schema：至少持久化 provisioning kind、transport kind、auth kind；network protocol/endpoint 与 secret alias 按组合 nullable，并由 repository 严格验证，不新增历史 migration 兼容链；
- 当前允许组合至少为：
  - `USER_CONFIGURED + Network + None/Secret`；
  - `MANAGED_ACCOUNT + Network + ManagedAccount`；
  - `ON_DEVICE_ASSET + OnDeviceLocal + None`；
  其他组合默认 fail closed，未来有真实需求再扩展；
- network adapters 只接 `Network`；local backend 只接 `OnDeviceLocal`；managed subscription 仍可复用现有 network protocol adapter，但 endpoint/account editability 由 provisioning 决定；
- `ProviderFactory` extension seam 支持 local backend，不通过 `WireClient`；
- cache/binding identity 从裸 `endpoint.full` 假设改为 transport identity/cache key：network 至少包含 protocol + 规范 endpoint；on-device 使用稳定非 URL identity，并结合 provider/model/asset identity 做上层 metadata key，禁止伪造 `local://`；
- cleartext、network egress、endpoint binding prune 仅对 `Network` 执行；on-device inference 不因模型输入敏感而触发“网络出网”确认，但随后模型发起的 ToolCall 仍照常经过权限/egress/UNKNOWN-effect 体系。

## L2 — Local provider + fake backend contract（强模型）

新增 local provider 模块/API seam：

- backend 提供 exact model catalog、metadata/capabilities、validate、stream；
- `LocalModelProvider` 只消费 `ON_DEVICE_ASSET + OnDeviceLocal + None` 的合法配置，把 backend 事件归一成现有 `ModelEvent`；
- host fake backend 覆盖 text、reasoning、tool call、usage、terminal、cancel/error；
- 用现有 AgentLoop/Provider probe 测试证明 local provider 可以驱动完整 loop，不新增特殊 Agent 分支。

## L3 — Local inference runtime（强模型 + native 风险切片）

### L3.1 架构裁决：llama.cpp 是 Runtime backend，不是内置 inference server

首版目标固定为：

```text
App / Agent process
    │
    │ ModelProvider contract
    ▼
LocalModelProvider
    │
    │ LocalInferenceRuntimePort
    ▼
LocalInferenceRuntimeClient
    │
    │ Binder / typed IPC
    ▼
:model-runtime private process
    │
    ▼
LlamaCppBackend
    │ JNI
    ▼
llama.cpp
    │
    ▼
verified GGUF asset
```

核心裁决：

- **llama.cpp 在 Helix 内置路径中是 `LocalInferenceRuntime` 的 backend / execution engine，不是 HTTP inference server。**
- 内置 `OnDeviceLocal` 不启动 TCP 端口、不通过 OkHttp/Retrofit、不暴露 OpenAI-compatible localhost API，也不使用 `local://`/`127.0.0.1` 伪造 Provider endpoint。
- `llama-server` 若未来作为用户自行启动的服务被 Helix 连接，则与 Ollama/SGLang/vLLM 一样归 `USER_CONFIGURED + Network`，按实际 endpoint 分类；它不是 HXA-222 内置 local runtime 的实现路径。
- Provider 层只依赖稳定 `LocalInferenceRuntimePort`，不能 import llama.cpp/JNI 类型；未来替换为 NPU/vendor SDK/private service 不改变 `LocalModelProvider` 或 AgentLoop。

### L3.2 进程模型：首选 private process，而非主进程直接长期 JNI

首版推荐 `:model-runtime` Android private process：

- 主进程拥有 Session/Turn/AgentLoop、Provider selection、Room durable truth、权限与 UI；
- `:model-runtime` 只拥有本地推理执行资源：native library、已加载 model/context、当前 generation job 与运行时资源统计；
- runtime process **不是 durable truth**，不能保存独立 Session/Turn/Goal 状态，进程重启后只从主进程重新接收模型资产与新 generation 请求；
- 主进程不得把 runtime PID/Binder identity 当 Provider/Session/Turn identity；runtime instance 只用于诊断与当前执行 ownership；
- runtime 进程崩溃、Binder death、native abort 或 OOM 必须被归一化为当前 ModelCall 的失败/中断事实，由现有 TurnEngine settlement 处理；不得在 runtime 内自行恢复旧 Turn 或自动重放工具副作用；
- 如果未来实测表明同进程 JNI 在某类设备更优，只能作为经过 eval 的部署优化；不能因此改变 `OnDeviceLocal` Provider 语义。

选择 private process 的原因不是把本地模型做成“微服务”，而是把 native crash、大内存模型和主 UI/Agent 生命周期隔离；IPC 是应用内部执行边界，不是 network transport。

### L3.3 Runtime port

先实现 framework-free、可 fake 的 runtime port，再接 JNI：

```kotlin
interface LocalInferenceRuntimePort {
    suspend fun inspect(asset: ModelAssetRef): LocalModelInspection
    suspend fun load(request: LocalModelLoadRequest): LoadedLocalModel
    fun generate(request: LocalGenerationRequest): Flow<LocalInferenceEvent>
    suspend fun cancel(generationId: String): LocalCancelResult
    suspend fun unload(modelHandle: String): LocalUnloadResult
    suspend fun runtimeStatus(): LocalRuntimeStatus
}
```

要求：

- `LocalGenerationRequest` 来自已验证的 `ModelRequest` 映射，但 IPC DTO 与 public Provider wire protocol 解耦；不得把 OpenAI/Anthropic JSON 当内部 runtime API；
- `LocalInferenceEvent` 至少覆盖 text/reasoning/tool-call/usage/terminal/error，并由 `LocalModelProvider` 统一转换为现有 `ModelEvent`；
- generation 使用稳定 `generationId`，model 使用 process-local `modelHandle`；二者都不是 durable Turn identity；
- IPC 回调/Flow 必须有有界背压与明确终止；Binder 断开不能留下“主进程认为已取消、native 仍持续运行”的未知 owner；
- 大对象不得无界塞入 Binder transaction；首版 token/event 流使用小型 typed chunks，模型资产通过可信 asset identity/只读文件描述符或受控 app-private path handoff，具体方式在实现切片中按 Android 限制验证。

### L3.4 Load / unload / residency

首版资源策略保持简单、可证明：

- arm64-v8a CPU baseline；GPU/NPU 是后续优化，不作为首版前置；
- 首版允许 **一个 runtime process 内一个 active loaded model baseline**；只有真实设备 eval 证明收益且内存可控后才扩展多模型常驻；
- exact asset hash + inference config 相同才允许复用已加载 model；模型 ID/display name 相同不能替代资产身份；
- 切换模型时 load/unload 必须串行化，旧 model 未确认释放前不得假定内存已回收；
- load 失败、mmap/alloc 失败、模型不兼容、GGUF 校验失败均结构化上报，不能降级为 `TRANSPORT`/HTTP 错误；
- Android memory pressure 下允许 runtime 主动卸载 idle model，但不能在 active generation 中静默卸载；主进程 UI 只能展示可验证的 loaded/loading/unloaded/failed 状态。

### L3.5 Cancel、timeout 与 executor exit

沿用 Core Engine 已冻结的不变量：**cancel/timeout != executor exited**。

- TurnEngine/Provider cancel 先请求 runtime cancel；
- runtime 必须区分 `REQUESTED / ACKNOWLEDGED / EXITED`（或等价语义），只有 generation 确认退出后才释放 process-local execution owner；
- Binder call 返回、Flow collector cancel 或客户端断开都不能自动解释为 native generation 已停止；
- cancel 后若 runtime 无法证明 executor exit，应终止/重建 runtime process 或进入明确的 runtime-unknown/failure 处理，而不是启动同一模型的新并发 generation；
- 本地推理本身没有外部 Tool side effect，因此 runtime generation 可失败重建；但 generation 之前/之后由 AgentLoop 发起的 ToolCall 仍受现有 effect truth 与 review 规则约束，不能因 runtime 重启重放。

### L3.6 Crash / OOM / watchdog

本地模型增加的是 native 资源故障面，不应伪装成 network failure：

- 至少区分 `MODEL_LOAD_FAILED`、`MODEL_ASSET_INVALID`、`LOCAL_RUNTIME_CRASHED`、`LOCAL_RUNTIME_OOM`、`LOCAL_GENERATION_FAILED`、`LOCAL_CANCEL_TIMEOUT`（最终 error taxonomy 可在实现时映射到现有 `ModelErrorCode` 或新增受控值）；
- private process death 由 Binder death/进程观察明确检测；当前 ModelCall fail closed，主进程保持 Room durable truth；
- 不做 same-generation resurrection：runtime 重启后下一次推理是新的 ModelCall/请求边界，是否由 successor Turn 继续由现有 Agent lifecycle 决定；
- watchdog 只判断 runtime 无响应/资源失控，不判断“模型思考太久”；generation timeout 使用显式预算，不能以 UI 无 token delta 直接杀死合法 reasoning；
- native crash/OOM 诊断不得记录 prompt、secret、完整用户内容或模型内存 dump。

### L3.7 llama.cpp backend contract

`LlamaCppBackend` 只负责把 runtime port 映射到 llama.cpp：

- GGUF load、tokenization、context/KV cache、sampling、generation、usage 统计；
- grammar/JSON/schema 约束属于生成辅助，不构成 ToolCall 已验证事实；最终工具名/参数仍经过现有 schema validator 与 Dispatcher；
- reasoning/content/tool-call 的具体解析必须有模型模板/metadata 证据，不能由“Qwen/Llama/DeepSeek”名字猜格式；
- context window、KV memory、threads、batch size 等运行参数由设备资源 + exact model metadata + eval 决定，默认值有界；
- backend 不直接访问 Room、Tool Dispatcher、Capability/Permission store、Chat UI 或 network Provider 配置。

若 native 依赖/构建体积需要独立风险切片，顺序固定为：**runtime port + fake runtime → private-process IPC → llama.cpp JNI/backend → real asset/device eval**。不得用 loopback HTTP server 作为中间“完成版”。

## L4 — Model asset lifecycle

模型不进入 APK，资产生命周期属于主进程/受控 store，llama.cpp runtime 只消费已验证资产引用：

- 用户显式选择/下载；
- app-private model store；
- `ModelAssetId + SHA-256 + size + format/metadata` 构成可信资产身份，display model name 不作为执行身份；
- resumable transfer、SHA-256、临时文件 + 原子 publish；只有 VERIFIED 资产可交给 runtime load；
- runtime load 优先接收 `ModelAssetRef` / read-only FD / 受控 app-private canonical path，不接受模型输出或任意 Tool 参数拼接出的文件路径；
- 可见大小/下载状态/verification/load 状态/删除；删除 active-loaded asset 时必须先完成 runtime unload 或明确拒绝；
- quota/空间不足/部分下载/校验失败 fail closed；失败残片有界清理，不把未校验文件提升为可用模型；
- 不把 Workspace/SAF 文件默认当可执行模型资产；用户主动导入模型若未来支持，也必须先复制/验证进入 model store，而不是直接 mmap 任意外部路径。

## L5 — UI / probe / full-loop validation

- Provider 管理 UI 产品层分组为 `API / Self-hosted`、`Subscription / Managed account`、`On-device`，但三组不能反向成为 AgentLoop 分支；
- `API / Self-hosted` 中 Ollama/SGLang/vLLM 显示 endpoint 实际 residence；loopback/LAN/public 语义不同；
- `Subscription` 显示账号/认证状态和只读 managed endpoint 信息，不冒充 API-key editable row；
- `On-device` 显示模型资产、设备内 residence、capabilities 与资源信息，不显示 endpoint/API key/network cleartext repair；
- capability probe / model metadata 与网络 Provider 使用同一 UI 语义；
- fake backend/runtime host tests 覆盖完整 Agent loop 工具调用、cancel、runtime death、load/unload 与恢复边界；
- AndroidTest compile 覆盖 Binder contract、runtime process manifest/visibility、asset handoff 与 death-recipient 代码路径；
- 真实设备验证时必须分别记录：首次 load、warm reuse、generation latency/token rate、峰值 RSS/PSS、OOM/crash、取消到 executor exit、模型 unload 后内存回收、温升/持续运行；
- 真实 native 性能/热/内存/模型任务 eval 只有 owner 明确要求设备验证时执行，不能用 host fake 或 APK 编译冒充真实 inference 通过。

## L6 — 实施切片与执行者分工

为避免 native/IPC 与 Provider contract 一次性耦合，实际开发按以下顺序：

1. **L1 Provider contract（强模型）**：provisioning/transport/auth/residence + Room v1 schema + caller migration；网络 Provider 行为保持不变。
2. **L2 fake LocalModelProvider（强模型）**：endpoint-free config + fake `LocalInferenceRuntimePort` 驱动完整 AgentLoop；先证明架构，不接 native。
3. **L3a private-process IPC（强模型）**：定义 typed Binder/client/service、death/cancel/owner contract；fake runtime process 验证 crash/cancel/load/unload。
4. **L3b llama.cpp JNI/backend（强模型负责接口与 review，小模型可做机械 JNI/Gradle 接线）**：只实现 runtime backend，不碰 AgentLoop/权限。
5. **L4 asset store（强模型定义 integrity/ownership，小模型可做下载/UI/机械测试）**。
6. **L5 UI/probe/eval**：三组 Provider 管理、真实模型 metadata/capability、资源状态与 full-loop eval。

任一切片失败不得临时改成 localhost server 绕过既定 runtime contract；如果 private-process IPC 被真实 Android/native 证据证明不可行，再回到 ADR-PROVIDER-001 `Reconsider when` 重新裁决部署边界。
