# HXA-199：终端专项集成与交付

分类：集成验收。当前是否执行见[实施状态](../status.md)。

前置条件：194～198；同版本共享证据。

本次复核：保留终端性能、后台真机和恢复集合，不与206重复建设另一套执行器或全产品验收。

核对依据：[源码或有效证据](../../architecture/terminal.md)。本轮只审查，不新增测试通过或完成声明。

## 范围与验收要求

- 允许：跨阶段缺陷修复、标准 tests/scripts/docs、发行边界检查；不得顺带改主题、Provider、Goal 语义或历史许可证。
- 场景：查看固定测试结果；长命令实时日志与停止；异步结束后回收；手动 REPL；双会话；切页重连；运行中杀主/Runtime；consumer 排除；旧版本数据库/结果迁移。
- 运行 G1～G4 及所有本包设备类，补 owned-runner 的 `scripts/verify-terminal-runtime.py`（新增）和此矩阵入口；它必须校验失败/跳过计数，保存设备 owner/关闭记录。
- 专项成功率使用“已通过场景/执行场景”，标明设备/API与跳过原因；记录日志首包、取消延迟、冷启动、包体增量和资源变化，不用测试数量替代产品成功率。
- 更新架构当前章节、工具文档、状态、HXA 完成记录和用户帮助。全量门禁失败、关键物理设备项未验或新 ADR 未接受时不得标记本包完成。允许验证通过的独立切片本地提交，遵循 [统一提交规则](../implementation-guide.md)；不自动推送、合并或发布。

197 单终端的主进程/Runtime 死亡、实际 reboot 对账及 1 MiB 输出压力已交付，按最终制品范围复用其证据。本任务继续验证 30 分钟 detach idle、默认两小时完整租期、OEM/Doze/热压/长稳及真实 16 KiB 设备，不将 197 的短租期或静态对齐视为这些项目通过。

## 后续执行计划（2026-09-20，仅规划）

启动条件：198 的双会话验收完成，并核对 194～198 在同一待验提交上的影响范围。196 真机 HOME/锁屏/Doze 仍缺证据，应首先补验并共享原始记录；不得用 197 的重启旅程替代后台 Job 真机验收。本轮不创建验收 runner 或运行长时任务。

1. **确定制品和证据清单**：固定一个提交、双 flavor 主/测试 APK SHA 与 RootFS 身份。逐项登记固定结果、日志/停止、后台回收、单终端 REPL、双会话、重连、进程死亡、升级和 consumer 排除；复用同版本且未受影响的原始证据，变更路径重新执行。
2. **汇总入口**：实现计划中的 `scripts/verify-terminal-runtime.py`，复用已有独占模拟器基础，不另造执行引擎。入口检查测试类存在、非零执行、失败与跳过，输出场景结果、命令、时间、制品身份、owner/closed。与 206 共享证据结构，两个入口只负责各自范围。新建输出目录，设备 finally 清理仅针对本次 owner。
3. **自动化矩阵与升级**：API29/36 运行 G1～G4 和新增全部设备类。选定可追溯旧 APK/数据库，先写固定结果和会话，再覆盖安装新 APK，核对读取、恢复及无重放；记录实际旧/新 SHA，不能用清库安装替代升级。验证 consumer release 的组件、dex/native 排除。
4. **真机及实际时长**：分开运行 30 分钟 detach idle、默认两小时租期和运行中到期；记录开始/截止/终止及 PID 证明，不能缩短配置冒充。补 HOME、锁屏、Doze、OEM 后台限制、热压/长稳与真实 16 KiB 设备；保存机型/API/页大小、电源及温度条件。设备不可得时明确缺口，保留任务未完成。
5. **产品统计与收口**：按固定场景记录成功/执行/跳过、日志首包、取消延迟、冷启动、包体与资源变化，报告采样方式和异常。局部缺陷回到所属模块修复后重验影响矩阵；更新终端帮助/架构/完成记录。关键真机项缺失、全量门禁失败时不创建完成声明。

终端专项不扩展到 Provider、主题或全产品工作流；真实账号不是 synthetic fixture 的替代品或默认依赖。只有相关账号用例才使用显式 opt-in profile，缺失跳过、格式错误失败。
