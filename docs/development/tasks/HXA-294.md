## 范围与验收要求

1. 冻结一个确切代码/制品及测试环境，汇总从 286 契约、287/288 最小纵切/核心及各领域适配持续积累的证据，再做整体集成回归；取消迟到、崩溃窗口、输出完整性和插件缺失不能在本任务才首次验证。确认每条生产路径只剩一套 owner/实现，外部协议适配与内部兼容残留区别记录。
2. 覆盖完整 Turn、文件检索、Browser、Mobile Use、PRoot Job、文档/视觉、Skill/MCP Resources 与 Memory 的实际接线；独立核验业务结果，不以 Turn 正常结束等同任务成功。
3. 回归审批/撤权、在途停止、真实资源退出、主进程/Runtime 死亡、UNKNOWN 不重放和结果恢复；结构重构与新增能力分别记账，保留首次失败及修复证据。
4. 清理被替换接口的历史测试/临时脚本和重复夹具，保留有效失败反例、稳定模板与调试经验；删除不再使用的代码与产物，不用固定文件/测试/工具计数衡量完成。
5. 旧黑屏及 Notion/Linear结案不重开；提前结束专项和长稳保持暂停。新的长稳须单独确认当次设备/模型/时长/任务/停止条件，不能从本任务排期推导执行授权。正式发行仍由签名、包名、渠道等独立输入控制。

6. 按 [方案 §23.9](../../architecture/harness-refactor-plan.md#239-后续扩展约束) 核对多运行隔离、长期资源引用、执行阶段及内容版本反例，确认 286～288 未固化未来扩展障碍。区分已有行为通过、设计审查和未来功能未实现，不要求以提前上线四类功能换取“扩展性通过”。

## 验证入口

- 汇总 287/293 的运行隔离、288 的资源生命周期、286～288 的治理顺序以及 289/293 的陈旧内容测试证据；检查全局可变当前运行、单次调用拥有所有资源、产品数量写入共享类型等反例。复用既有夹具，不新增空框架或固定计数门禁。

- 主机按影响运行契约/集成回归与双渠道制品检查；设备和真实模型仅在该阶段明确授权后执行，编译、短验、长稳和账号矩阵分别结论。
- 最终报告逐项给出冻结身份、复现/结果、影响、失败处理和未测边界。重构完成不要求所有未来平台、全 OEM 或发行条件满足。
- 开始实施时定位现有测试入口并按改动选择回归；目标契约可替换旧实现镜像断言，权限、持久原子性、取消、真实退出与恢复反例不得丢失。设备/服务须核对当次授权与配置，本轮未执行。
