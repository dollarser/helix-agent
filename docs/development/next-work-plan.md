## 分工与资源

206 已完成；后续由熟悉持久结算和 Android 生命周期的执行者负责 199 物理专项的条件确认、跨层失败分析与最终复核。公共 runner、授权 resolver、Runtime admission 和共享 UI 必须先明确单一文件所有者，避免两个任务同时改写。

独立工作树允许并行编辑，不代表可以抢占同一构建和设备资源。重型 Gradle/设备任务通过现有 host slot 串行；每次运行创建并清理自有模拟器。206 与 198 的证据分别绑定实际提交和制品；合并后重跑受影响路径，不能拼接不同源码版本的通过数字冒充整体通过。

每个任务按“可验收切片 → 本地证据 → 复核 → 合并后 CI”交付。任务开始前解决强制基线失败；普通 CI 的 Debug 档不能替代 HXA 要求的 `./scripts/check-all.sh --all` 和设备门禁。详见 [CI 分层](ci.md)。

## 保持应用能力与 Agent 能力分离

搜索、主题、能力准备、终端管理、导出和审计查看保留为应用能力，不为了可见性额外注册 Agent 工具。通用任务优先使用既有工具、MCP、Connector、Skill；206 要验证这些路径不会无故启动模型、Goal 或扩大 scope。

不在本批增加子 Agent、通用工作流引擎、场景专用规划器、自动重放 shell 或远程执行平台。若现有能力确有重复失败，先用旅程证据确定缺口，再提出最小修复或独立 ADR，而不是按其他 Agent 的功能清单补齐。
