## 报告遗漏的优先问题

### R1：新会话默认权限会影响没有显式配置的旧会话

证据：`SessionPermissionService.configFor` 使用 `configs.forSession(sessionId) ?: configs.appDefault()`；`SessionPermissionConfigRepository` 缺行时没有固定快照；`ChatService` 普通创建、草稿落库及共享草稿路径未写入会话权限快照。`resetToDefault` 删除配置，也重新引入动态继承。

因此，在只读默认下创建会话 A、未单独编辑其权限，再把“新会话默认”改为完全免确认，A 的后续解析也会得到新默认。这违反 [ADR-PERMISSIONS-001](../../adr/permissions/001-session-authorization.md)“默认变更只影响以后新建会话，不修改现有会话”的约定。不是模型自行提权，但用户操作的实际生效范围超出页面与 ADR 承诺，应首先修复。

处理方向：在真正创建会话时原子保存默认快照；覆盖草稿、复制/导入等实际创建入口；为历史缺行会话明确迁移策略，保留显式配置；重置操作保存当时默认，而非永久跟随未来默认。旧数据未保存的历史选择不能凭空恢复，迁移不得冒充恢复了历史权限。

### R2：权限修改与审计不是一个原子操作

`SessionPermissionEditService` 先 `setForSession` / `setAppDefault`，再 `appendAudit`；CUSTOM 保存还包含草稿与活动配置两次写入。`DefaultAppContainer` 未给这些操作提供共同事务。`SessionPermissionSection` 的保存协程也没有对应错误处理。

若后续审计写入失败，权限可能已生效，而操作表现为失败；未处理异常还可能导致页面所在进程退出。调用链缺口已确认，具体故障需注入验证。应将相关配置、草稿、审计纳入同一存储事务，并在 UI 处理失败、重读真实状态；仅增加 `catch` 无法消除部分提交。

### R3：快速连续 CUSTOM 编辑可能互相覆盖

`SessionPermissionSection.setDraftRule` 在启动保存协程前从 `draft.value` 生成完整规则映射。两次快速点击可能都基于旧映射，后提交者覆盖前一次修改。仓库的 revision 也采用读后加一再写，缺少独立的原子递增/冲突处理。

与 R2 一起修复：串行提交编辑命令并在事务内读取最新状态，或采用可验证的版本冲突协议。测试需控制交错顺序；单纯禁用按钮不是完整的持久层保证。

## 订阅 Runtime：修资源实现，不恢复已撤销配额

`CliPfdChannel` 默认可全量读取；结果编解码与进度读取存在整体 JSON 和事件列表；`SubscriptionModelStream`、`CodexJobProgress`、客户端分别保留累计事件，存在内存放大。按事件数分批也不能限制单个巨大事件的字节数。这些是应修的实现问题，尚未在本次制造 OOM。

但 [ADR-PROVIDER-002](../../adr/provider/002-subscription-adapters.md) 明确撤销固定总响应时长与累计字节截断，同时要求单批传输有界。旧常量未使用不能直接等同漏接保护，现有测试还明确要求超过旧配额继续成功。**不采纳原报告直接恢复旧累计上限/总超时的建议。** 优先流式落盘、有限批次读取、稳定游标/完整性校验、释放已消费数据；任何重新引入总配额的行为都需要另行决策。

另外两条失败路径应纳入同一修复批次：

- `CodexPayloadJobRunner` 先写请求再写 job 记录；后者失败可能留下无记录目录。准入限制 128 个目录，所以不是数量无限，但孤儿目录可能占满名额，且单个内容没有同等总量保证。补所有权明确的失败清理及重启回收。
- `CliRuntimeServiceBinder.writeReconcile` 在 `runCatching(...).onSuccess` 中调用 `finishReconcile`，该回调自身异常不会被前面的 `runCatching` 捕获。应覆盖整个结算路径，失败时保留可恢复证据，不把失败清理伪装成成功 ACK。

## 性能、构建和清理建议的取舍

1. 聊天时间线反复过滤、历史工具结果逐轮查询、流式更新重复查询 Turn，以及 Files 状态构造时同步 SAF 调用有源码依据。优先局部优化与真实数据测量。Kotlin `copy` 是浅复制，StateFlow/Compose 也有合并与跳过机制，不能断言“每 token 深复制并重绘整个界面”。
2. 不取消文件内容哈希验证。`artifactId` 在内容更新时可保持不变，按 ID 永久缓存验证会漏掉外部改动；缓存需要内容版本及失效依据。
3. KSP 与 Kotlin 版本数字不同不是错误证据：[KSP 2.3.0 官方说明](https://github.com/google/ksp/releases/tag/2.3.0) 已说明版本解耦。Detekt 的编译版本差异可列维护调查，但不能直接断言检查失效；参见[官方兼容表](https://detekt.dev/docs/introduction/compatibility/)，升级需规则与构建回归。
4. `core:workspace` 当前已经是 JVM 模块，原报告再迁移建议过时。IPC 中 Android Binder/PFD 不能整体搬入纯 JVM 模块；只考虑契约相同的纯编码部分。不同签名/授权用途的 canonical JSON 不能未经字节向量验证合并。
5. 环境文档仍有独立 APK、独立 UID、离线 PRoot 的旧说明及失效命令，应尽快校正。QuickJS 并非全部 developer-only。模块名含 `-app` 的重命名有脚本与治理成本，不是当前阻塞项。
6. 不批量删除 spikes、测试和调试历史；它们可能承载 ADR 验证与复现来源。也不为“清理”无条件删除含旧 APK、测试证据的 build 目录。大类拆分不是缺陷修复的先决条件。
7. 隐私删除 UI、下载生命周期、无障碍与错误文案应继续跟踪，但“已有底层服务”不等于仅接一个按钮即可验收；涉及运行中任务、级联文件和共享引用的删除需完整边界。品牌文字、箭头或视觉尺寸本身不证明 i18n/触控缺陷。
