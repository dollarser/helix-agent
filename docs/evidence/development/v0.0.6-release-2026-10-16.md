日期：2026-10-16（Asia/Shanghai）。Owner 要求修复上一轮观察/渲染问题并完成 GitHub 开发预览发布收尾；继续仅模拟器、既有预览签名、`versionCode=1`。不启动 HXA-286～294，不追加已结案的账号测试、真机或长稳。

## 起点与根因

起点 main / `348632a8`，保留并审查已有包体、UI、文档及插件收尾改动。上一轮 [候选验收](v0.0.6-preview-acceptance-2026-10-15.md)中的 SwiftShader 图像损坏、观察拒绝及 code 2/code 1 对象差异保持原始结论。

观察缺陷已独立复现：自有 API36/Shizuku 中，同一测试窗口每 80 ms 改变一个文本节点，旧 APK 的 `ui.snapshot` 返回 `TARGET_CHANGED`。它把完整语义树 revision 当作新鲜读取的稳定前提；窗口和授权没有改变，内容更新也阻止了模型重新观察。这证明了该机制的缺陷，不声称已捕获上一轮抖音每次失败的具体字段。

## 修复与边界

- 修改位于 Mobile Use 插件的高权限观察实现与调用宿主；新鲜快照及截图允许内容更新，仍核验原授权、目标包/窗口/显示/尺寸/方向/边界。截图采集和编码后继续复核窗口集合与授权，范围受限时仍使用真正的窗口截图。
- 截图不更新旧 frame revision。坐标动作仍验证原完整 frame，节点动作仍验证原节点指纹；后端重建、撤权、取消、锁屏与原调用身份不放宽。没有按应用名特判或自动重放。
- 对 `TARGET_CHANGED` 的提示只解释观察事实，不推导 FLAG_SECURE 或登录要求。设计更新原 [权限 ADR](../../adr/permissions/001-session-authorization.md#decision-history--2026-10-16动态页面的新鲜观察与操作凭据分离)。
- 自有模拟器运行器支持显式 GPU 参数并记录，默认采用 `auto`；本轮使用 `host` 与上一轮 `swiftshader_indirect` 证据对照。模式改变本身不算渲染验收。

修复位于 `ShizukuHierarchy.synchronizeWindowTransactions` 与 `PrivilegedDeviceService.targetFor`：在既有 shell/root 边界内调用平台窗口事务同步，然后再核验原授权并读取截图目标。View 脱离和主线程两帧不是 WindowManager Surface 提交的同步屏障；[WindowManagerService](https://github.com/aosp-mirror/platform_frameworks_base/blob/android16-release/services/core/java/com/android/server/wm/WindowManagerService.java)提供的同步覆盖窗口事务。反例与对照支持这一同步缺口，**没有证据将问题归因于 R8 混淆本身**。没有应用名特判、全局动画修改、固定等待、裁剪/涂抹或自动重放；原范围、旧凭据、取消/deadline、窗口集合及编码后复核均保持。设计补充在原权限 ADR。

维护测试首次新增的 Kotlin Surface 类在独立测试 APK 进程中缺少 Kotlin runtime 而崩溃，导致读取到 Helix 页面、TICK 断言失败；改为同目录体系已有的平台 Java 夹具后真实复测通过，没有弱化原断言。临时 UI 夹具另修正过期无障碍缓存、已有默认模型的选择器假设；最终两渠道独立 UI **6/6 passed**，失败日志保留。

最终四个 APK 位于 ignored `candidate-overlay-final/`，旧 `candidate/` 和首个修复的 `candidate-overlay-fix/` 原样保留。最终生产输入是 `be52a824` 基础上的两处后端修复，当前有未提交工作区差异；随包记录差异、输入清单、签名、Manifest 与哈希，不伪标成干净旧提交。四个 APK 均已按当前生产源码重建，两渠道 ARM64 安装读回哈希一致；x86_64 仅主机构建。仍是 0.0.6/code 1、与 v0.0.5 相同的既有开发证书。后续仅设备夹具由 Kotlin 改为 Java，不影响生产 APK 输入。

本轮有界结果关闭已复现的悬浮按钮截图缺陷；其他 API/OEM、Root、无障碍截图及长期运行未因此获得通过。官方入口发现效率仍是质量限制，首批完整抖音任务的辅助条件也继续保留。

最终 Developer ARM64 又通过实际 Qwen3.8-27B 的连接/能力检测，并执行一个只操作独立夹具的视觉任务：原 Turn COMPLETED，9 次模型调用、8 次工具调用；截图 SAVED，原图与回填产物哈希核验、两个按钮区域像素均干净，模型正确描述深青绿/浅蓝背景与白色短条。真实视觉回填子项通过，**整个任务不记全通过**：双渠道同时安装时，ui.apps 如实列出两个同名 Helix，模型随后选择 `com.helix.agent` 而非发起任务的 `com.helix.agent.developer`，并错误声称返回原对话；最终前台也确认是 consumer。该返回目标歧义作为独立交互质量限制保留，未通过硬编码跳转或改写模型结论掩盖。后续宜在插件观察结果中明确宿主身份并验证模型使用该事实，不扩大工具授权；本轮不把此改进混入已冻结的截图修复。

真实模型准备夹具最初误选了同页其他 Provider 的同名连接/能力按钮；随后按 **Preview Qwen 卡片范围**定位公开 UI 控件，实际确认 Qwen 的流式、工具、视觉及推理能力。临时凭据只写自有测试 UID，并由夹具删除；导出仅包含该合成 Turn 的 24 条消息、31 个哈希核验内容对象和 2 个图像产物，不含 Provider 配置或完整数据库。
