# v0.0.6 动态观察修复与发布收尾

日期：2026-10-16（Asia/Shanghai）。Owner 要求修复上一轮观察/渲染问题并完成 GitHub 开发预览发布收尾；继续仅模拟器、既有预览签名、`versionCode=1`。不启动 HXA-286～294，不追加已结案的账号测试、真机或长稳。

## 起点与根因

起点 main / `348632a8`，保留并审查已有包体、UI、文档及插件收尾改动。上一轮 [候选验收](v0.0.6-preview-acceptance-2026-10-15.md)中的 SwiftShader 图像损坏、观察拒绝及 code 2/code 1 对象差异保持原始结论。

观察缺陷已独立复现：自有 API36/Shizuku 中，同一测试窗口每 80 ms 改变一个文本节点，旧 APK 的 `ui.snapshot` 返回 `TARGET_CHANGED`。它把完整语义树 revision 当作新鲜读取的稳定前提；窗口和授权没有改变，内容更新也阻止了模型重新观察。这证明了该机制的缺陷，不声称已捕获上一轮抖音每次失败的具体字段。

## 修复与边界

- 修改位于 Mobile Use 插件的高权限观察实现与调用宿主；新鲜快照及截图允许内容更新，仍核验原授权、目标包/窗口/显示/尺寸/方向/边界。截图采集和编码后继续复核窗口集合与授权，范围受限时仍使用真正的窗口截图。
- 截图不更新旧 frame revision。坐标动作仍验证原完整 frame，节点动作仍验证原节点指纹；后端重建、撤权、取消、锁屏与原调用身份不放宽。没有按应用名特判或自动重放。
- 对 `TARGET_CHANGED` 的提示只解释观察事实，不推导 FLAG_SECURE 或登录要求。设计更新原 [权限 ADR](../../adr/permissions/001-session-authorization.md#decision-history--2026-10-16动态页面的新鲜观察与操作凭据分离)。
- 自有模拟器运行器支持显式 GPU 参数并记录，默认采用 `auto`；本轮使用 `host` 与上一轮 `swiftshader_indirect` 证据对照。模式改变本身不算渲染验收。

## 新发现与发布阻塞

归档两张实际 R8 视频工具截图时，一张完整隐藏，另一张仍含悬浮控制按钮；状态条与控制按钮不能混为同一个已通过结论。现有隐藏协议要求移除窗口、等待两帧并确认脱离，不应通过裁剪、涂抹截图或放宽旧 frame 来掩盖。对照 [Android UiAutomation 源码](https://github.com/aosp-mirror/platform_frameworks_base/blob/android16-release/core/java/android/app/UiAutomation.java)仅得到截图调用不自行等待窗口事务的排查线索，**尚未证明这是根因**，未盲目加入隐藏 API、全局动画修改或固定等待。

追加 Debug 夹具刷新真实持久 Turn 的任务投影，在独立窗口/画面采样确认浮窗确实显示后，检查控制区域应恢复为底层夹具像素。首个追加夹具未能取得有效语义快照（UNSUPPORTED_UI），失败保留；调整布局并刷新投影后通过，最终两个按钮区域断言 1/1 passed。它没有复现实际 R8 残留，因此不作为该缺陷已修复的证据。发布前应定点收敛实际 R8 浮窗实例/窗口提交时序；官方入口发现效率也仍是质量限制，未新增自动重试或应用特判。

自动审批拒绝了 `git push origin main`，理由是远端默认分支历史及 CI 变更需要针对该写入的明确许可。已向 Owner 提出“推送 main，并在主机 CI 和模拟器实测通过后发布 v0.0.6 预览”的具体确认，截至本记录仍待答；未改用其他分支、API 或传输方式绕过。**精确候选提交的远端 CI 尚未运行，v0.0.6 没有发布链接**。本地门禁不替代 CI，README 的已发布入口继续保留 v0.0.5。
