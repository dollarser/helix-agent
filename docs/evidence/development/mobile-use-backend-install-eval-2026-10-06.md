# Mobile Use 三后端安装/卸载真实模型评测

日期：2026-10-06。所有者明确授权模拟器和当前真实模型评测、复测。本轮是发现问题与交互评估，不是修复后的安装验收。

## 方法和边界

- API36 `Helix_API_36` 分别启用普通无障碍、Shizuku；API34 `Helix_MobileUse_Root_API34_20261004` 使用 Magisk 应用级 Root。高权限组关闭 Helix 无障碍，无障碍组停止 Shizuku。实际工具返回分别包含 `accessibility`、`shizuku`、`root`，不是仅根据设置推断后端。
- 两台覆盖安装同一 Developer Debug APK，当前工作树含此前未提交工作。版本仍为 0.0.4 / 4，不代表发布包。APK 哈希与部署输出保存在忽略目录。
- 模型均为现有服务的 `Qwen3.8-27B`；Root 独立设备为测试临时迁移配置与凭据，传输不输出凭据，临时文件和 Root 测试 Provider/密钥已清理。Root 首次连接探测不计入任务调用数。
- 应用为无账号、无用户数据的 `com.helix.validation.installfixture`（Helix Install Fixture）。测试宿主准备 APK、打开安装来源/应用详情页；模型通过生产 ChatService、Dispatcher、Mobile Use 自主决策。每项仅发一条明确请求，不补充“继续”，不代点安装/卸载确认。
- 安装失败后，为独立测试卸载，宿主通过 ADB 准备测试 APK；这不能算 Helix 安装成功。未操作微信、抖音、酷安的数据或账号，也未评测网上寻找/下载 APK。
- 会话通过测试夹具配置 Advanced、完全访问、Mobile Use 全手机范围，额度为 40 次模型/30 次工具及累计 524288 token。这是已授权能力下的执行评测；不代表普通用户首次配置、审批交互已经端到端通过。
- 单样本和少量复测只能定位本轮问题，不能推导总体成功率；Root/API34 与另两组/API36 不构成控制 Android 版本后的性能比较。

## 主要问题

### 1. 安装确认在高权限路径被 Helix 过度保护

Shizuku 快照已经得到安装按钮的边界，但返回为 `Protected field`、空 token、不可点击；`recoveryHint` 又明确要求人工操作，不得使用截图/坐标/另一后端绕过。Root 同样返回受保护按钮。因此当前失败不能解释为 Shizuku/Root 没权限、无法看到屏幕或模型缺工具。

当前 `AndroidSnapshotNode.accessibilityDataSensitive` 将系统敏感标记转为保护节点；`publicPermissionControl` 只例外放行可信 PermissionController 的公开权限选项，不包含 PackageInstaller 的安装确认。`PrivilegedSemanticEngine` 和 `AutomationSnapshotEngine` 延续该结果。这与早期特权直接点击安装成功的历史证据是不同执行路径，历史通过不能覆盖当前语义路径。

普通无障碍这次没有拿到安装按钮，走截图/坐标后多次返回动作已派发，但安装状态未变。它还遇到 4 次 `STALE_TOKEN` 和 1 次 `TARGET_NOT_FOUND`。本轮未证明这些点击无效的唯一平台原因，也未证明节点过期一定由悬浮窗造成，不能把二者与 Helix 明确脱敏混为同一根因。

建议优先单独修复公开安装确认的分类：验证系统安装器身份、限定非密码/非编辑的公开确认控件，仍经过原范围、授权、窗口与结果核验；不能全面关闭敏感保护，也不能把未知保护区域改为坐标回退。

### 2. 无进展时收尾不稳定

- 无障碍安装反复截图/点击，最终 `TURN_TOTAL_TOKEN_LIMIT`，没有及时清楚交接。
- Shizuku 遵循工具明确的保护提示，正确请求人工；之后等待 60 秒，最终未完成。这不是遗漏截图调用。
- Root 最后一句是 “The INSTALL button is being redacted. Let me take a screenshot to see the actual UI state.”，随后 turn=COMPLETED，没有 screenshot 调用。这是可复现的“计划式最终回复”，不是安装成功。

建议优化工具指导和模型评测：相同观察、无结果变化时不要盲目重复；应更换有证据支持的策略或明确交接。受保护时应说明阻塞事实，而非承诺下一步。Harness 继续保存真实调用和效果，不凭文字臆造动作，不自动重放安装/卸载。

### 3. 卸载验证缺少精确、便宜的事实入口

`ui.apps` 只列 Android 可见且可启动的应用；不在列表里并非所有情形下都能证明已卸载。模型因此会进入 Settings、搜索、滚动，Root 干净页面复测仍用了 19 次工具调用。

建议为已授权包提供准确的只读包状态查询，区分已安装、未安装、不可见/无法确定；不要将 launcher 列表缺项等同未安装。若已有宿主包查询可复用，应接入现有移动工具契约，避免为了核查增加任意 shell。

## 配置交互实测

在 API34 实际沿抽屉操作到权限页并保存 UI 层级/截图，结合当前源码核对：

- 路径为抽屉 → 设置展开 →（滚动）权限与安全 → 设置访问权限 → 授权管理 →（滚动多屏）设备控制。集中管理方向正确，但日常开启 Mobile Use 的路程偏长。
- 悬浮窗位于“通知与日历”标题下，分类不准确。应归设备控制或独立任务显示；仍应是可选授权。
- Root 系统页“申请或检查”只取得应用授权；Mobile Use 插件页还需“连接 Root”。这两步在代码中是不同操作，用户只看“已授权”容易认为已经可用。Root 未核验、已授权、已连接应分清，但无需迫使用户跨两个页面完成常用操作。
- 无障碍显示“已授权 0 / 1 项应用服务”，偏技术且不直接说明是否能操作；Shizuku 不可用时入口是“打开 Shizuku”，缺少安装/服务未启动/未授权/连接故障的具体修复引导。
- 本轮权限页检查未测完普通用户从零配置的全部授权按钮；模型测试通过夹具设定权限，不能据此宣称授权流程简单或零配置。

建议统一一个面向任务的状态区：当前可用后端、缺少的具体能力、一个主要修复操作。Helix 继续管理系统授权，插件复用；已有授权下的连接可在明确启用功能时建立，不自动申请新 Root 权限。高级详情再展示连接、诊断和后端选择。此方案属于下一步设计建议，本轮没有修改生产授权语义。
