# 对标豆包手机助手：Helix 的差距与本轮改进

核验日期：2026-10-05。范围：公开一手资料、Helix 当前源码及仓库既有验证记录。没有豆包手机、Roubao 或一加 Ace 5 的本轮实机横评。官方演示和宣传说明不等于可重复完成率；仓库测试数量也不等于消费者体验。

## 1. 结论

Helix 应优先让普通用户从“我想做什么”顺利走到“知道缺什么、开始执行、检查结果”。当前最明显且可以立即改善的产品差距，是**首个任务入口与能力准备分散**，而不是缺少另一套 Agent 调度框架。

这不代表底层工作已经完成 60～70%，也不支持“Mobile Use 已反超 Roubao”“记忆明显强于豆包”等结论。缺少同任务、同模型、同设备、同权限条件下的测量，无法给可靠百分比或总分。

产品表达建议仍是：**Helix 是开源 Android AI 助手，能在授权范围内组合手机操作、网页和文件工具完成任务，并提供可检查的结果。** OEM/System Image 是独立合作与产品决策，本轮不把它升级成发行承诺。

## 2. 对输入分析的事实校正

| 原分析主张 | 核验结论 | 采用方式 |
| --- | --- | --- |
| 豆包 M153 与操作系统深度集成，展示跨 App 任务 | 中兴 2026-03-03 官方材料明确说明系统级集成，并举餐厅预订、比价与路线规划等例子 [S1] | 可作为体验目标，不能当成所有第三方 App 的成功率证据 |
| Roubao 是截图驱动的手机 Agent | 本轮可见主分支源码包含 Shizuku UserService 控制、动作后截图与 Reflector 调用 [S2][S3] | 借鉴任务入口，不能从某段路径推断所有模型始终执行固定多轮流程 |
| Roubao 有低权限 local shell fallback | 可见 DeviceController 的 exec 在无服务或异常时调用本地 shell [S3] | Helix 保持明确执行域与失败结果，不复制这类隐式降权路径 |
| 最近提交停在特定日期、v2 宏录制、GUI-Owl/MAI-UI 支持 | 本轮未形成提交 SHA 与完整分支审计；部分分支页面读取失败，README 搜索未确认专用模型名称 | 不引用这些日期判定停更，不把未找到视为不存在 |
| Roubao allowlist 被注释、回归不足 | 未完成对应 ShellTool 与全测试目录审查 | 列待核验，不当作安全或成熟度排名依据 |
| Helix 可以通过 android.open_uri 直接调用任意 App DeepLink | 不成立：当前 AndroidOpenUriTool 和桥实现仅允许 HTTP/HTTPS | HTTPS App Link 是否进入目标 App 仍取决于系统与应用；自定义 scheme 需要独立白名单、参数和 effect 审查 |
| Helix 已具备三档、应新增四个发行版 | 当前有效产品边界仍是完整 Standard 与 Advanced/developer 能力集 | 普通/无障碍/Shizuku/Root 是能力与验证矩阵，不新设 Enhanced/Power/OEM 产品渠道 |
| Root → Shizuku → 无障碍 + Vision | 高权限后端优先是已有设计；Vision 是观察/定位方式，不是与系统授权同层的权限后端 | 按每项操作实际可用能力、授权和屏幕身份检查，不能把存在 Root 等同于全能 |
| 记忆、安全和 GUI 已领先竞品 | Helix 有相关代码与定向证据，但没有等条件横评；豆包公开了隐私安全白皮书入口 [S4] | 只比较可确认特性，不从闭源内部未知推断竞品没有边界 |

## 3. 当前欠缺，按用户影响排序

| 优先级 | 差距 | Helix 当前证据 | 最有价值的补齐 | 本轮状态 |
| --- | --- | --- | --- | --- |
| P0 | 首个任务不知道怎么开始 | 空会话默认是代码分析、技术方案、测试；无模型时示例消失；手机操作准备分散 | 日常任务示例、直接选模、手机操作准备入口，保留用户主动发送 | 已实施入口收敛，设备交互待验证 |
| P0 | 跨 App 成功率和速度没有稳定指标 | 有抖音/酷安和合成任务的有界历史验证，不覆盖每个 OEM/账号/版本 | 固定任务集测完成率、耗时、模型调用、人工介入、错误副作用 | 给出下节验收协议；本轮不调用模型或设备 |
| P1 | 缺少经过验证的 App 快速能力目录 | 有原生工具、HTTP/HTTPS 打开与插件 Skill；不等于成熟 App API/DeepLink 目录 | 按应用/版本维护能力、参数、权限、后置验证和回退条件 | 先设计契约，不增加未经验证 scheme |
| P1 | 随时唤起和语音闭环 | 当前为打开应用后调用系统识别界面；无消息朗读和系统级常驻唤醒 | 先做好系统服务兼容性和明确失败，再单独评估系统助手角色 | 本轮前置系统语音优化已完成主机验证；OEM 仍待验证 |
| P1 | 手机任务的完成反馈不够可比较 | 可展示工具结果、成果、UNKNOWN/recovery，但缺少统一业务验收样本 | 对每个任务定义成功事实，区分“打开安装器”和“已安装包” | 保持原事实体系，不把模型一句“完成”当测量结果 |
| P2 | App/API/GUI 的组合策略缺少真实效果对照 | 通用模型、工具发现、插件技能已接通 | 比较原生路径与 GUI 路径；只有重复任务收益成立才加目录/专用模型 | 保留浅 Harness，不引入固定 Manager/Executor/Reflector 流水线 |
| P2 | 成功轨迹还不是可复用技能 | 有 Skill，不代表具备安全的轨迹编译与回放 | 参数化语义目标、逐步条件检查、用户批准、版本漂移拒绝 | 独立后续工作，不直接重放坐标或未知副作用 |
| 长期 | 系统/OEM 集成能力缺口 | 普通 APK 与系统合作产品在权限、唤醒和后台能力上不同 | OEM 合作、签名/系统服务边界、分发与设备测试 | 未授权为当前发行路线 |

“最大缺口”分两层：最大的外部能力差距是系统集成；最大的当前可改善产品缺口是首个任务体验。本轮选择后者，因为可以复用现有能力，不需要 OEM 合作，也不靠扩大权限取得表面改善。

## 4. 本轮落地

1. 空会话改成任务导向入口，普通模式示例覆盖找资料、整理内容和出行规划；Goal 模式示例描述报告、文件索引等可检查成果。技术工作仍可直接输入或从项目进入，不删除现有能力。
2. 未选模型时仍可选择任务草稿；提供直接选模入口，复用现有订阅/API/本地模型选择流程。点击示例只填入输入框，不发请求、不消耗额度。
3. 在包含 Mobile Use 的安装中提供“让 Helix 操作手机”：集中展示插件启用/注册、本会话选择状态，并链接原有会话能力选择、插件配置与宿主授权页面。没有插件的渠道不展示虚假的手机能力入口。
4. 插件选中仅表明模型可获得工具，不宣称系统授权已齐全。页面不自动开 Root、Shizuku 或无障碍，不要求所有权限全开。亮度示例只填入草稿，仍走工具授权及验证链路。
5. 系统语音另有[兼容性修复](../evidence/development/system-voice-compatibility-2026-10-05.md)：区分 Activity 与服务、显式错误、系统设置回退。TTS 仅展示已安装引擎，Helix 尚无消息朗读功能。

这一步解决“从哪里开始和去哪里准备”，不是宣称跨 App 完成率已经提升。准备入口仍跳转到既有权限页面；自动判断每种设备的所有执行能力属于后续闭环。

## 5. 下一步最值得做的快速能力契约

不要先做通用 DeepLink 执行器。先选择一两个有官方文档、可在受控样本验证的能力，放在 Mobile Use 的插件内容或现有 typed 工具中。每条记录至少含：应用包/版本条件、官方来源、动作和参数 schema、允许的 URI/Intent 模板、原执行域与授权类别、成功观察条件、不可用原因、GUI 回退规则、最近验证设备/API。

优先级是可验证的原生工具/官方接口 → 已验证的 App Link → 当前语义界面 → 必要的视觉定位。它是向模型提供可选能力，不是 Harness 按关键词偷偷替模型选择动作。打开目标页只证明导航发生，不能证明订单、消息或安装完成；失败后的回退必须重新观察，禁止复用旧坐标、绕过审批或自动重放 UNKNOWN 副作用。

微信联系人/扫码、Bilibili 搜索等列举能力在没有官方契约与设备验证前，不发布成“已支持”。涉及付款、发送、授权等动作继续按有效权限与风险决定处理，不用“少确认”取消必要的用户控制。

## 6. 可执行的任务验收协议

以下为待执行协议，不是通过结果。真机/模拟器和真实模型分别需要所有者授权。

| 任务组 | 初始条件 | 成功事实 | 必须保留的失败分支 |
| --- | --- | --- | --- |
| 首个任务 | 新安装/无模型、已配模型各一组 | 用户能选模、保留草稿并发起任务；点击示例无模型调用 | 无模型、插件禁用、权限缺失有对应入口 |
| 手机设置 | 固定初始亮度与明确目标 | 系统读取的最终值符合目标，错误应用未被操作 | 无后端、弹窗遮挡、任务取消 |
| APK 安装 | 可信测试 APK、未安装的固定包名 | 包管理器确认包名/版本；模型终止状态与事实一致 | 未知来源设置、安装器按钮、下载失败、UNKNOWN |
| 网页与文件 | 固定公开页面/测试文档 | 输出存在、来源可查、内容符合指定字段 | 页面不可达、文件权限失效、无模型 |
| 跨 App 草稿 | 测试账号与固定对象，默认不实际发送 | 对象和草稿内容正确、发送前可核对 | 错联系人、界面漂移、人工接管 |

每个环境先跑固定 10 次；逐次记录设备/API/App 版本、权限后端、模型及配置、是否一次自主成功、总耗时、模型调用数、人工介入次数、错误副作用和失败原因。10 次只能筛查回归，不能代表生产可靠性。分别报告中位耗时和尾部耗时；重试成功不算一次成功。无设备或模型运行写 pending/not requested，不能填零耗时或 100% 成功。

决策门槛：先消除错误对象操作、重复副作用和虚假完成，再谈减少步数；使用同一任务/设备/模型比较“当前路径”和“快速路径”。专用 GUI 模型、宏技能和更复杂调度须在这些指标上有收益才进入实施。
