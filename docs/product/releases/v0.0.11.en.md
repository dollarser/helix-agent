# v0.0.11 Development Preview

[简体中文](v0.0.11.md) · [Changelog](../../../CHANGELOG.md) · [Acceptance record](../../evidence/development/v0.0.11-preparation-2026-11-13.md)

Published on [GitHub as a prerelease](https://github.com/dollarser/helix-agent/releases/tag/v0.0.11) on 2026-11-14 (UTC). [ModelScope](https://modelscope.cn/datasets/dollars/Helix) also provides the same two APKs and a live update manifest. The combined candidate's Debug/R8 core acceptance, final-source CI and public signed-APK installation/update checks are listed separately below.

Compared with v0.0.10, this preview focuses on service and model settings, cross-session collaboration, web and file tools, and long-running task recovery. The product version is **0.0.11**. Android versionCode and Helix-owned internal versions remain **1**. The artifacts are Standard (consumer) and Advanced (developer) ARM64 Release/R8 APKs using the existing development-preview certificate, not store production signing.

Helix has not reached a formal release. Development previews do not guarantee in-place installation or preservation of existing data, even if installation succeeds. Save important content separately before upgrading.

## Main changes

- **Manual update checks:** Settings → About Helix → Check for updates reads ModelScope metadata only after a user action. It selects the newest semantic version matching the installed package and device ABI; opening its browser download requires a separate action. No background checks, installation permission, automatic installation or data clearing are added.
- **Ordinary conversations and required checks:** Fixed the production Room store rejecting a bounded `tools.cost` diagnostic before the model request. Unknown types and payload limits remain enforced. Every candidate requires actual conversation, successful tool backfill, persisted history after process restart, cancellation, no replay and continuation checks.
- **Tool details:** Compact conversation summaries lead to grouped, copyable details. Business content and internal diagnostics are presented separately without replacing stored tool results, model records or audit values.
- **Services and models:** API connection fields and model selections share one editor with a single save action. Add multiple models and display names without leaving it. Connection, model-generation and capability checks keep separate results. Conversation model pickers group models by service; subscription sign-in retains its own management flow.
- **Cross-session collaboration:** Explicit, separate grants control history access, management, creation and task delivery. Query sessions, create them idempotently, queue work or steer a specific active Turn. Model-origin messages retain provenance and do not copy file grants, create user Goals or bypass the target's approvals.
- **Web and search:** Bounded public-page fetching, browser search and form actions, plus page text that retains usable source links. API search and supported Responses native search require explicit enablement and do not silently activate paid services.
- **Files and granted directories:** Stronger native glob and literal grep behavior with real system SAF providers, readback, revocation and cancellation checks. Fixes cover directory-to-conversation handoff, long directory names and refresh state.
- **MCP and skills:** Bounded text and binary MCP Resources are delivered through host-managed artifacts. Binary bytes are not inserted directly into model text. Skills retain plugin ownership, with atomic composer tokens and slash discovery.
- **Long tasks and recovery:** Changes to compaction preflight, tool discovery and schema projection, stable cache prefixes and observed cache accounting. Goal coordination, tool settlement and process recovery retain explicit unknown-effect states rather than automatically replaying them.
- **Advanced media and mobile use:** FFmpeg continues through the existing PRoot/Job path for media, subtitles, fonts and multiple outputs. A MediaCodec initialization patch removes the encoder-flush path. The computer ADB helper supports non-debuggable Advanced builds on Android 12+ through app-issued, one-use, process-bound handoff tickets. Standard has no helper entry.
- **Documentation:** Chinese and English READMEs focus on core capabilities, GitHub/ModelScope downloads and real screenshots using a public example file. Version changes are kept in bilingual changelogs, with verified historical dates and explicit preview upgrade risks.

## Before upgrading

- **v0.0.10 has no in-app update entry.** Manually download the matching channel from GitHub or ModelScope for the first upgrade to 0.0.11, then use the Android system installer. Settings → About Helix → Check for updates is available from 0.0.11.

- This candidate's database structure differs from the earlier v0.0.10 build, including new cross-session grant and idempotency-receipt tables. Keeping the internal schema version at 1 does not imply compatibility or lossless upgrades.
- An incompatible database requires a specific impact notice and independent confirmation. Canceling must not clear it. Rebuilding the main database is distinct from clearing all application data; release preparation does not authorize clearing a daily installation.
- An application backup is not a copy of account/OAuth sessions, Android permissions, directory grants or running tasks. An older backup is not evidence of restore compatibility.
- versionCode remains 1. Android may reject installation over an older preview with a higher versionCode; uninstalling removes private application data. Automatic system/store update discovery is not promised. Package, signature, installation and retention claims depend on the exact final APKs.

## Checking for updates

- The fixed [ModelScope repository](https://modelscope.cn/datasets/dollars/Helix) supplies `resolve/master/update-manifest.json`. Selection uses semantic version precedence and package/ABI compatibility, not a hard-coded target version or README upload time. Release APKs use `releases/v<versionName>/` paths.
- A newer version name with an unchanged or lower versionCode shows an in-place-update warning. Do not uninstall or clear data to bypass it. The download action hands off to the browser; installation and Android's package/signature checks remain separate. Helix does not claim it has verified the downloaded APK or installed an update.
- Network errors, an unpublished manifest (HTTP 404), invalid metadata and missing compatible packages have distinct results with retry or manual-download options. Both GitHub Releases and ModelScope remain available as download entries. An absent manifest is not reported as “up to date”.
- The [public update manifest](https://modelscope.cn/datasets/dollars/Helix/resolve/master/update-manifest.json) lists both 0.0.11 channels. Publicly downloaded APKs match the local signed artifacts. Both 0.0.11 channels read the live service and reported the current version on an isolated API36 emulator. No newer public release existed, so this is not a complete future-version upgrade test. See the [distribution contract](../../adr/platform/001-distribution.md#modelscope-更新发现).

## Limits

- Search, subscription, MCP and model support depend on the configured provider. Integration is not universal service or model acceptance.
- MediaCodec encoding depends on the device. No x264, x265 or AV1 software encoder is included; codec coverage and performance are not universal.
- Cross-session controls are not remote computers or production subagents, and do not grant file, device or external-service access automatically.
- Host, emulator, physical-device and real-model checks are listed separately. Old candidate results are not current acceptance. No claim is made for every OEM, 24-hour soak testing, 16 KiB physical devices or microphone/headset quality.

## Final core acceptance and historical evidence

The current results below were rerun after integrating update detection and the bilingual documentation/screenshots. Earlier UI-only, phone and media results remain separately identified. Exact source, build and installed-artifact identities are recorded in the [acceptance record](../../evidence/development/v0.0.11-preparation-2026-11-13.md).

- Both channels passed 40 actual Debug methods on exclusive API36 emulators: 35 real-Room conversation-core methods across 9 classes, plus 3 update UI methods and 2 About methods. There were zero failures, skips or missing methods. The earlier 28-method tool-detail UI batch remains a separate historical check, not part of this count.
- Update UI fixtures verify explicit check/download actions, versionCode warnings, retry/error presentation and cancellation preventing stale results from reopening a dialog. They do not establish a live published manifest, completed browser download or Android installation.
- Both ARM64 R8 channels were built from the same final production and Release-test inputs, using isolated package IDs, a test certificate and non-debuggable applications. All four source-enumerated default smoke methods passed per channel. The conversation journey reaches a real loopback HTTP provider, executes a real read-only tool and returns its successful result, verifies process exit and a different PID after restart, reads persisted history into the next request, closes a cancelled connection, avoids replay after restart and continues successfully. Installed APK hashes match the frozen copies; exact fixture-package removal and owned-instance closure are recorded.
- The same strengthened test APK rejected the retained broken candidate before the first ordinary request reached its provider and passed a repaired intermediate candidate. This establishes a useful regression control; the intermediate result is not final two-channel acceptance.
- The final complete `check-all.sh --all` host gate, both ordinary ARM64 distribution builds and artifact-boundary checks exited successfully with an unchanged full-file inventory across all host/device stages. Four owned emulator instances verified installed APK hashes, removed the exact fixture packages and closed successfully. Only result documentation was updated afterward, followed by another source gate. Normal Gradle cache reuse is not described as reexecuting every task, and host success does not replace actual device acceptance.
- Earlier ONEPLUS_A6013 / API34 / ARM64 / 4 KiB-page runs covered 30 Debug checks and 8 R8 entry checks. The phone/API36 media reruns repeat a three-method subset. That batch did not exercise the ordinary-conversation production Room chain and did not detect the later reported defect; it is not final-candidate core acceptance.
- Historical media evidence supports only the tested OnePlus 320×240/NV12 synthetic H.264/HEVC sync/async cases with 8 frames and actual decoding. The rejected 96×64/yuv420p input remains recorded; no universal Qualcomm rule or minimum size follows. Reusing this evidence requires checking the unchanged media payload in the new artifacts.
- Earlier phone and daily-emulator cover installs retained data for those exact installations, not every public v0.0.10 upgrade. Final core acceptance used exclusive test instances without touching the daily foreground or physical phone.
- Test signing is not final public distribution signing. A 16 KiB ZIP-alignment check is not 16 KiB hardware execution. These core fixtures make no external model calls and do not cover API29, other OEMs, real-model media workflows, prolonged thermal/background stress or microphone/headset quality.

Core device acceptance belongs to the combined product inputs at `36a68c95`. The final `a957defd` only changes CI resource budgets, scripts and related tests, leaving product inputs unchanged. Core device evidence is therefore reused, not rerun for the CI-only change. Installation and live-update acceptance of the final public signed APKs is listed separately below.

## Public signed-APK installation and live update acceptance

On 2026-11-14, publicly downloaded ModelScope APKs matched the local signed artifacts in size and SHA-256. On an isolated API36 / ARM64 emulator, both Standard and Advanced were cover-installed from verified public 0.0.10 packages to 0.0.11 using Android's system installer. Neither upgrade used uninstall, clear-data or `adb install`. Installed APK bytes matched the downloads, while application IDs and first-install times were retained. Both channels queried the live service and reported the current version; close/repeat and Back dismissal checks also passed.

This batch did not modify the public manifest or touch the daily emulator or a physical phone. The temporary install permission was restored and the owned instance shut down. Retained IDs/timestamps do not establish compatibility of all historical content; data warnings and independent incompatible-database confirmation still apply. v0.0.10 has no update entry, so no old-client in-app check/download success is claimed. No newer release existed for a complete future-upgrade test. This batch did not rerun every core-conversation or real-model journey described above.
