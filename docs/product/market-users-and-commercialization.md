# Helix 市场、用户与商业化分析

文档状态：产品策略假设

核验日期：2026-09-02

适用范围：Android 单机版 Helix。本文负责目标用户、使用场景、竞争替代、产品包装、分发和商业化假设；技术执行域、协议与竞品能力证据见[竞品与定位](competitive-landscape.md)，当前实现范围见[实施状态](../development/status.md)。

## 1. 结论摘要

Helix 不应以“最安全的手机 Agent”作为第一卖点。对目标用户而言，先决条件是它能在手机上完成有价值的任务；权限、审批和审计应服务于能力交付，而不是让用户为了安全模型本身付费。

推荐产品定位：

> **Helix 是面向开发者与效率用户的 Android 本机 AI 执行工作台。它连接用户自己的模型，让文件、网页、代码和 Android 能力在手机上形成可组合的任务闭环；Advanced 面向理解权限与设备风险的用户，能力优先，用户对主动开启和确认的操作承担最终责任。**

这不表示模型可以自行授权或产品可以隐瞒影响。能力优先仍需要一个最低可信底座：用户知道正在操作什么、能力是否已经开启、数据发往哪里、任务最终成功还是结果未知。该底座的目标是让高级能力可控、可诊断，而不是把产品变成安全审计工具。

市场切入顺序：

1. 先服务开发者、技术爱好者和重度 Android 效率用户，不追求全民助手。
2. 先完成文件、项目、网页和代码闭环，再扩展 Android UI 自动化。
3. 先证明“安装后在手机上真正完成任务”，再建设工作流、市场和商业生态。
4. 不进入支付、电商下单、抢购、批量养号和无人确认对外发送等责任与平台冲突过重的场景。
5. 商业化优先验证“为稳定能力和省时间付费”，不依赖模型转售差价。

## 2. 分析方法与证据口径

### 2.1 四层竞争关系

| 层级 | 用户实际上在比较什么 | 代表产品/路径 |
| --- | --- | --- |
| 直接能力竞品 | 能否在 Android 本机调用文件、终端、浏览器和设备能力 | Operit、AndCode、ClawMobile |
| GUI Agent 竞品 | 能否看懂手机屏幕并完成跨 App 操作 | Open-AutoGLM、Mobile-Agent 等 |
| 自动化替代品 | 能否稳定重复执行 Android 任务 | Tasker、Auto.js/AutoX.js、Hamibot、MacroDroid |
| 入口与体验竞品 | 能否快速连接模型、开始对话或使用系统助手 | Chatbox 等 BYOK 客户端、Gemini/Claude Android、OEM 助手 |

云端 Agent、云手机和系统级助手是产品上限参照，但不是 Helix 首阶段要正面竞争的交付模型。

### 2.2 证据等级

1. 官方产品页、官方文档、官方仓库和实际 release 用于确认公开能力。
2. 官方自述只能证明产品声明，不能证明任务成功率、稳定性或安全性。
3. GitHub Star、下载量、价格、套餐和社区热度是时点数据，只在决策前实时查询，不写入长期结论。
4. 媒体横评、社区帖子和外部报告用于发现假设，不直接作为市场规模、迁移比例或成功率证据。
5. “目标能力”与“当前已实现能力”分别记录，禁止用路线图中的未来能力填充现状矩阵。

## 3. 目标用户

### 3.1 第一目标：移动中的开发者与技术爱好者

典型任务：

- 在没有电脑时查看、搜索和修改项目文件；
- 运行小段 JavaScript/Python 或调用完整 CLI Runtime 处理数据、修复配置和生成产物；
- 审阅 diff、继续一个 Agent 会话、查看任务日志；
- 连接自有 API、自建模型或官方 CLI，而不是被单一模型订阅锁定；
- 在同一个任务中组合文件、网页、终端和 Android 能力。

他们愿意承担的成本：配置 Provider、安装 Runtime、理解目录和权限、为高价值工具付费。

他们不能接受的成本：必须连接电脑才能初始化、每次任务重复解释环境、失败后不知道改了什么、移动端只是桌面或云端的遥控器。

### 3.2 第二目标：Android 效率与自动化重度用户

这类用户已经理解 Tasker、Auto.js 类产品的价值，但不一定愿意继续手写脚本、维护选择器或调试复杂流程。

Helix 的机会不是原样兼容任意旧脚本，而是把常见意图变成可检查的任务模板：

- 处理下载目录、图片、文档和压缩包；
- 从网页或通知提取信息并生成本地结果；
- 打开 App 或系统页面并完成一段用户可见操作；
- 把一次成功任务保存成参数化模板，在用户触发时重用。

UI 自动化具有 ROM、App 版本和风控依赖，不能成为首个稳定价值证明。文件、网页和代码任务应在没有 Accessibility 的情况下也成立。

### 3.3 暂不作为第一目标的用户

- 只需要免费聊天和内容生成的普通用户；
- 期待“完全不用配置、永远不失败”的全民语音助手用户；
- 依赖抢购、群控、养号、自动支付或规避平台规则的自动化用户；
- 需要跨设备团队管理、云端 Worker 或企业集中管控的组织。

适老、无障碍辅助和大众生活服务可能有长期价值，但与当前开发者/效率用户的产品、支持和责任模型不同，不应混进首发定位。

## 4. 用户任务与购买理由

### 4.1 Jobs to be done

| 用户任务 | 现有替代 | Helix 应提供的增量价值 |
| --- | --- | --- |
| 手机上完成代码/文件任务 | Termux、AndCode、Operit、远程桌面 | 原生触控 UI、多 Provider、文件/网页/代码组合、无需先掌握终端 |
| 用自然语言完成 Android 自动化 | Tasker、Auto.js、Open-AutoGLM | 从意图到任务、过程可见、失败可诊断、成功任务可模板化 |
| 使用自己的模型和 endpoint | Chatbox、开源客户端 | 不止聊天，同一配置可驱动本机执行任务 |
| 在碎片时间继续工作 | 云端 Agent、桌面 Coding Agent | 手机本机工作区、持久任务状态、随时查看产物与下一步 |
| 使用 Root/All-files/Accessibility 等高级能力 | 脚本工具、Root 工具、零散插件 | 一个统一入口、逐能力启用、明确作用范围和状态 |

### 4.2 用户真正可能付费的部分

- 节省配置时间：安装后能较快完成第一个真实任务；
- 能力密度：文件、浏览器、代码和 Android 工具可以组合，而不是多个 App 拼接；
- 稳定性：任务失败有明确原因，升级后模板仍可维护；
- 高级能力体验：Runtime、Root、All-files 和 Accessibility 的安装、检测、修复与状态展示清楚；
- 持续维护：适配 Android/ROM 变化、Provider 协议和 Runtime 资产；
- 本机与 BYOK：用户不必购买平台转售的模型额度，也不必把文件上传到一个中转 Agent 服务。

“参数级审批”本身不是购买理由；它只有在减少误操作、解释失败和建立对 Advanced 能力的信心时才有产品价值。

## 5. 竞品带来的产品启示

### 5.1 Operit：能力密度和一体化工作台

[Operit 官方仓库](https://github.com/AAswordman/Operit)公开展示了 Android 系统、终端、浏览器、文件、项目工作区、本地/云模型、工作流以及 ToolPkg/MCP/Skill 市场的一体化形态。

值得借鉴：

- 任务、工具过程、工作区和文件变更在同一移动界面中呈现；
- 用户可以为不同用途选择不同模型；
- 终端、浏览器、设备能力和扩展市场共同构成“能力密度”；
- 语音、悬浮入口、默认助理和模板触发降低重复进入成本。

不直接照搬：首版同时建设工作流、市场、角色、记忆、本地模型和多种自动化后端会显著分散交付。Helix 应先用少量能力形成可靠闭环，再按真实使用数据扩展。

### 5.2 AndCode：移动 Coding Agent 的完成形态

[AndCode 官方仓库](https://github.com/yuga-hashimoto/and-code)已经把 PRoot、Git、文件树、diff、终端、会话、定时任务和 Coding Agent 做成触控优先工作台。

值得借鉴：

- Runtime 初始化隐藏在 Workspace 流程中，而不是要求用户先学习 Linux 环境；
- 文件树、diff、terminal、conversation 和 Agent 状态形成一个项目闭环；
- Full Access 等专家模式明确警告后交给高级用户决定；
- 语音、桌面组件和默认 Assistant 入口让 Agent 更像手机产品。

Helix 的机会不是只强调比它更严格，而是覆盖更广的本机任务：Provider 中立的原生工具、浏览器、Android 能力以及独立 CLI Runtime。能力尚未形成前，安全差异不能替代可用性差距。

### 5.3 ClawMobile：渐进开启能力

[ClawMobile 官方仓库](https://github.com/ClawMobile/ClawMobile)采用 app-local runtime 起步，再由用户开启 Termux、Android 控制和其他通道；重复 UI 操作还可以沉淀为可复用 Skill。

值得借鉴的是“渐进能力”产品模型：先让用户看到当前能做什么，再按任务引导开启更强能力。Helix 可把这一模型落实为能力中心，而不是在首屏堆叠所有权限说明。

### 5.4 Open-AutoGLM：自然语言驱动 GUI 的吸引力与限制

[Open-AutoGLM 官方代码入口](https://github.com/zai-org/Open-AutoGLM)代表视觉理解、规划和屏幕动作路线。它证明跨 App GUI 演示具有很强传播力，但这类系统依赖模型、屏幕状态、App 版本和执行后端，成功率不能从单次演示外推。

Helix 应把 GUI Agent 作为高吸引力的 Advanced 能力，但首发宣传同时提供失败边界：支持的 App/版本、是否需要用户接管、任务中断后哪些步骤已经发生。

### 5.5 Tasker、Auto.js 与 Hamibot：用户池和商业教育

传统自动化产品已经教育用户为“节省重复操作”付费，并验证模板、插件、脚本分享、定时触发和设备能力存在持续需求。[Hamibot 官方定价页](https://www2.hamibot.cn/pricing)也表明团队、独立部署和容量可以形成高于个人工具的商业层级。

Helix 可承接的是需求，不是直接兼容所有脚本：

- 从高频模板和自然语言配置切入；
- 允许用户查看参数、修改触发条件和手工运行；
- 先服务单设备个人场景，不加入云端群控；
- 只有稳定任务积累到足够规模后，才评估公开模板库或市场。

## 6. 产品定位与能力优先级

### 6.1 产品支柱

1. **本机执行**：文件、浏览器、轻量代码、完整 CLI 和 Android 能力尽可能在当前手机上完成。
2. **能力组合**：同一个 Agent 任务可以跨文件、网页、代码与 Android 工具，而不是只增加更多聊天功能。
3. **开放模型**：BYOK、多 Provider、自建 endpoint 和官方 CLI 登录由用户选择。
4. **Advanced 能力产品化**：All-files、PRoot/CLI、Accessibility 和 Root 有清晰安装、状态、测试、修复和停用入口。
5. **可观察执行**：用户能看到当前步骤、调用目标、输出、失败原因和产物；可观察性服务调试与控制，不作为第一宣传口号。

### 6.2 能力优先路线

| 阶段 | 用户可感知结果 | 不应提前扩张的内容 |
| --- | --- | --- |
| A：文件工作台 | 浏览目录、导入/导出、搜索、编辑、diff、trash 恢复 | 技能市场、复杂工作流 |
| B：网页与轻量代码 | 网页阅读/操作、下载、JS/Python 类短任务、产物回填 | 云端浏览器农场、远程 Worker |
| C：本机开发环境 | PRoot/CLI 安装、项目、Git、终端、Coding Agent | 未经验证的任意 CLI 与自动更新 |
| D：Android 自动化 | 系统 Intent、通知/日历、Accessibility、Root 工具 | 支付、认证、无人确认发送、群控 |
| E：复用与生态 | 私有任务模板、导入导出、版本与兼容性 | 在签名、审核和撤销机制前开放 UGC 市场 |

### 6.3 Standard 与 Advanced 的产品责任

| 责任方 | 责任 |
| --- | --- |
| 用户 | 选择模型与 Provider；开启 Advanced 和具体系统能力；决定 scope；备份重要数据；遵守目标 App、服务和内容条款；确认自己理解的高影响操作 |
| Helix | 不伪造能力或结果；不在用户关闭能力后继续执行；展示真实目标、scope 和数据去向；保留停止入口和任务结果；不允许模型替用户开启权限或生成用户批准 |
| 模型/Provider | 提供建议和 ToolCall；其输出默认可能错误，不获得设备权限或用户身份 |

Advanced 的体验目标是减少无意义摩擦，而不是把用户责任伪装成产品免责。[ADR-0012](../adr/0012-capability-first-advanced-grants.md)已接受 Trusted Workspace、动态风险不高于 L1 的有界长期规则和精确批量批准；`Full Workspace Access` 只表示较宽的用户所选文件 scope。模型自授权、全局自动批准和 L2/L3 永久放行仍被拒绝。

## 7. 产品体验建议

### 7.1 首次价值路径

首个会话不要只展示聊天。推荐路径：

1. 选择 Provider 模板或 OpenAI-compatible endpoint；
2. 运行连接测试并选择模型；
3. 选择一个示例目录或创建 Workspace；
4. 运行“分析目录并生成整理建议”；
5. 查看计划和 diff，确认后执行；
6. 展示结果、耗时、产物和可继续动作。

目标是让用户在一次引导中理解“模型 + 本机能力 + 可见结果”，而不是先阅读完整安全模型。

### 7.2 Advanced 能力中心

每项能力使用同一结构：

- 能做什么、典型任务和当前限制；
- 当前状态：未安装、未授权、可用、失效、需修复；
- 一键验证与最小 smoke；
- 需要的组件、存储、网络和电量成本；
- 启用、暂停、撤销和清理入口；
- 最近任务和失败原因。

### 7.3 模板而非脚本市场优先

首批模板由项目维护并随版本测试，例如：

- 整理下载目录但不立即删除；
- 批量重命名并预览冲突；
- 网页资料汇总到本地 Markdown；
- 检查 Git Workspace 并生成 diff；
- 从通知或日历生成本地待办草稿。

模板先保持参数化、有限节点和明确输入输出。积累任务完成率、兼容性和用户复用数据后，再决定是否开放创作者生态。

## 8. 商业化假设

### 8.1 可选模式

| 模式 | 优点 | 风险 | 当前判断 |
| --- | --- | --- | --- |
| 一次性买断 | 符合 Android 工具用户心智，决策简单 | 难覆盖长期 ROM/Provider/Runtime 维护 | 可作为早期 Founding/Pro license 实验 |
| 订阅 | 与持续更新、兼容性维护和支持匹配 | BYOK 用户反感“工具也按月收费” | 需要持续价值和用户访谈后验证 |
| 免费核心 + Pro | 降低试用门槛，能力分层清楚 | 免费/付费边界容易伤害信任 | 较适合；免费保留聊天和基础文件，Pro 对应高级 Runtime/自动化体验 |
| 模板/技能交易分成 | 有网络效应与创作者供给 | 审核、恶意能力、退款和兼容成本高 | 后期选项，不进入 MVP |
| 模型额度转售 | 上手简单 | 资金、合规、毛利和服务责任重 | 不作为主模式，优先 BYOK |
| 企业/团队版 | 客单价高 | 需要设备管理、审计和云控制面 | 当前单机范围外，只保留市场观察 |

不在没有成本数据时写死价格。定价实验至少记录：首次任务完成率、7/30 日留存、每周真实任务数、用户愿意付费的能力、支持工时、Runtime/资产维护成本和退款原因。

### 8.2 建议的付费边界假设

免费层可验证产品：多 Provider/BYOK、聊天、一个 app-private Workspace、基础文件读取和有限模板。

Pro 候选价值：多 Workspace、SAF/All-files 完整 UI、Browser Agent、高级模板、PRoot/CLI Runtime 管理、Git/diff、Accessibility/Root 能力中心、定时任务和更长历史。最终边界必须等对应能力真实交付后再定，不能预售路线图。

## 9. 分发与获客

### 9.1 冷启动渠道

- Google Play 与国内 Android 应用商店：Standard 作为完整产品提交，按 [ADR-0013](../adr/0013-standard-store-capability-preserving-distribution.md)只做有政策证据的最小渠道差异；
- GitHub：源码、release、路线、可复现 demo 和 issue 反馈；
- 官网：一句话定位、能力矩阵、安装方式和短视频；
- 酷安、V2EX、开发者社区：发布真实任务演示，不用概念宣传；
- 视频平台：展示完整任务，包括配置、等待、失败和结果，不只剪成功点击；
- 小范围测试群：收集设备、ROM、Provider 和任务模板证据。

### 9.2 最有效的演示内容

1. 手机本地分析一个真实项目并生成可审阅 diff；
2. 从网页收集资料、下载文件、运行处理代码并输出报告；
3. 在 Advanced 中安装 Runtime、验证能力并完成第一个 CLI 任务；
4. 展示同一任务在中断后如何继续，而不是重新执行全部动作；
5. 展示一个 Android 自动化任务的支持范围、用户接管和失败处理。

## 10. 需要验证的市场假设

| 假设 | 最小验证方式 | 通过信号 |
| --- | --- | --- |
| 开发者愿意在手机上完成真实文件/代码任务 | 10～20 名目标用户完成固定任务 | 多数无需电脑协助完成并愿意再次使用 |
| 用户愿意配置 BYOK 换取开放模型 | 观察 onboarding 漏斗 | Provider 配置不是最大流失点，或模板能显著改善 |
| Advanced 用户接受自己承担设备操作责任 | 风险说明 + 任务访谈 | 用户理解开启能力的影响，仍认为价值高于风险 |
| 文件/浏览器/代码组合比纯聊天更有价值 | 比较首周使用频率 | 真实工具任务带来更高复用率 |
| 买断或 Pro 分层有支付意愿 | 不收款价格页/候补名单或封闭测试访谈 | 用户能指出愿意付费的已交付能力，而非只支持概念 |
| 模板可以替代脚本学习成本 | 维护 5～10 个官方模板 | 模板重复使用且参数修改不需要作者介入 |

## 11. 产品指标

### 激活

- 安装到 Provider 连接成功；
- 安装到第一个本机任务完成；
- 第一个任务中需要的配置步骤和失败次数；
- Advanced 能力安装/授权/验证完成率。

### 能力与质量

- 固定文件、网页、代码和 Android 任务的端到端完成率；
- 用户接管率、失败原因分布、结果未知比例；
- 同一模板跨版本、ROM 和 Provider 的成功率；
- 任务耗时、内存、发热、电量和后台存活。

### 留存与商业

- 7 日/30 日仍完成真实工具任务的用户比例；
- 每周完成任务数与重复模板使用率；
- 各能力被启用、停用和修复的频率；
- 免费到 Pro 的意向、实际转化、退款和支持成本。

安全指标仍作为底线门禁，但不取代激活、任务完成率和留存：模型自行放权、关闭能力后仍执行、把失败显示为成功等事件必须为零。

## 12. 本轮建议

1. 当前产品叙事从“安全型本机 Agent”调整为“能力优先的 Android 本机执行工作台”。
2. 优先交付[实施状态](../development/status.md)中的下一项文件工作台闭环，并把首次真实任务作为演示和激活指标。
3. 竞品重点增加 Operit、Tasker/Auto.js/Hamibot 和 Open-AutoGLM；AndCode/ClawMobile继续作为直接 Runtime 对照。
4. Advanced 的产品目标是减少高级能力安装与使用摩擦；developer 只是当前开发测试构建，不作为用户等级。用户承担主动开启和确认后的操作责任，产品承担真实展示和不越权责任。
5. 先发布维护方提供的任务模板；Tasker 插件桥接、Auto.js/AutoJs6 任意来源脚本导入与兼容 Runtime 作为后续研究，不放进 MVP，也不承诺任意脚本零差异执行。
6. 商业化先验证免费核心 + Pro 或早期买断，不写死价格，不依赖模型差价。
