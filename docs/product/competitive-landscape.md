# Helix 移动 Agent 竞品分析：决策总览

更新日期：2026-09-08。文档性质：产品研究与待验证策略，不是 APK 横评结果、市场份额报告或新增开发授权。核验批次见[证据记录](competitive-evidence.md)。

## 1. 执行摘要

Helix 面临的已不是“手机上有没有 Agent”，而是用户能否更省事地完成任务。现有竞品已覆盖原生工具工作台、Linux harness 一键安装、手机 GUI 控制、远程开发和系统助手。**原生、BYOK、MCP、工具确认本身都不足以形成独有优势。**

建议继续聚焦：**无需电脑、连接自己的模型、组合手机文件/网页/代码与受授权 Android 能力，并交付可检查结果的本机工作台。**这是细分价值主张，不是通吃办公、离线 AI、云端开发和全民系统助手。

三个主要判断：

1. 最近的产品压力来自 Operit、PalmClaw、RikkaHub、AndCode、PocketCode 与 DSHA：分别考验能力组合、原生执行、聊天入口、开发闭环与安装交付。依据见[直接竞品档案](competitive-direct-agents.md)。
2. Helix 的分域执行、统一授权和持久对账有工程价值，但只有转化成低摩擦任务完成、可理解失败和不重复副作用，才可能形成用户优势；当前没有同条件胜出证据。
3. 应优先补“任务体验、设备/发布验证、常用扩展可用性”的证据，而不是按竞品功能列表扩充 Runtime、工作流和跨设备范围。

## 3. 竞争格局：按用户替代关系分组

| 用户想完成什么 | 可选路线 / 代表对象 | 路线的合理优势 | Helix 需要证明什么 |
| --- | --- | --- | --- |
| 手机内完成文件、网页、代码任务 | Operit、PalmClaw、RikkaHub、Helix | 原生 UI 与工具组合，设备随身 | 同任务完成成本与结果正确性 |
| 安装现成 Agent/Linux 生态 | DSHA、deepcode-lab、BotDrop、Termux | 复用引擎与依赖，配置灵活 | 按需 Runtime 的安装/兼容取舍值得接受 |
| 手机修改代码项目 | AndCode、PocketCode | 项目、diff、终端等垂直交互 | 是否需要完整 IDE，还是小任务足够 |
| 随时管理电脑上的开发任务 | Happy、HAPI、AndCode 远程路径 | 利用已有电脑、依赖与算力 | 没有电脑时本机价值；不承诺重型替代 |
| 让手机界面完成操作 | ClawMobile、GUI 社区 App、DroidRun 等 | 跨 App 视觉/结构化控制 | 限定 App 上的可停止、可复核与恢复 |
| 快速问答、离线或固定重复任务 | Chatbox、PocketPal、Automate/Tasker | 配置低、离线或确定性成本低 | 值得使用 Agent 的非固定任务 |
| 系统与业务一体化服务 | 小艺、Gemini、YOYO 等 | 预装入口、系统权限、服务合作 | 以开放模型和工作区切入，避开入口正面竞争 |

这些是不同需求，不合成“谁最强”总分。手机有界面、Loop 在手机、工具在手机、模型在手机是四个独立事实。详细条目均标明公开声明与限制，不用“真/假 Agent”二分。

## 4. Helix 的优势、短板与适用边界

### 4.1 有依据的工程特点与待证明收益

| 工程特点（以状态/架构为依据） | 可能的用户收益 | 成立条件与代价 |
| --- | --- | --- |
| 原生 Tool、isolated QuickJS、独立 PRoot 按任务分层 | 常见任务不必启动完整 Linux | 测冷启动、峰值内存、总完成时间；多 APK、快照有成本 |
| 模型协议与工具执行分离 | 可换 Provider、自建 endpoint | 模型工具/视觉能力不同，不保证结果等价 |
| 一致的 scope、批准、结果与对账路径 | 中断后知道做了什么，减少误重试 | 需要故障注入、真机和用户理解度证据；审批过多会损害收益 |
| 本机文件、网页与 Android 工具组合 | 从输入到产物留在一个工作台 | 与 Operit/PalmClaw 等重合，不是单项独有能力 |

这些来自[架构](../architecture/overview.md)及[状态记录](../development/status.md)，不是对竞争产品内部实现的反向推断。“未披露精确批准”不能写成“竞品没有安全机制”。独立 UID 不是 VM，PRoot 本身不是安全沙箱，本机执行也不等于数据不出网。

### 4.2 当前最重要的短板

- **交付成熟度证据不足**：物理 OEM、长稳、Root、部分受保护服务和发布门禁仍需分别闭合；没有可比较的用户留存与首个任务成功率。
- **Linux 兼容有取舍**：固定资产、无网 PRoot 不等于可任意 apt/npm 的联网 Debian/Ubuntu；复杂依赖、大仓库与常驻服务不能默认兼容。
- **安装与恢复复杂度**：主 App/companion 的版本、签名、安装、登录和修复增加维护与交互成本；分层清晰不保证更快更轻。
- **办公格式和产品范围受限**：文本/图片已支持；PDF/PPT/DOC、音频/视频仍仅预留，不宣传为全面办公文档助手。Git Spike 不等于完整 Git 产品。
- **生态不等于协议数量**：Skill Creator/Installer、MCP Installer 已在状态记录中完成分项验收；这不证明所有真实服务可用或已有成熟市场。订阅 Runtime 是第三方协议适配实验，不是完整官方 CLI，也不等于服务商认可。

### 4.3 哪些场景不应强行竞争

真正离线推理优先看本地模型产品；大仓库/长编译可由远程开发方案更好服务；固定触发操作可能用确定性自动化更便宜；预装生活服务入口是 OEM 的合理长项。Helix 更有希望赢得“手机随身数据 + 开放模型 + 跨工具小任务”的选择，仍是待验证假设。

## 5. 产品应对建议

以下是研究优先级，不是 HXA 排期或实现承诺。

| 优先级 | 要验证的问题 | 建议产出 | 暂不做什么 |
| --- | --- | --- | --- |
| P0 | 初次用户能否独立完成首个本机任务 | 同机首装录像、步骤数、失败归因、正确产物 | 不继续堆通用工具数量 |
| P0 | 停止/断网/回收后是否能理解并安全继续 | 原任务结果对账与重复副作用记录 | 不把后台自动重启当作恢复成功 |
| P1 | 常用 Skill/MCP 与依赖是否可用 | 固定版本兼容清单、安装/启用/修复反馈 | 不宣称任意插件一键兼容 |
| P1 | 开发者真正需要哪些工作台交互 | 与 AndCode/PocketCode 的小项目对照 | 不默认扩成完整 IDE |
| P1 | 能力中心是否足够低摩擦 | 状态、安装、授权、验证、修复和停止的用户测试 | 不增加无证据的重复警告 |
| P2 | 官方模板能否促进再次使用 | 文件/网页/系统接口模板的复用记录 | 不先开无边界技能市场 |

首批横评六个对象；第二批围绕安装增加 BotDrop、GUI 增加 ClawMobile、替代路径选 Happy/HAPI、PocketPal、Automate。QSH36/DroidClaw 保持早期观察；DroidMind/Mobile Next 是技术参照，不能因出现 MCP 就成为 Helix 的已选依赖。具体方案见[横评计划](competitive-evaluation.md)。

## 6. 定位与对外表述

建议：“Helix 是 Android 本机 AI 执行工作台，连接你的模型，将手机上的文件、网页、代码和受授权设备能力组合成可检查的任务结果。”

可以解释开放 Provider、按需执行域、产物与恢复；避免“首个/唯一 Agent”“全离线”“任意 App”“全部可回滚”“官方 CLI 全兼容”及“已通过商店审核”。Standard 的完整产品定位和渠道差异按有效 ADR 与实际 artifact 判断，不把目标当发布事实。

## 7. 本轮补充与判断变化

新增 BotDrop、QSH36/DroidClaw、unitedbyai/droidclaw、DroidMind、Mobile Next，分别填补部署引导、早期综合工作台、GUI 控制、设备诊断 MCP 和跨平台测试 MCP。详情和一手来源在主题档案中。

重新核验 AndCode 的本机/远程双路径、ClawMobile 的 Android/iOS 能力区分，以及 AppFunctions 的实验准入。它们共同说明：**执行位置、渠道和权限条件必须按产品模式拆分，而不能按品牌打勾。**

## 8. 后续跟踪指标

详细定义统一在[评估方法](competitive-evaluation.md)。核心指标为首次任务成功率、首次价值时间、人工接管、自助恢复、结果正确性、重复副作用、资源成本及 7/30 日真实任务留存。安全/发布硬门禁仍见[安全与发布](../security/testing-and-release.md)，不由竞品得分抵消。

价格、套餐、活跃用户与市场规模本轮均未测量；不使用 star/下载数字代替，不给出伪精确排名。
