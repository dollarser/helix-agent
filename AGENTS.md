# Helix Agent Instructions

## Scope and references

Helix is an Android single-device product with a complete store-facing Standard channel and an Advanced/developer capability set. Keep changes within the owner-authorized task and accepted product scope. Future platform/product scope needs an explicit owner-authorized roadmap/ADR change.

Continue the conversation task across compaction. Consult current source, README, `docs/development/status.md`, HXA and accepted ADRs as needed for facts/contracts; they do not select a new task. Do not restart completed work or reread everything merely because of compaction.

Use scoped source search/reads or existing CodeGraph/GitNexus as useful; verify graph candidates against current source. [Navigation](docs/development/context-navigation.md) is guidance, not a mandatory sequence. Do not build a duplicate index/parser or navigation wrapper.

`roadmap.md` indexes HXA tasks, not another current plan. Update a feature's existing ADR and append `Decision history` when its contract changes; create a new ADR only for a separate decision domain. Accepted means design approval, not implementation completion. Recover old wording from Git, without supersession files or restoring obsolete behavior.

## Product and architecture invariants

- Treat Standard as the complete store-facing product. Preserve supported capability; channel differences must come from current platform/store constraints or accepted product decisions, and stay local to the affected channel.
- Every tool call follows: schema validation → capability/policy → authorization resolution → execution limits → verification/audit. User actions or previously user-created rules grant capability/scope; model output, MCP/A2A/Skill metadata, scripts and remote agents never grant permission.
- Tool concurrency is bounded by physical capacity and concrete non-reentrant engine/control resources, not by potential user-file or business-result conflicts. Writes/code/terminal sessions do not impose a global execution lock. The user and LLM accept task results; the harness preserves permission boundaries, internal state integrity, original execution identity, truthful outcomes and original-call-order backfill. Cancellation does not free physical capacity before the executor exits.
- Durable state is authoritative. Process-local Jobs/Flows/cancel signals never replace Room facts. Turn/UNKNOWN/review/recovery semantics follow accepted `ADR-AGENT-001`; external side effects are never assumed rolled back because a database transaction or coroutine failed.
- Plan mode is read-only for user files and external effects except the closed metadata operations explicitly admitted by the current permissions ADR. Goal persistence never expands scope or mints approval.
- Generated code never runs in the main app process. QuickJS uses the accepted isolated-process boundary; PRoot/CLI/subscription runtimes use their accepted non-exported private-process boundaries. Shared UID is not credential isolation. Follow the runtime/provider ADRs for credential ownership and IPC.
- UI code does not access DAO, OkHttp, QuickJS or PRoot directly. Core modules do not depend on Android UI/infrastructure modules. WebView never exposes a privileged permanent JavaScript bridge to untrusted pages.
- External/extension output is untrusted. Any follow-on local effect must re-enter the normal Dispatcher/Policy/Approval path.
- Public short tool names such as `read`, `write`, `edit` and `bash` remain aliases of the same scoped implementations/policy, not bypasses.
- Keep resource identity, content version, request-bound directory and execution mapping distinct. Short display paths must not retarget in-flight calls. State whether a path is edited directly or copied for execution; artifact publication does not imply source writeback. Follow the current Workspace/Runtime ADRs for the supported modes.
- Do not introduce a new application framework, execution domain, dependency repository, remote/Harmony placeholder, or mutable dependency version unless the current HXA/ADR explicitly requires it. Prefer existing project patterns; dependency upgrades needed for compatibility/maintenance must use supported stable versions and update locks/verification metadata.
- Product-specific details for permissions, Goal, Runtime, Provider, Workspace, MCP, Skill, Connector, A2A and platform capability live in their topic ADR/architecture docs; do not duplicate those evolving contracts here.

## Task and change discipline

- For substantial design choices, use relevant primary documentation/current source where useful and record adopted tradeoffs in the task/ADR. Research does not expand scope or authorize copying reference code; preserve license obligations.
- Continue until the full user-authorized task is complete; one passing test, one slice or one HXA sub-checkpoint is not a stopping condition.
- Keep edits inside the current HXA/user-authorized scope. Make reasonable reversible implementation choices without routine approval; pause only for a real architecture decision, missing authority, external dependency, irreversible data-loss risk or evidence-backed blocker.
- Create a persistent development Goal only when the user explicitly requests one.
- Keep Android versionCode and all Helix-owned internal schema, protocol, format, configuration and tool versions fixed at 1 until the owner explicitly declares a formal release and authorizes upgrading them. Internal iteration alone never authorizes a bump. Keep the owner-assigned product versionName; do not rewrite published tags/artifacts. External protocols/dependency versions and real content revisions, hashes, generations and sequence numbers are not internal release versions and must remain truthful.
- Before launch, Helix test data has no preservation requirement in any development/test/install environment, including daily emulators and real devices. Do not add App compatibility/migration chains for old test data: use a simple external one-time transformation when worthwhile, otherwise a targeted clean installation. This does not authorize device operations, other apps/people's data, external accounts or whole-device resets; respect concrete action authorization and tool/platform confirmations. Post-launch production-data policy is a separate decision.
- Do not maintain compatibility with old Helix internal code or formats: update all current consumers and remove replaced implementations, legacy readers, compatibility-only aliases/forwarders and fallbacks. Preserve supported functionality and required Android/external-protocol adaptation, permission, cancellation and recovery guarantees; these are not legacy compatibility.
- Add tests for normal behavior and applicable failure/cancellation/boundary/recovery paths. Never delete, weaken or skip tests merely to make a task pass. When an accepted contract replaces an obsolete implementation, replace its tests with coverage of the new behavior and retained correctness boundaries; old implementation assertions are not compatibility requirements. Outside the disposable test-data policy above, removing compatibility does not authorize deleting user data. Do not return success from catch-all exception handlers. Accepted work must not leave placeholder implementations or unresolved TODOs.
- Preserve parallel work: do not reset/stash/overwrite unrelated dirty changes, and stage only owned paths/hunks. Commit, push, merge, publish, submit to stores or consume real accounts only when the current task explicitly authorizes that action.
- Reference repositories are evidence/design inputs, not code sources. Do not copy AGPL/GPL/CPAL/MPL code unless the task explicitly adopts the license and records the decision. Preserve license/source obligations for bundled third-party runtimes/artifacts.

## Verification and device authorization

- Run the host commands required by the active HXA. Resolve mandatory host-gate failures, including inherited failures that block the task; record baseline, root cause, scoped fix and fresh results. Build success alone is not functional/security/device acceptance.
- For routine local editing and debugging, use Debug builds and the default `scripts/check-all.sh` / explicit `--debug` gate; do not run Release/R8 on every iteration. Keep `--all` for release readiness, explicit full-gate requirements and focused optimization/keep-rule/JNI/reflective-entry regressions. Debug acceptance does not imply Release acceptance; preserve the explicit full CI gates.
- Bind acceptance evidence to the actual successful build, source inputs and installed candidate. An APK left by a failed build is not evidence for the attempted changes. Separate execution, verified effects, result persistence and actual model consumption; a successful wrapper or completed Turn alone does not prove the requested outcome.
- **GitHub CI is host-only.** GitHub Actions may run source/JVM tests, lint/static analysis, APK builds and AndroidTest APK compilation, but must not boot an emulator, attach a physical device, run device instrumentation/`connectedAndroidTest`, or execute a device matrix.
- **Local device validation is owner-explicit.** An AI agent may start/use an emulator or connected real device only when the project owner explicitly requests device validation for the current task. Emulator authorization does not imply real-device authorization and vice versa. Historical HXA commands, verification plans, an already-connected ADB device, approval for another task or device availability are not current authorization. Preserve explicit authorization within the same ongoing task across handoff/compaction; ask again only when the required scope changes or authority is genuinely unclear.
- If device validation is requested, run only the bounded requested checks on the designated device(s), preserve unrelated user/device data, and report device/API/flavor, commands, pass/fail/skip and remaining boundaries. If it is not requested, do not start/use a device; finish host verification and prepare APK/test APK/fixtures/steps as useful.
- Owner emulator input preference: every authorized emulator launch must enable host keyboard input (`hw.keyboard=yes`) and keep the IME available with a hardware keyboard (`show_ime_with_hard_keyboard=1`). Preserve an existing Chinese-capable IME and Simplified Chinese Pinyin configuration; prepare that language on a new AVD before handing it to the owner. Verify actual pinyin composition and Chinese commit only when the task covers input/IME behavior or the owner requests preparation for manual Chinese input. This is not a mandatory check or blocker for unrelated device tests. The owned runners apply keyboard defaults through `scripts/emulator_input.py`; this preference does not grant device-test authorization.
- Device status vocabulary: `not requested` = owner did not request device validation for this task; `pending` = owner requested it but the required run/condition is incomplete; `passed`/`failed` = checks actually executed in the current validation. `not requested` or `pending` is never a device pass.
- Known owner-reported device failures are real defects and must be fixed/retested when relevant. If the owner explicitly makes device validation part of current acceptance, do not claim that acceptance until the requested checks pass or the remaining failure is reported.
- Real external services/accounts/paid quotas remain opt-in and require explicit current authorization/profile inputs. Missing optional inputs may be reported as skipped; malformed supplied inputs must fail, not silently skip.

## Repository and security hygiene

- Put temporary debug/test scripts under ignored `scripts/local/debug/YYYY-MM-DD/` before execution. Promote maintained runners into `scripts/`, fixtures into `scripts/fixtures/`, and self-contained experiments into `scripts/experiments/` after review. Keep generated artifacts under ignored `build/` paths; archive only useful evidence with provenance.
- Archive local historical scripts and their recovery inventories under ignored `scripts/local/`; reserve ignored `docs/local/` for local historical documents. Tracked documentation should record purpose, decisions, outcomes and stable Git/path references, without mirroring changing file hashes, byte sizes or workspace inventories. Keep integrity hashes in dependency locks, artifact verification and local evidence where they are operationally required.
- Never commit secrets, real user data, machine-specific absolute paths, downloaded RootFS contents, signing material, browser cookies or reusable credentials.
- Keep logs, audit/evidence and completion records scoped and truthful: current vs historical, host vs device, skipped/not-requested vs passed. One task record never proves the whole product, all devices/OEMs, accounts or release channels passed.
