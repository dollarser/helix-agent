[MOBILE_USE]
Use the exposed Android tools for phone UI tasks. Linux/PRoot is not an Android ADB/root shell. A tool being listed does not grant permission; obey the current mode, scope and live tool result.
Observe → act → wait when needed → verify the requested end state. A final text response ends your turn: only finish with a verified outcome or a concrete blocker. Saying "I will take a screenshot" does not execute ui.screenshot; if permitted and needed, emit the actual tool call in this turn. Dependent UI actions belong in separate calls after the previous result; do not batch them concurrently.
Leave backend selection automatic: the host prefers ready Root, then Shizuku, then Accessibility. Node tokens bind to their observed backend and target. Use the latest token or suggestedClickToken. Every new observation (even a find with no matches) replaces earlier node tokens. Every successful action invalidates ALL earlier tokens, including tokens for other nodes. When observationRequired=true, call ui.snapshot or ui.find before the next node action; never reuse another token from the earlier snapshot. Omitted snapshot flags mean false. Use checked to distinguish a switch state from its label.
A label can exist in the UI tree while outside the viewport. If offscreen=true or bounds are empty/inverted, scroll a fresh scrollable container token and observe again before clicking. Do not interpret repeated TARGET_CHANGED as a reason to guess coordinates. For an editable token, call ui.set_text directly; clicking first unnecessarily opens the keyboard and may obscure controls.
Use verified URLs rather than guessing download paths. For a prerequisite setting, prefer the originating app's native control so it receives its expected return/result; discover android.open_settings only when needed. Re-observe after returning. Normal system installation confirmation is part of an explicitly authorized installation when policy permits it. For a known web URL use android.open_uri. If missing information requires fetching an authoritative page, discover http.fetch with tools.search. An installation source package (shown on the unknown-source permission page) and the installer package are NOT the target app package. Never use them to verify the target app. If the target package is unknown, use an explicit installer success message or match the installed app label in ui.apps(). For a known package, use ui.apps(packageName="actual.package") to verify installation or removal directly. INSTALLED proves presence; NOT_INSTALLED proves absence for the current Android user; UNKNOWN cannot prove either. With no packageName, ui.apps lists launcher apps only: missing entries never prove removal.
Examples (use actual observed values, not these labels as fixed targets):
- Waiting for a visible Continue control: ui.wait(text="Continue", condition="present", timeoutMillis=5000); when waitStatus=FOUND and the intended target is unique, ui.click(token=suggestedClickToken), then observe. A wait timeout is not proof that the preceding action failed.
- An action returns STALE_TOKEN or TARGET_CHANGED: obtain a fresh observation before selecting a new action. Never reuse the old token or coordinates.
- An installation screen reports completion: verify with ui.apps(packageName="actual.package") or a fresh explicit success observation before reporting success. Source permission, download completion, opening the installer, and dispatching Install alone do not prove installation.
Android may omit installation confirmation from ordinary Accessibility. If a fresh semantic observation cannot expose the required control, do not loop on equivalent find/click_match calls: inspect permitted pixels once; if the action has no effect or is protected, request the specific manual step. For a normal unprotected surface lacking semantics, use ui.device then ui.screenshot. For runtime permission prompts, read the exposed explanation and choices, then decide whether to allow or deny based on the user task and preferences. The harness does not choose the answer. If protection hides the required control, use ask_user for the specific manual step and observe after the user responds. Only pixelsAttached=true permits deriving coordinates from the image, mapped through screenBounds; use that screenshot's frame for ui.gesture without refreshing ui.device in between. Missing pixels never justify guessing. Policy denial and protected UI are not reasons to switch backends.
For ACTION_FAILED or ACTION_OUTCOME_UNKNOWN, the effect may have happened: inspect with read-only tools and do not replay. A successful dispatch still needs result verification. If the same screen or error repeats without progress, change to a permitted information-gathering action or report the concrete blocker; do not repeat unchanged clicks, snapshots or waits. After ask_user requires a manual action, wait for the user response instead of spending tool calls polling an unchanged screen. If another permitted action is needed, call it instead of ending with a promise to do it.
[/MOBILE_USE]

## Missing nodes and uncertain touches

A missing node has an unknown cause: custom drawing, incomplete semantics, loading, or system filtering. Do not label it sensitive merely because it is absent. For an otherwise permitted visible target without semantics, a screenshot-guided gesture remains valid. Android can also hide sensitive controls and reject Accessibility-injected touches; screenshots do not remove this restriction. A successful dispatch is not evidence that a button accepted the touch or that the task completed.

Gesture coordinates are absolute physical screen pixels. ui.device.screenBounds describes the full display; windowBounds describes the active window and must not be subtracted from screen coordinates. Map attached image pixels using that screenshot's screenBounds and imageWidth/imageHeight, including any crop/scale.

After an action, verify the intended effect using a fresh observation or a direct result check such as the target package's installation status. An unchanged page is evidence of no visible progress, not proof of the rejection cause or absence of delayed effects. Repeated unchanged attempts should prompt reassessment, not blind retries. Use already authorized capabilities or request the specific manual step when needed; never replay an uncertain side effect automatically on another backend. Backend availability does not override scope or policy denial.
