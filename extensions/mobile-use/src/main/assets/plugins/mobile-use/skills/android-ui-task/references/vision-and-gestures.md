# Vision, gestures and transient content

Common gestures use the same `ui_gesture` authorization and single-use screenshot frame. Supply exactly one of `pattern` or raw `strokes`. For example, with an observed center at (500,500), pinch out is `pattern={"kind":"pinch","center":{"x":500,"y":500},"span":160,"scale":2,"durationMillis":400}`; rotate uses `kind="rotate", span=160, degrees=90`; a three-finger swipe uses `kind="swipe", center, to, fingers=3, spacing=48`. Use real image coordinates, not these illustrative values. `tap`, `double_tap` and `long_press` take `center`; generated paths outside the grant are rejected rather than clipped. OEM three-finger screenshot recognition is separate from delivering three fingers.

## Missing nodes and uncertain touches

For the current phone screen, call ui_device and pass its exact frame to ui_screenshot and use its attached pixels with the existing conversation screen grant. view_image can reuse that grant when the host verifies exact bytes from a trusted screenshot in the same conversation and the original grant remains active. Filenames do not establish provenance; other images follow the ordinary disclosure workflow. Reopening a file does not refresh the phone screen. If pixels were omitted, inspect the stated reason and use a fresh authorized screenshot; do not claim a picture was seen from its filename alone.

A missing node has an unknown cause: custom drawing, incomplete semantics, loading, or system filtering. Do not label it sensitive merely because it is absent. For an otherwise permitted visible target without semantics, a screenshot-guided gesture remains valid. Android can also hide sensitive controls and reject Accessibility-injected touches; screenshots do not remove this restriction. A successful dispatch is not evidence that a button accepted the touch or that the task completed.

Gesture coordinates are absolute physical screen pixels. ui_device.screenBounds describes the full display; windowBounds describes the active window and must not be subtracted from screen coordinates. Map attached image pixels using that screenshot's screenBounds and imageWidth/imageHeight, including any crop/scale.

After an action, verify the intended effect using a fresh observation or a direct result check such as the target package's installation status. An unchanged page is evidence of no visible progress, not proof of the rejection cause or absence of delayed effects. Repeated unchanged attempts should prompt reassessment, not blind retries. Use already authorized capabilities or request the specific manual step when needed; never replay an uncertain side effect automatically on another backend. Backend availability does not override scope or policy denial.

For a user-requested launch of a known package, ui_apps is not a mandatory preflight. Acquire a fresh ui_device frame after launch. TARGET_UNAVAILABLE capture flags describe the missing target, not permanent backend support. A requested screenshot requires ui_screenshot and actual attached pixels; node text alone does not fulfill it. For a read-only screenshot task, additional semantic observations are needed only when pixels are unclear or interaction needs nodes. Refusal never authorizes wider scope or another backend.

A privileged screenshot returns a new frame bound to its window/display coordinate environment: use the output frame, not its input. Observe once, execute one explicit action, then verify the result. Coordinate actions do not take another screenshot or compare pixels/tree content before dispatch, so moving video and transparent controls remain actionable. Each new DOWN checks authorization and window/display identity; it does not require stable content. A same-window custom layer can change the recipient of the touch. A window/mapping refusal before the first DOWN dispatches no input; a refusal after an earlier tap is an unknown partial outcome and must not be replayed.

## Transient content and sampled observations

For changing visual content, ui_screenshot accepts count=2..4 and intervalMillis=500..3000 (default 1000). One call captures serially on the device, waits that interval after each capture, and returns an indexed contact sheet through the normal vision path; no model request occurs between samples. Read samples in index order. Request start/end times and monotonic offsets describe actual capture intervals, not media presentation timestamps or guaranteed frame rate. The sequence has a 15-second deadline and discards unpublished frames on cancellation, target/mapping changes or capture refusal. The sheet has no gesture frame or screen mapping: obtain a fresh single screenshot before acting.

Sampling starts when this tool executes. It cannot recover video that ended during the preceding model round trip, and it captures no audio. If a short clip keeps ending before observation, repeating device/find/click/screenshot may miss it indefinitely. Inspect available authorized playback controls and use an explicit pause, seek or replay only when appropriate to the user's task and observed player state, then observe; do not blindly replay uncertain actions. A phone workflow reminder is not proof of failure: continue if each cycle adds useful evidence, otherwise change the method or report exactly what remains unseen. Do not claim complete transcription from sparse samples. Small text may be reduced in a sheet; use a single paused-frame screenshot when detail matters.
