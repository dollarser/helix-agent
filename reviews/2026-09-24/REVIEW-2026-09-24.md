## 二、新发现（全文收录各审查线报告）

### 2.1 运行时/工具/扩展模块 bug 排查（上次未覆盖范围）

*执行方式：按模块派 5 个只读审查代理并行通读；quickjs 代理完整交付，其余 4 个因 API 400 中断，其中间转录的候选发现经逐条到源码核实文件:行号与失败场景后收入，核实不成立或被降级为设计决策的已剔除。*

**统计：13 条——CONFIRMED 10、PLAUSIBLE 3；高 0 / 中 6 / 低 7。**

#### 中严重度

**#1（中 / CONFIRMED ✅抽查）quickjs 超时预算从 bind 之前起算，冷启动 bind 耗时吃掉 JS 执行时限**
- 位置：`runtime/quickjs/.../JsExecutionClient.kt:106`（`deadlineNanos = System.nanoTime() + timeoutMs` 在 `prepareTransport`/bind 之前计算）＋ `JsServiceValidation.kt:20`（service 端收到 EXECUTE 时 deadline 已过直接 REQUEST_REJECTED）
- 失败场景：`timeoutMs` 取下限 100ms 时，EXECUTE 到达 service 时 deadline 必然已过，**每次执行稳定返回 REQUEST_REJECTED "deadline already expired"，JS 根本没跑**；即使默认 10s，bind 3s + JS 跑 8s 也会误报 TIMEOUT
- 修法：deadline 计算移到 bindInstance 成功之后，或让 service 收到 EXECUTE 时用自己的 nanoTime+timeoutMs 重建 deadline

**#2（中 / CONFIRMED ✅抽查）JS 工具实际输出上限 64KiB，工具契约宣称 256KiB**
- 位置：`runtime/quickjs/.../tool/CodeJavascriptRunTool.kt:221-229`（构造 `JsExecuteParams` 从不传 `outputFile`）＋ `JsExecutionService.kt:380-389`（无 output PFD 且超过 `PARCEL_INLINE_MAX_BYTES`=64KiB 时 fail-closed 为 OUTPUT_LIMIT）
- 失败场景：全仓唯一生产调用方不传 outputFile，结果只能走 inline parcel；模型生成的 JS 合法返回 100KiB JSON → 过 `maxOutputBytes`（256KiB）检查、被 64KiB inline 上限拒绝 → 工具失败且按工具说明重试必再失败
- 修法：工具侧传入 app 私有临时文件作 outputFile（成功后读回、finally 删除），或把契约上限改为 64KiB

**#3（中 / CONFIRMED ✅抽查）proot job 运行期异常路径不杀进程组，孤儿进程无任何回收机制**
- 位置：`runtime/proot-app/.../ProotJobRunner.kt:526-545`（catch 块）＋ finally 段（~546-553）
- 失败场景：`runJob` 的 `catch (e: Exception)` 在进程仍存活（`process.isAlive`）时只调 `terminalFailed` 记 FAILED，从不调 `killProcessGroup`；`finally` 又取消 per-job watchdog 并 `liveJobs.remove`——之后进程再无任何 kill 机制。进程启动后、终态处理前抛异常（如 `ProotJobNotification.postRunning` 抛远程异常、长 `waitFor` 被 InterruptedException）→ 记录为 FAILED，但 proot 进程组带着完整 rootfs 继续跑，脱离看门狗/孤儿扫描（扫描只在 service 重启时跑）
- 修法：catch 路径中 `live?.process?.isAlive == true` 时先 `killProcessGroup(childPid)` 再 terminalFailed

**#4（中 / CONFIRMED）proot 终端容量按"未 ACK 记录"计数，陈旧记录可永久锁死终端启动**
- 位置：`runtime/proot-app/.../ProotTerminalHost.kt:42-44`（`activeRecords = records.filter { !it.reconciled }`，`>= MAX_SESSIONS`（=2，:175）即 CAPACITY_EXHAUSTED）＋ `proot-core/.../PtySessionRecord.kt:128`（只有 acknowledge 才 `copy(reconciled = true)`）
- 失败场景：容量上限算的是未 reconcile 的记录而非活着的会话，而记录只有客户端 ACK 才 reconcile——app 在 stop 之后、ACK 之前死亡留下的记录永远占位；累计 2 次后任何新 `start` 都返回 CAPACITY_EXHAUSTED，直到用户逐个查询并 ACK 旧记录
- 修法：容量只计 in-memory 活跃会话＋有活进程证据的记录，或 service 启动时对"已有 stopProof 的旧记录"自动 reconcile/清理

**#5（中 / CONFIRMED）MCP `testConnection` 无任何调用级超时，恶意/异常 server 可让设置页永久挂起**
- 位置：`extensions/mcp/.../McpHandshake.kt:74-104`（suspend 函数内无 withTimeout/NonCancellable）＋ `McpHttpClientFactory.kt:11-53`（`newOkHttpClient` 只配 SSE 与 interceptor，无 callTimeout/read/write timeout、未装 Ktor HttpTimeout）
- 失败场景：与 A2A 客户端（显式 45/90s callTimeout）不同；server 接受连接后返回 200 SSE 流并以 <10s 间隔持续发 keep-alive 字节（不断重置 OkHttp 默认 10s 读超时）→ `initialize` 永不完成 → 调用线程与 UI 无限挂起，无超时、无取消入口
- 修法：`newOkHttpClient` 加 callTimeout（或 OkHttp read/write 上限），并在 `testConnection` 外包 withTimeout

**#6（中 / PLAUSIBLE）工具结算进入"requiresReview"（合法设计态）后 turn 被标 FAILED/INTERNAL，取消语义丢失**
- 位置：`app/.../chat/ChatToolCalls.kt:264-301`（`requiresSettlementReview → settleBatchCall(callId, sideEffectUnknown = true)`）＋ `app/.../agent/TurnCoordinator.kt:117-129`（`settleCall` 存 UNKNOWN；`requireBatchSettled` 对 UNKNOWN 直接 `require` 抛 ISE）＋ `TurnCoordinator.kt:293-297`（`openNextModelCall` 调 `requireBatchSettled`）＋ `ChatService.kt:3705-3710`（runTurn `catch (e: Exception)` → FAILED/INTERNAL）
- 失败场景：协调器把框架**合法产生**的"副作用未知、需人工复核"结算态当作编程不变量违例抛 ISE → 用户在工具执行中点停止 → 工具返回"启动后取消"（requiresReview）→ slot 结算 UNKNOWN → 抛 ISE → turn 终态 FAILED/INTERNAL（用户看到"内部错误"而非"已取消"），且工具结果行已持久化但对应 model-visible 消息从未写入，store 与消息表不一致
- 修法：`openNextModelCall` 前检测 UNKNOWN slot 并走专门的 review/cancelled 终态路径

#### 低严重度

**#7（低 / CONFIRMED）quickjs service 在 EXECUTE 拒绝路径不关闭已接收的 PFD（fd 泄漏）**
`JsExecutionService.kt:105-135`——`handleExecute` 的畸形 parcel/校验拒绝/instance busy 三个分支直接 return；PFD 已由 `JsExecutionWire.readExecute` 读出；只有 `runPayloadAndExecute` 的 finally 回收。source > 64KiB（走 PFD）且撞 #1 的 deadline 过期拒绝 → 每次拒绝泄漏 1-3 个 fd（实例一次性有界，故低）。修法：try/finally 统一 closeQuietly 三个 envelope PFD。

**#8（低 / CONFIRMED）调用方提供的 outputFile 在 service 校验通过前就被 TRUNCATE**
`JsTransportPreparation.kt:54-64`——client 侧 `MODE_WRITE_ONLY or MODE_CREATE or MODE_TRUNCATE` 打开输出文件，发生在 bind 与 service 校验之前。调用方复用有内容的文件当 outputFile；执行因 deadline 过期/instance already used 被拒 → 结果失败且文件原内容被破坏。修法：先写私有临时文件、成功后 rename。

**#9（低 / CONFIRMED）oneway EXECUTE 事务直接崩掉 isolated 进程而非稳定拒绝**
`JsExecutionService.kt:72-73`——`CODE_EXECUTE` 分支 `requireNotNull(reply)` 在 try 块之外，`FLAG_ONEWAY` 时 `reply == null` → ISE 穿出 `onTransact`，违背该类"reply 永远携带稳定状态、绝不崩溃"的注释承诺，进程死亡且一次性实例白烧。修法：`reply == null` 时直接 `return true`。

**#10（低 / CONFIRMED）skills `sessionOverrides` 按 sessionId 无界增长**
`extensions/skills/.../SkillRepository.kt:57,127`——`linkedMapOf<String, MutableMap<...>>` 只 getOrPut，:178 只 remove(key)，无按会话驱逐。长驻进程 + 大量短会话 → 内存缓增。修法：会话终结时清理或改 LRU 上限。

**#11（低 / PLAUSIBLE）用户在 deadline 之后取消，结果被报 TimedOut 而非 Cancelled**
`JsExecutionService.kt:440-450`（deadline 优先于 interrupt 分类）＋ `CodeJavascriptRunTool.kt:233,264`（只有 INTERRUPTED 且 call.cancel 才映射 Cancelled）。JS 恰好拖过 deadline，用户 0.2s 后点取消 → 回 TIMEOUT（需 engine 在 deadline 后被 interrupt 及时打断才成立）。

**#12（低 / PLAUSIBLE）打满 input 上限时程序先整体物化再做尺寸检查，host 堆瞬时放大数倍**
`JsExecutionService.kt:323-342` ＋ `JsAbiAssembly.kt:137-191`——先拼完整 String（输入字面量最坏 6 倍展开）再 `toByteArray` 检查；`maxWrappedBytes` 用 Int 算术。`maxInputBytes` 抬到 32MiB 上限并传入大量会展开的合法 JSON（如 U+2028）→ 堆瞬时峰值 ~150-250MiB 逼近 OOM（边界恰好不溢出但余量仅 8KiB）。修法：按上限预检 + Long 算术。

**#13（低 / PLAUSIBLE）解压中途失败留下部分文件在模型可见工作区**
`tools/files/.../FilesExtractTool.kt:172-218`——`ArchiveCodec.extract` 失败仅返回 "extraction stopped"，无清理。畸形/恶意 zip 解到一半触发限额 → 目标目录留下半成品文件，可能误导模型后续操作基于残缺数据。修法：失败时删除本次写入条目（或先解临时目录成功后 move）。

#### 一、秘密与凭据

**发现 1.1（低 / CONFIRMED ✅抽查）** `runtime/cli-app/.../CodexLoopbackServer.kt:106,116` — `ServerSocket(port)` / `ServerSocket(0, 4)` 未指定绑定地址，默认通配 0.0.0.0。攻击者 = 同一 Wi-Fi 恶意设备；前置条件 = per-app 网络命名空间关闭（浏览器把 `http://localhost:1455` 回调送进应用进程本身就要求两者共享命名空间，合法流程能跑通的场景下此监听同时暴露到设备 LAN IP）。路径 = TCP 连 `<设备IP>:1455` 发任意垃圾 GET：`await` 循环对 Ignored 结果持续等待直到 180s 超时，且成功/失败都返回特征化 HTML（"Helix login complete"）。后果 = 登录 DoS（拖满超时）+ 在线指纹（探测出"该设备此刻正在做 Codex 登录"）。**代码窃取路径不成立**：state 为 256-bit SecureRandom（CodexOAuth.kt:56），即使 state 泄露，code 兑换还需进程内存中的 PKCE verifier（:57），双因子均不可获取。缓解：`ServerSocket(0, port, InetAddress.getLoopbackAddress())` 显式绑定回环（一行）。

**发现 1.2（信息级 / CONFIRMED）** `app/src/main/AndroidManifest.xml:99-114` — `McpOAuthCallbackActivity` exported + BROWSABLE，同设备任意本地应用可构造 `helix://oauth/callback?state=...&code=...` intent 直达。无 state 值（进程内存随机值，探测不到）时回调被拒，仅可制造登录失败态（DoS 单次登录）；state/PKCE/redirect_uri 相等/一次性消费四道绑定封死 code 窃取。不是可利用漏洞，记录在案作为导出面清单。

#### 总体安全姿态

Helix 的安全姿态显著高于同类 agent 运行时的常见水平：核心边界（SSRF、策略/审批、秘密存储、工具执行）全部呈 fail-closed 设计且防御分层独立——SSRF 有"解析全候选校验 + 连接对端再验证 + 逐跳重定向重检"三重闭合，审批绑定 11 个非模型声明字段使参数伪造无法复用授权，两个 secret store 均以 Keystore 不可导出 GCM 密钥 + 0600 + 原子写落地，工具执行面无任何 shell 字符串拼接面。发现的 7 项全部为低/信息级且多数需要用户配合或特定构建 flavor 才成立，无一条构成同设备恶意应用可直接利用的高危路径。最值得修的两项是 loopback OAuth 服务器的通配绑定（一行）和浏览器下载双重扩展名检查（一处逻辑）；最值得关注的是 `file_paths.xml` 的 `all-files` 宽域——它今天无害，但属于会随代码演化而变现的潜伏风险。整体结论：可发布姿态，建议将上述低危项排入常规清理而非阻塞版本。

#### 簇 E：HXA-217 request context manifest + 会话能力/输入簇

**总评**
manifest 管线主体符合 ADR-010：modelCallId 每个模型步推进、逐次模型调用一行（每请求语义成立）、256KiB 单行有界编码、JSONL 导出集成完整，且单测+基准+设备测试+迁移夹具覆盖扎实。偏差集中在边界：压缩（compaction）路径的 manifest 用合成 `summary-msg-$idx` ID 且 `inputIds` 置空，丢失真实消息 ID 和"摘要吸收来源"信息，直接抵触 ADR"按实际请求顺序的实际消息 ID、区分摘要来源与直接来源"；manifest 写入无隔离，`ChatService.runTurn` 的 catch-all 会把诊断写失败放大为整 turn 失败，违反 ADR"诊断写失败不单独阻断合法模型调用"；溢出策略 `take(512)` 保留最旧、丢弃**最新**消息且不记录原始来源数量。输入侧是半成品：@mention 候选从未被供给（死 stub）、`/help` 落入 else 分支把字面 "/help " 插进输入并发给模型、任何 slash 选择都清空整份草稿而非仅命令行。

## 四、总体评价

9/18 至今的 191 个提交以功能密度换来了三笔债：**ChatService 从 2876 涨到 4047 行**、**性能类发现整体未动**、**新功能测试/文档跟不上**（13 个新子功能中消息分享/搜索导航/代码块折叠等零测试或零文档）。同时崩溃级问题全部修复且质量良好，安全面经本次专项审查确认为可发布姿态。engine 收敛（结算原子事务 + 调度屏障 + 启动对账）的测试工程是本轮最扎实的（SQL trigger 逐阶段故障注入、恢复幂等双跑），但其"启动对账闭环"**不覆盖非终态父的 2-RUNNING 场景**——该场景在 HXA-015 时代的串行 require 处就中断，对账路径执行不到（见第五节 P0-1，独立报告独立发现、本线确认）。

最值得注意的是四个"静默失效"型问题：孤儿 GC 从未接线（功能不存在但提交记录看起来已完成）、工具耗时投影断链（徽章轮次结束后消失且测试盖不住）、quickjs 小 timeout 全灭（如果工具侧真用过 100ms 级 timeout，JS 执行一直是 100% 失败）、browser 重建后死标签页（显示旧 URL 但刷新无效，用户以为页面还在）。这四类的共同特征是**"实现存在 + 单测通过"但端到端链路不成立**——建议在验收标准里加入"功能必须有生产调用方 + 至少一条 androidTest 触达真实投影路径"的硬性要求。

### 6.1 模块层（30 模块）——方向合理，2 个真问题 + 1 个过切信号

- `core` 五模块分层干净：`model` 零依赖 → `agent/policy/workspace/storage` 依赖 `model`
- `provider` 按协议各一模块（`api` 契约 + `openai-responses`/`openai-chat`/`anthropic` 适配器），每个适配器 ~450-482 行单一职责 codec，内聚高

**真问题 / 澄清**：
1. **`:app` 过大**：main 55,182 行 / 356 文件，约占 main 源 38%（含测试全源集 ~46%，独立报告 F1）。其余 29 个模块合计 ~88K 行——单一模块占了近四成。
